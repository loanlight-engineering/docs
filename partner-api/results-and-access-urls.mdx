Once an audit is `complete`, partners read its findings two ways: the structured JSON from `GET /api/v1/partner/audits/:auditId/results` (see [Audits API](/partner-api/audits)), or a short-lived portal viewer URL minted by `POST /api/v1/partner/audits/:auditId/results/access-url`. This page covers the result payload shape and the access-URL token lifecycle.

## Result payload shape

When the run is `complete`, the results endpoint spreads `AuditResultsService.getFormattedResults(auditId)`. The top level is:

```json
{
  "auditId": "uuid",
  "loanId": "uuid",
  "status": "complete",
  "startedAt": "<iso>",
  "completedAt": "<iso>",
  "summary": {
    "totalIssues": 4,
    "criticalIssues": 1,
    "warnings": 3,
    "checks": { "recorded": true, "ran": 42, "needsReview": 4, "counts": { "Passed": 38, "Missing": 4 } }
  },
  "agents": { }
}
```

<Warning>
`summary.totalIssues`, `summary.criticalIssues`, and `summary.warnings` are **deprecated** (LOA-3301). Read `summary.checks` and each agent block's `coverage` instead. Removal is scheduled one month after this reaches production.
</Warning>

### The agents object

`agents` is keyed by agent name; a key is present only if that agent ran. Possible keys:

| Key | Shape | Notes |
| --- | --- | --- |
| `piiValidation` | `{ status, results (dep.), checks, coverage }` | One check per displayed field × document × borrower row, plus Not-applicable checks. [PII validation](/agents/pii-validation) |
| `documentHealth` | `{ status, results (dep.), checks, coverage }` | One check per document × check type (`presence`, `completeness`, `signature`, `expiration`). Signature checks have `checkType: "signature"`. [Document health](/agents/document-health) |
| `signatureVerification` | `{ status, results }` — **deprecated** | Problem-only array. Signatures are now `documentHealth.checks` entries with `checkType: "signature"`. Removal tracked in LOA-3301. |
| `propertyData` | `{ status, results (dep.), checks, coverage }` | One check per property rule. [Property data](/agents/property-data) + [red flags](/agents/property-red-flags) |
| `urlaCompleteness` | `{ status, checks, coverage }` | 1003 completeness checks, one per rule outcome per borrower. **Absent** when the 1003 agent was not planned; present with empty `checks` and unrecorded `coverage` when it was planned but has no recorded results. |
| `creditEvaluations` | `CreditReportPayload[]` (array) | Each evaluation now carries `coverage` (over that report's own rows) and each `complianceResults` row carries `label`, `classification`, `reason`. [Credit evaluation](/agents/credit-evaluation) |
| `appraisalEvaluation` | `AuditAppraisalProjection` | Carries `coverage` and each `complianceResults` row carries `label` and `classification`. [Appraisal-Evaluation agent](/agents/appraisal-evaluation) |
| `bankStatementIncome` | `BankStatementIncomeCompleted \| BankStatementIncomeSkipped \| { status: "failed", results: [] }` | No `checks` or `coverage` block. [Bank-statement income agent](/agents/bank-statement-income) (entitlement required) |

#### bankStatementIncome block

The `bankStatementIncome` key is present only when the agent was planned (entitled + requested, or entitled + `defaultOnLanes` default). A key is **never omitted silently** — if the agent was planned but did not run, a `skipped` or `failed` block is surfaced explicitly.

**`completed` shape:**

```json
{
  "status": "completed",
  "summary": {
    "qualifiedIncomeMonthly": 8500.00,
    "qualifiedIncomeAnnual": 102000.00,
    "borrowerType": "personal",
    "incomeQualification": 12,
    "statementCount": 12,
    "findingsCount": 2,
    "monthlyBreakdown": [
      {
        "month": "2025-01",
        "deposit_total": 8750.00,
        "gross_deposit_total": 9200.00,
        "deposit_count": 4,
        "mom_change_pct": -0.02,
        "largest_deposit": 4800.00
      }
    ]
  },
  "detail": { },
  "findings": [ ],
  "findings_truncated": false,
  "findingsTotal": 2
}
```

The `summary` is a **frozen snapshot** taken at agent completion and stored on `agent_runs.output`. A later recalculation, settings change, or re-claim does not alter what a past audit reported. Rows completed before the snapshot feature launched fall back to live derivation.

**`skipped` shape** (agent was planned but did not run):

```json
{ "status": "skipped", "reason": "no_bank_statement_income_document" }
```

Partner-visible `reason` values: `no_bank_statement_income_document`, `missing_borrower_type`, `indeterminate_income_qualification`, `not_entitled`, `missing_loan_id`, `dev_flags_skip_langgraph`, `trigger_error`, `audit_failed_before_trigger`. Unrecognized values are collapsed to `null`.

**`failed` shape:** `{ "status": "failed", "results": [] }` (extraction error or ledger deadline).

Each non-credit issue object carries fields such as `issueKind`, `message`, `confidenceScore`, `documentRef`, `severity`, `category`, `expirationDate`, `daysUntilExpiration`, `fieldName`, `documentName`. The [issue kind taxonomy](/pipeline/issue-kinds) explains the codes.

### Checks and coverage

Each agent block except `bankStatementIncome` now carries `checks` and `coverage`.

**`checks`** is an array of labelled check objects, one per check the portal's readers produce. Every check object carries:

- `checkId` — stable identifier within the audit. Format varies by agent: `<fileId>|<checkType>` for Document Health; `<validationId>` or `na|<field>|<borrowerIndex>` for PII; `<ruleId>` for Property Data and URLA.
- `label` — a plain string, never an enum (new labels must not break strict clients, LOA-1088). Current values include `Passed`, `Missing`, `Incomplete`, `Flagged`, `Not applicable`, and others. `null` when the row is not a check (a lender-disabled Credit rule, or an appraisal `DIFF_*` / `XDOC-*` row). Treat unknown values as opaque.
- `classification` — always `null`; reserved.
- Agent-specific fields (see the table above for each block).

**`coverage`** summarises whether the agent's checks were recorded and, if so, how many ran:

```json
{ "recorded": true, "ran": 12, "needsReview": 2, "counts": { "Passed": 10, "Missing": 2 } }
```

When `recorded` is `false`, a `reason` string is present instead of counts:

```json
{ "recorded": false, "reason": "not_evaluated" }
```

Possible `reason` values: `saved_before_coverage`, `not_run`, `not_complete`, `stale`, `not_evaluated`, `unreadable`, or an agent-specific failure reason. An unrecorded coverage is not a zero count.

**Legacy `results` arrays** on `piiValidation`, `documentHealth`, and `propertyData` are **deprecated** — they list problem rows only; `checks` lists every row including passing ones. The `signatureVerification` key itself is deprecated: its content is now in `documentHealth.checks` with `checkType: "signature"`. Removal for all deprecated fields is tracked in LOA-3301.

If a labelled reader throws, its block degrades gracefully: `checks: []` and `coverage: { recorded: false, reason: "unreadable" }`. The legacy `results` array and the HTTP 200 response are unaffected.

### Summary buckets

`summary` carries `{ totalIssues, criticalIssues, warnings, checks }`. `summary.checks` is a coverage union over the agents the portal hero counts: Document Health (signatures included), Data Consistency, URLA Completeness, Properties, Credit (superseded reports excluded), and Appraisal. Skipped agents are excluded; Income is never counted separately. `summary.checks` is unrecorded when any counted agent is unrecorded, reporting the first such agent's reason. When every counted agent is excluded by the ledger, `summary.checks` is `{ recorded: true, ran: 0 }`.

`summary.totalIssues`, `summary.criticalIssues`, and `summary.warnings` are **deprecated** (LOA-3301, removal one month after this reaches production). They count raw agent outcomes before overrides; `summary.checks` counts post-override labelled checks — these totals legitimately differ. Issue kinds and severities are bucketed into critical vs warning (critical wins; the buckets are disjoint). Credit severities are derived from rule outcome (`FAIL → HIGH`, `WARNING → MEDIUM`; `PASS`/`SKIPPED` excluded). The full bucket sets live in [issue kinds](/pipeline/issue-kinds).

## Credit results

<Note>
**Credit lives under `agents.creditEvaluations` (an array).** The legacy top-level `creditEvaluation` key is stripped from the partner response (`const { creditEvaluation: _legacy, ...agentsWithoutLegacy }`). `creditEvaluations` is absent entirely when no credit agent ran.
</Note>

Each `creditEvaluations[]` item is a `CreditReportPayload`:

| Field | Notes |
| --- | --- |
| `id`, `lenderId`, `userId`, `loanId` | identifiers |
| `status` | `pending \| running \| completed \| failed \| reviewed` |
| `inputFilename`, `auditedCreditDocumentFileName` | source document names (`auditedCreditDocumentFileName` nullable) |
| `extractedData` | parsed credit report fields |
| `complianceResults[]` | each `{ ruleCode, name, category, outcome (PASS\|FAIL\|WARNING\|NEEDS_INFO\|SKIPPED), message, severitySource, overridden, originalOutcome, overrideReason, overrideUser, overrideAt, label, classification, reason }`. `label` is a plain string (see [checks and coverage](#checks-and-coverage)); `classification` is always `null`; `reason` is why a SKIPPED or errored row reached no verdict (absent on verdicts). |
| `coverage` | Coverage over this report's own rows; a superseded report keeps its own. Unrecorded (`not_evaluated`) when the report has no results. See [checks and coverage](#checks-and-coverage). |
| `aiSummary` | narrative summary |
| `isScanned`, `coveragePercent`, `overallRisk` | quality / risk signals |
| `dtiRatio`, `grossMonthlyIncome` | computed ratios |
| `ruleSetId`, `selectedRuleSources[]` | which rule set evaluated |
| `errorMessage` | nullable |
| `startedAt`, `completedAt`, `createdAt`, `updatedAt` | timestamps |

<Warning>
**The partner surface omits `metrics`, `inputS3Key`, and `triggeredBy`** — these are portal-only fields. The credit projection runs with `{ redact: true, triggeredBy: null, includeInputS3Key: false }`, and `complianceResults` are sorted ascending by `ruleCode`. Rows with `status ∈ {pending, running}` are skipped.
</Warning>

## Access URLs

`POST /api/v1/partner/audits/:auditId/results/access-url` mints a short-lived, single-use link into the lender portal's results viewer. It is backed by `ResultsAccessService` (`services/results-access.service.ts`).

```json
{
  "url": "https://portal.../results/audits/<auditId>?token=<JWT>",
  "expiresAt": "<iso>"
}
```

### Token lifecycle

<Steps>
  <Step title="Mint an exchange token">
    `generateAccessUrl(auditId, lenderId, lenderCode, loanId)` produces an HS256 JWT (`expiresIn = ttlMinutes * 60`) with claims `{ auditId, lenderId, lenderCode, loanId, purpose: "partner-results-exchange", embedContext: "top", iat, exp }`. The URL is `{baseUrl}/audits/{auditId}?token={jwt}`.
  </Step>
  <Step title="Consume it once">
    When the portal opens the URL, a one-shot Redis `SET NX` consumes the exchange token (single-use), then `mintViewToken` (`packages/app/src/lib/results-access-token.ts`) issues a view token with `purpose: "partner-results-view"`.
  </Step>
  <Step title="Read results">
    The portal proxy forwards the view token as the bearer on every `/api/v1/portal/audits/...` request. `verifyViewToken` checks the signature and `purpose` claim with a 5-second clock tolerance; the `lenderId` comes from the claims, never from a header.
  </Step>
</Steps>

### Configuration and failure modes

| Env var | Default | Notes |
| --- | --- | --- |
| `PARTNER_RESULTS_BASE_URL` | none in prod (dev: `http://localhost:3001/results`) | Missing in prod → `503`. |
| `PARTNER_RESULTS_JWT_SECRET` | none in prod (dev/test fallback string) | Missing in prod → `503`. |
| `PARTNER_RESULTS_TOKEN_TTL_MINUTES` | `60` | Token lifetime in minutes. |

<Warning>
If the service is misconfigured in production, `isConfigured()` returns false and the access-url endpoint throws `503 ServiceUnavailableException`. The endpoint also returns `409` if the audit is not yet `complete`.
</Warning>

`ResultsAccessService` is shared with the EPC integration, which mints `epc-results-exchange` / `epc-results-view` tokens through the same code path.
