LoanLight migrated from `drizzle-kit` to [Atlas](https://atlasgo.io) in LOA-3403 (2026-11-14). New migrations go exclusively in `packages/api/db/migrations/atlas/`. The older numbered files under `packages/api/db/migrations/` (and `meta/`) are a **frozen history**: CI fails any PR that adds or changes them.

## Atlas migrations (LOA-3403, current)

All commands run from `packages/api` unless noted.

<Warning>
`pnpm db:generate`, `pnpm db:generate:custom`, and `pnpm db:renumber` are **retired** and exit 1 with a pointer to the Atlas workflow. Do not use them for new migrations.
</Warning>

### Setup

First time on a machine, or when anything looks wrong:

```bash
pnpm atlas:doctor
```

This checks that Atlas is at the pinned version (`infra/lib/atlas-version.ts`), that `atlas login` to org `loanlight` is current, that Docker is running, and that the local database is reachable. It prints the fix for each failure.

### Authoring a migration

<Steps>
<Step title="Schema change (TypeScript)">
Edit `src/database/schema/`, re-export the table from `schema/index.ts`, then:

```bash
pnpm db:new <name>
```

Atlas diffs the schema against the migration directory and writes a new timestamped file (`YYYYMMDDHHmmss_<name>.sql`) in `packages/api/db/migrations/atlas/`. Review the SQL — never hand-author DDL that the schema can express.
</Step>
<Step title="Hand-written SQL (backfill, seed, trigger, partial index, CHECK, etc.)">
```bash
pnpm db:new --blank <name>
```

Write the SQL, then validate and lint:

```bash
atlas migrate hash --env local
atlas migrate lint --env ci --latest 1
```
</Step>
<Step title="Apply locally">
```bash
pnpm db:migrate
```

A database built before the Atlas cutover is handed to Atlas automatically. The command refuses a non-local database (for example, an open `pnpm db:connect:*` tunnel on port 5432 — close the tunnel first). To reset a stale local DB:

```bash
pnpm db:migrate --reset          # preview what would be deleted
pnpm db:migrate --reset --yes    # do it
```
</Step>
<Step title="After a rebase or gt sync">
If `atlas.sum` conflicts or looks wrong after rebasing:

```bash
pnpm db:rebase
```

The first output line names the base branch it compares against. If it prints `Next: git rebase --continue`, continue the rebase; otherwise commit the result. Never hand-edit `atlas.sum` or a migration already on `main`.
</Step>
</Steps>

Never run `atlas migrate push` manually — CI pushes to Atlas Cloud after merge.

**Local schema check.** To verify that your Drizzle schema matches the Atlas migration history (the same check CI runs):

```bash
pnpm atlas:no-op-check
```

This exports the Drizzle schema, diffs it against `db/migrations/atlas`, and exits non-zero if they diverge. It requires Docker (`atlas.hcl`'s `ci` env uses a local Postgres container). It replaces the former `pnpm validate:migrations` command.

### Atlas configuration

Config lives in `packages/api/atlas.hcl`. Three environments are defined: `local` (development), `ci` (lint and schema diff), and `rebuild`. The migration directory for all three is `file://db/migrations/atlas`. The Atlas Cloud org is `loanlight`. The `drizzle` and `atlas_schema_revisions` schemas are excluded from every env.

## Drift canaries

Because `drizzle-kit generate` re-derives SQL from the schema, a schema file that drifts from the latest migration causes a silent revert on the next generate. A set of spec canaries pins the high-risk cases (`src/database/schema/*.spec.ts`):

| Spec | What it pins |
|---|---|
| `timestamp-invariants.spec.ts` | Every timestamp column uses `{ withTimezone: true, mode: "string" }`. Omitting it breaks API date formats. |
| `index-direction.spec.ts` | DESC indexes must be declared `` sql`${t.col} DESC` `` or generate reverts prod to ASC. |
| `fk-ondelete-policy.spec.ts` | Drizzle `onDelete` mirrors the migration `ON DELETE` action exactly (e.g. `credit_rules.source_template_id` is not an FK). |
| `fk-repoint.spec.ts` | `relations.ts` repoints match schema `foreignKeys` on both sides. |
| `operator-check-drift.spec.ts` | The appraisal operator union (incl. `abs_less_than*`) matches the latest migration. |
| `migration-0161-classification-split-modes.spec.ts` | The classification-mode CHECK set. |
| `migration-0203-agent-platform.spec.ts`, `migration-0204-audit-runs-not-null.spec.ts` | The agent-platform and `audit_runs` NOT NULL migrations. |
| `migration-0202-audit-runs-lender-anchor.spec.ts` | The `audit_runs` lender-anchor EXPAND migration. |
| `migration-0201-asset-runs-loanless-runnum.spec.ts` | The `asset_runs` loanless `run_number` uniqueness. |
| `result-readers.spec.ts` | `red_flag_results` reads use the triple `orderBy`. |

<Note>
The timestamp invariant is why nearly every timestamp column is declared `timestamp(..., { withTimezone: true, mode: "string" })`. A `pg.types.setTypeParser` override returns raw ISO strings (no JS `Date` coercion) for timestamptz/timestamp OIDs.
</Note>

## Squashing migrations — LOA-1495

<Note>
`pnpm migrate:squash` and its supporting scripts (`squash/equivalence-proof.ts`, `squash/run-equivalence-proof.ts`, `squash/pinned-spec-sweep.ts`) were deleted in LOA-3719. The squash tooling is no longer available. The first (and final) squash has already been executed; the Drizzle chain is frozen and Atlas owns all new migrations. The description below is retained for historical context.
</Note>

The migration chain only grows. `pnpm migrate:squash <cutoff-idx>` collapsed the settled
prefix (entries `0..cutoff` in journal order) into a **baseline set** without touching the
database schema:

- One transactional `0000_baseline.sql` (all non-enum bodies, wrapped in `BEGIN;…COMMIT;`).
- N isolated enum baselines — each `ALTER TYPE … ADD VALUE` is split into its own file because
  PostgreSQL forbids `ADD VALUE` inside a transaction.

After collapsing, the script rewrites the journal head, deletes the collapsed `.sql` files,
preserves and renumbers the tail (keeping each entry's original `version`/`breakpoints`/`when`
— only `idx` is rewritten), and emits an **append-only reconciliation manifest**
(`meta/_squash_manifest.json`). Re-running the same cutoff is a manifest-detected no-op.

The full operator flow:

```bash
pnpm migrate:squash <cutoff-idx>   # collapse entries[0..idx] → baseline set
pnpm validate:migrations            # exit 0; check 6 validates the manifest
pnpm squash:equivalence-proof       # schema + pg_dump diffs are empty
pnpm db:generate                    # expect "No schema changes"
pnpm test && pnpm test:migration    # both green
```

The cutoff is a journal **idx** (not a filename tag). Run `migrate:squash` on a branch freshly
cut from `main` so the captured pre-squash base commit stays a durable ancestor.

**Production is a zero-schema-DDL no-op.** Deployed databases already applied the collapsed
prefix. On the first CD deploy after merge, the `DbMigrate` Lambda reconciles the
`drizzle.__drizzle_migrations` ledger — an idempotent `INSERT` of the baseline-set hashes.
Superseded rows are retained (rollback safety). No application schema DDL runs. Every subsequent
deploy sees the same hashes and skips. End-to-end: **author + verify locally → commit →
merge → first INT deploy reconciles INT ledger → promote → first PROD deploy reconciles PROD
ledger.**

### First squash run (LOA-2351, 2026-09-02)

The first squash was executed on `main` on 2026-09-02. **321 migrations were collapsed at cutoff idx 320** into 11 baseline files: `0000_baseline.sql` (all non-enum DDL wrapped in one transaction) plus 10 isolated enum `ADD VALUE` files (PostgreSQL forbids `ADD VALUE` inside a transaction). The 19-migration tail was renumbered to journal entries 0–18.

The cutoff was derived from prod and INT applied-set intersections pulled over the RDS Data API and matched to the journal by SHA-256. Prod had applied through idx 322; INT through idx 328 (INT runs ahead due to unmerged branches). The intersection set idx 0–322 was the hard ceiling; a 7-day soak window inside that ceiling gave cutoff idx 320.

After pulling the squash onto a populated local DB, drop and rebuild the entire database, clearing the **`drizzle` schema** (not just `public`) so the `drizzle.__drizzle_migrations` ledger is reset before `db:migrate` reconciles against the new baseline hashes.

<Warning>
Never hand-collapse migrations or hand-edit `meta/_journal.json`, the
`drizzle.__drizzle_migrations` ledger, or `meta/_squash_manifest.json`. Run
`pnpm migrate:squash` and let it do this deterministically. After pulling a squash onto a
populated local DB, drop and rebuild, clearing the **`drizzle` schema** (not just `public`).
</Warning>

## Migration Lambda runtime guards (LOA-1919)

The `DbMigrate` Lambda runs as a CloudFormation custom resource on every deploy. Before LOA-1919, a blocked statement would silently exhaust the Lambda's full budget (up to 15 minutes), and CloudFormation's failure reason named neither the statement nor its blocker. Three hardening measures now apply:

**Session guards.** Immediately after connecting, the handler applies three Postgres session-level settings to the migration connection:

```sql
SET lock_timeout = '5s';
SET statement_timeout = '60s';
SET idle_in_transaction_session_timeout = '30s';
```

`lock_timeout` caps how long a migration waits for a table lock — and, as a side effect, how long it parks application queries behind it in the lock queue. `statement_timeout` bounds any individual statement that does acquire a lock. `idle_in_transaction_session_timeout` evicts a connection that opens a transaction and stalls. Source: `packages/api/infra/lambda/db-migrate/session-guards.ts`.

**Failure pointer.** Every Lambda error is re-thrown with the CloudWatch log group and stream name prepended (`failure-pointer.ts`). CloudFormation truncates long failure reasons at an internal limit, so the pointer leads and the detail trails — without this, an operator reading a red stack must grep all invocations to find which produced the error.

**Preflight edited-migration check.** After ledger reconciliation and before applying any pending migration, the Lambda checks whether any already-applied migration file has changed on disk (`preflight.ts`). Drizzle selects migrations by content hash, so an edit silently re-runs the migration, and not all are idempotent. If any edited migration is found, the Lambda fails fast with a list of the offending tags rather than proceeding.

**Lambda timeout.** `DbMigrateFn` timeout was reduced from 15 minutes to 5 minutes (300 s). The prior 15-minute budget was the ceiling for the whole function; a single statement blocking for that long manifested as an opaque Lambda timeout rather than a lock-wait error. The session guards now bound statement execution well within 5 minutes, so the shorter timeout brings CloudFormation failures to the surface faster.

## aus-db shared package (LOA-1961)

`@loanlight-engineering/aus-db` in `loanlight-shared` is the canonical, versioned distribution of the AUS database migration chain. It was created to make the chain consumable by the API deploy process, the Postgres release docker image, and Octy without each consumer duplicating the SQL files.

The package ships:
- `migrations/` — the full ordered migration chain (`*.sql` + `meta/_journal.json`).
- `schema/` — a copy of `packages/api/src/database/schema/`, shipped as raw `.ts` source.
- A locator API: `migrationsDir`, `schemaDir`, `readJournal`, `migrationFiles()`.

The migration chain is the load-bearing artifact and is fully self-contained. The schema copy depends on the `_payloads/` refactor (LOA-1990) to become fully self-contained; until that work is complete, do not compile against `schemaDir` directly.

Publishing follows the standard bump-to-publish flow. For the full package description, see [shared packages](/ops/shared-packages#aus-db-aus-database-migration-chain-and-schema).

## Two migration ledgers

Do not confuse:

- The **Drizzle DDL journal** (`_journal.json` + the numbered `.sql` files) — schema structure.
- The **`migration_runs` table** — a ledger for *data-backfill* migration scripts (PK `id`, `name`, `status` CHECK `pending | complete | failed`, `counts` jsonb, `notes`, `started_at`, `completed_at`). This tracks application-level backfills, not DDL.
