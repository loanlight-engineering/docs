The Billing Reports page at `/billing-reports` has two tabs: **Vendor Costs** (AI spend from the cost-attribution ledger, LOA-997) and **Billing** (the existing loan/agent credit report). A third tab surfaces the [LLM Experiments](/octy/llm-experiments) cockpit.

## Vendor Costs tab

The Vendor Costs tab (`VendorCostsView`) aggregates AI vendor spend from the `agent_runs.cost` and `audit_infra_steps.cost` JSONB ledgers across the date range and lender/agent filter. It queries at read time — there are no rollup tables — so the view always reflects the current ledger state. The default date range is **last 30 days**; URL-provided presets and custom `from`/`to` ranges override it.

### API

`GET /api/vendor-costs` (route `src/app/api/vendor-costs/route.ts`, query function `getVendorCostSummary` in `src/lib/vendor-costs.ts`):

<ParamField query="from" type="string (ISO date/datetime)">
Inclusive lower bound on `audit_runs.started_at`.
</ParamField>
<ParamField query="to" type="string (ISO date/datetime)">
Inclusive upper bound.
</ParamField>
<ParamField query="lenderId" type="string (repeated)">
Scope to one or more lender ids.
</ParamField>
<ParamField query="agent" type="string (repeated)">
Scope to one or more `agent_type` labels (or `infra:<capability>` for infra-step rows). Absent = all.
</ParamField>
<ParamField query="bucket" type="string">
Time bucket for the trend series: `hour`, `day` (default), `week`, or `month`.
</ParamField>

### Response shape (`VendorCostSummary`)

All dollar values in the response are projected via the **largest-remainder cent allocation** method so every displayed partition (by vendor, by lender, by day) sums exactly to the visible grand total at 2dp — no penny drift between widgets.

| Field | Notes |
|---|---|
| `totals.usd` | Sum over priced, non-estimated lines. |
| `totals.estimatedUsd` | Sum over client-counted lines (marked `estimated: true`). As of LOA-997, LlamaCloud retrieval is **not charged**, so `estimated: true` lines are no longer written for retrieval. `estimatedUsd` reads `$0` from retrieval on new runs; historical rows from before LOA-997 may still contain retrieval estimates. |
| `totals.interactiveUsd` | Spend from interactive/comment-chat calls (`interactive: true`); included in the above totals but broken out so consumers can split pipeline cost from on-demand. |
| `totals.unknownLines` | Billed-but-unquantifiable events (LLM errors, responses with no usage payload). Never zero-priced. |
| `totals.runCount` | Distinct (day, source, lender) tuples with captured spend. |
| `totals.todayUsd` | Spend since UTC midnight today, same lender/agent scope regardless of the selected range — a cockpit vital sign. |
| `byVendor[]` | Per-vendor `{ vendor, usd, estimatedUsd, calls }`. |
| `byOp[]` | Per-vendor · operation/model drill-down `{ vendor, op, usd, calls, credits, tokens, pages, estimated, interactive }`. LlamaCloud index lines now include `pages` (vendor-reported `pages_indexed` sum, LOA-997). |
| `byDay[]` | Trend series bucketed per `bucket` with per-vendor splits: `{ day, usd, vendors: Record<vendor, usd> }`. |
| `byLender[]` | Per-lender `{ lenderId, lenderName, usd }`. |
| `bySource[]` | Per-source-label `{ source, usd }` (source = `agent_type` or `infra:<capability>`). |

### Run-level cost insights (octy #97)

The **Vendor Costs** dashboard also surfaces run-level analytics computed at query time over both ledgers:

- **Costliest runs** — the above-p95 tail plus two below-p95 runs for context (under the UI's p95 divider line), each with its top-3 cost drivers inline (including page counts where available). Deep-links to `/audit-runs?q=<id>&audit=<id>`.
- **Run cost distribution** — a static-bucket histogram (`<$2 / $2–$5 / $5–$10 / $10–$20 / $20+`) with a **bucket-share** label in each histogram tooltip (e.g. ‘42% of runs”) plus an interpolated median, p95, and max.
- **Outliers** — amounts render amber and bold when above the p95 threshold (range-scoped on the dashboard; a trailing-30d `percentile_cont` baseline is used in the audit-runs table).
- **Sortable Cost column** — the audit-runs table can now sort by a per-run sum over both ledgers (`totalUsd + estimatedUsd`), probe-gated with a date fallback on pre-migration-0270 databases.
- **Per-run cost by source** (octy #104, replaces the former LlamaCloud indexing unit economics chart) — one dashed line per source (agents + infra) tracking dollars-per-run per trend bucket, with legend checkbox toggles. A solid neutral-ink line shows the blended all-source $/run (total spend ÷ distinct runs, same scope as the selected client rail). Legend items carry each source's range-total spend, replacing the former "Spend by source" meter grid. Absent sources render as gaps, never as $0. Line hues are fixed per agent from a colorblind-validated 8-slot palette.
- **Avg \$/run** — per source label and per lender, using exact distinct-run counts.

**Time zone.** The Vendor Costs dashboard anchors date-range presets (Today, Yesterday, Last 7 days, …) to **US Central Time** (CST/CDT via `Intl.DateTimeFormat`) rather than UTC. Custom From/To inputs and the trend-series labels also display in Central Time. Other Octy date filters (audit-runs, billing) remain in browser-local time.

### Vendor vocabulary

Nine vendors are tracked as of LOA-2100. Lines are attributed by the `vendor` field on each cost line; the aggregation layer is open — new vendors surface automatically without code changes.

| Vendor | Cost line type | Notes |
|---|---|---|
| `openai` | LLM tokens | Exact (usage payload) |
| `anthropic` | LLM tokens | Exact (usage payload) |
| `reducto` | Pages / calls | Exact (usage payload) |
| `llamacloud` | Index pages / classify calls | Exact (usage payload) |
| `attom` | API calls | **Estimated** (`estimated: true`); contracted $500 / 3,000 calls blended |
| `hasdata` | API calls | **Estimated**; $99 / 1,000,000 credits |
| `mashvisor` | API calls | **Estimated**; $0.2075 per call |
| `plaid` | Enriched transactions | **Estimated**; $2.00 / 1,000 transactions |
| `encompass` | Loan transactions | **Exact** (flat $3.00 per audit run, by contract); landed in `totalUsd`, not `estimatedUsd` |

A line whose provider cannot be mapped lands in `unknown`. Estimated lines (`estimated: true`) accumulate in `totals.estimatedUsd` and are separated from exact lines (`totals.usd`) in all response fields.

### Cost sources and double-counting

`classify_split_runs.cost` is **excluded** from this view: it is a per-document breakdown of spend already counted on the `preAuditClassification` agent run in `agent_runs`. Including it would double-count. Use `classify_split_runs.cost` only for per-document attribution (cost per source file), not fleet-level totals.

### IRIS cost attribution (LOA-2100)

The IRIS agent's LLM spend is attributed at the step level. Each LLM call inside `catalog-conversation.ts` carries the `LLM_STEP_METADATA_KEY = IRIS_VISION_CATALOG_STEP` metadata tag, so the cost handler writes a `step`-scoped cost line on the `agent_runs.cost` ledger. IRIS spend appears under `bySource[]` as `source = "iris"` with per-step drill-down in `byOp[]`.

## Audit Runs page

The Audit Runs page at `/audit-runs` is a cross-lender table of `audit_runs` rows with cost, status, agent mix, and issue counts. It is the operator surface for spotting high-cost runs, investigating failures, and deep-linking into the audit-run modal (see [Loan Lookup and audit-run modal](/octy/loan-lookup)).

The rightmost column is **Findings / Errors** (LOA-2111, octy #103). It carries two badges in a single cell:

- **Amber — findings**: sourced from `audit_runs.finding_count`, the canonical nine-bucket count maintained by loanlight-api (LOA-2113). A `NULL` value renders `—` ("not yet computed"), never 0, so a missing migration does not masquerade as a clean run. The column read sits behind the same `columnExists` probe as the cost columns, degrading to “not computed” rather than 500-ing on environments where the column has not yet landed.
- **Rose — agent errors**: sourced from `audit_errors` (the per-agent exception log). Deliberately excluded from `finding_count`; the separate badge and distinct colour (WCAG 1.4.1) keep the two axes distinguishable.

A click on the row opens the audit-run modal at the overview section.

## Billing tab

The Billing tab counts billable usage per lender over a date range. The logic lives in `src/lib/billing.ts`; shared definitions are in `src/lib/billing-shared.ts`. As of the agent-platform work (octy #84), billing is **catalog- and ledger-driven**: the billable agent set comes from the `agents` catalog and per-agent credit comes from the `agent_runs` execution ledger, replacing the old per-result-table existence probes.

<Note>
Migration `0317` (LOA-2100) set `agents.is_billable = true` for the `bankStatementIncome` agent. Completed `bankStatementIncome` runs now count toward billable units, including standalone portal runs (billed as loanless units keyed on `audit_run_id`). The precondition — portal runs having a real audit container so cost lines land on the ledger — was satisfied by migrations `0315`/`0316`.
</Note>

## The billable unit

A billable unit is **a loan (or, for a loanless run, a single audit run), counted once**. A unit is billable in a report when its **first** completed audit run lands in the window. "First completed" means:

- `audit_runs.status = 'complete'`
- `completed_at` is not null
- `is_shadow = false`
- `completed_at` (the unit's **earliest** such completion, `first_completed_at`) falls in `[from, to)` (half-open; both bounds optional for an open-ended report)

The unit key is `COALESCE(loan_id::text, audit_run_id::text)`, so loan-bound runs group per loan while each loanless run (a standalone portal appraisal, for example) is its own unit. Anchoring on first completion keeps re-audits from billing twice. The per-unit agent mix is the union of billable agents that completed across **all** of that unit's runs.

<Note>
Lender attribution is via **`audit_runs.lender_id`**, not `loans.lender_id`. The lender-anchored model makes `audit_runs.lender_id` non-null, which is what lets loanless runs bill correctly. For the rare loan whose runs span two lenders, the unit is attributed to the lender of its **earliest** completed run (the same first-completion anchor).
</Note>

## How agents are detected

The billable agent set is the DB **`agents` catalog filtered to `is_billable`** (`billableAgentTypes()`), so marking a new agent billable in the catalog bills it automatically — there is no per-agent SQL. A unit is credited with agent `X` when there is an **`agent_runs` row with `agent_type = X` and `status = 'complete'`** among the unit's completed runs. `complete` mirrors the old "produced results" signal, but a `failed` agent that left a partial result row is now correctly **not** counted.

The query builds one shared `billable_filtered` CTE (`completed → unit_first → unit_agents → billable`) used by both the summary and detail views; its `agents` column is the `text[]` of billable agent_types that completed for the unit. The agent filter intersects the requested `?agent=` values against the billable catalog first: selecting every billable agent applies no predicate (the count stays complete), a strict subset keeps units whose detected set overlaps the selection, and a request that intersects nothing valid selects nothing.

If the catalog has no billable agents, the report is empty by construction.

## Schema-drift handling

<Note>
Octy reads a **vendored schema that runs ahead of some deployed databases**, so the billing reader probes for column existence rather than assuming it.

- **`columnExists` drift-probe.** Platform reads (e.g. the `agent_runs` ledger reader) probe `information_schema.columns` once per `table.column`, cache the result, and **degrade to empty** rather than erroring when a column the migrations haven't landed yet is read. A genuine "absent" is cached; a transient failure is evicted so the next call re-probes.
- **Lender join.** The unit's lender is joined as `lenders.id = audit_runs.lender_id` (uuid to uuid). The optional `?lenderId=` filter compares on `lender_id::text` on both sides, and the values are bound as discrete IN params (node-postgres rejects a JS array bound as one param).
- **Ledger dependency.** Because credit is now keyed on `agent_runs.status = 'complete'`, an environment whose `agent_runs` ledger is not populated will under-count. This replaced the per-result-table `EXISTS` probes; the one intentional delta from the old probes is that credit runs which failed with partial output are now excluded.
</Note>
