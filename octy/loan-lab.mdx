Loan Lab (`/loan-lab`) generates synthetic mortgage loans — borrower data plus a generated PDF document set — and submits them to LoanLight int for a real audit run. It is a port of [loanclone](https://github.com/loanlight-engineering/loanclone), a local-only tool that previously ran on one engineer's machine with one set of credentials. The port makes scenarios team-accessible from any deployed Octy instance and makes a scenario something you can describe and save rather than a pull request.

Source: `octy/src/lib/loan-lab/` (core library), `octy/src/app/(app)/loan-lab/` (UI), `octy/src/app/api/loan-lab/` (Next.js API routes). Internal spec: `octy/docs/loan-lab.md`.

<Note>
**Loan Lab is always-on as of LOA-2953.** The `loanLabEnabled` CDK context gate was removed. The `/loan-lab` route and nav item are always present; a signed-out request gets a 401. The three required secrets (`PartnerApiKey`, `EncompassUatClientSecret`, `EncompassUatPassword`) must still be provisioned for the credentials to be available — see [Prerequisites](#prerequisites).
</Note>

## Where loans go

**Nowhere near production, from any environment.** `src/lib/loan-lab/config/destinations.ts` compiles in LoanLight **int**'s partner API and the **Concept (UAT)** Encompass instance. Both int Octy and prod Octy post to those same two endpoints — the URLs are code constants, not configuration. Only credentials are configured, and they carry int-scoped values in both environments.

| Destination | Payload | Run ends at | IDs recorded |
|---|---|---|---|
| LoanLight int | MISMO XML | **audit started** | loan id, audit id |
| Encompass UAT | loan-entity JSON | **loan + documents delivered** | GUID, loan number |

The two destinations are not symmetric. Creating a loan through the partner API does not start an audit — that is a separate call which the run makes. Creating via Encompass produces no LoanLight audit; start one through the normal pipeline and the loan appears in int under the test lender.

A run started from **prod** Octy creates its loan in **int**, so result links are absolute rather than relative.

## Isolation model

`audit_runs` has no `is_test` column. The only thing separating synthetic data from real data is the **name** of the lender it belongs to, and only a handful of call sites filter on it (`src/lib/billing.ts`, `classify-split-config/actions/staged-targets.ts`, the epc-sim modules).

Two environment variables control which lender names are used (LOA-2837):

| CDK context key | Env var | Used by | int | prod |
|---|---|---|---|---|
| `testLenderName` | `OCTY_TEST_LENDER_NAME` | billing, Findings Explorer, dry-run staged targets, EPC Simulator | `Demo Account - CSO #6` | `LoanLight` |
| `loanLabDestinationLenderName` | `LOAN_LAB_DESTINATION_LENDER_NAME` | Loan Lab preflight only | `Demo Account - CSO #6` | `Demo Account - CSO #6` |

The two variables answer different questions. Loan Lab creates loans in **int** from every environment (`config/destinations.ts`), so prod Octy's partner key resolves to an int lender — checking it against prod's own `OCTY_TEST_LENDER_NAME` (`LoanLight`) would refuse every run. `LOAN_LAB_DESTINATION_LENDER_NAME` lets the preflight check the destination environment's lender instead. Both variables fall back to `"Octy Test Lender"` when unset, preserving previous behaviour on undeployed instances.

<Warning>
`epc-sim/seed.ts::seedTestLender` refuses to run when `OCTY_TEST_LENDER_NAME` is set to anything other than the default `"Octy Test Lender"`. The seed upserts by name and would take over the configured real lender row if allowed to run.
</Warning>

Before creating anything, `loanlight/preflight.ts` calls the partner API's `GET /api/v1/partner/whoami` endpoint to confirm which lender the configured key belongs to, and **refuses the run** if it is not the `LOAN_LAB_DESTINATION_LENDER_NAME` lender. It fails closed: an unreachable identity endpoint is treated the same as a key pointed somewhere unexpected.

<Note>
Int is shared. Synthetic loans are visible in int dashboards, aggregate counts, the alert feed, and Datadog monitors alongside real runs. Scenarios designed to fail look like real incidents there. Int alert noise is expected to rise; check the lender before treating an alert as a regression.
</Note>

## Scenarios and runs

### A scenario is data

`src/lib/loan-lab/scenario/schema.ts` defines `ScenarioSpec` — a single Zod object describing a loan's shape, its borrower, which documents are produced, and which of them deliberately disagree with the loan.

Everything converges on this object: the 30 built-in presets are spec literals, the Generate agent emits one, deriving from a production loan produces one, and saving stores one. A spec is PII-free by construction (`scenario/overrides.ts` is an enumerated allowlist, not a free-form map), which is what makes derivation safe and lets a scenario move between environments as plain JSON.

`buildScenario(spec, { seed, clock })` turns a spec into MISMO XML, an Encompass payload, and document files. The **seed lives on the run, not the spec**: the same scenario run twice produces two different borrowers, while the same seed and clock produce byte-identical output — which is how the previewed borrower is the one that actually gets created.

### Surfaces

- **Generate** — describe a scenario in prose or edit the form. Both edit one object. A live preview shows the document manifest and borrower. Re-submitting edited prose replaces the whole spec and warns first.
- **Scenarios** — the library. Presets and your own scenarios in one list; presets are read-only and offer **Duplicate**.
- **Runs** — history, polled. Statuses are `running`, `succeeded`, `partial`, `failed`, `interrupted`. A `partial` run is flagged *audit outcome unreliable*, because an audit over an incomplete document set reports on the upload rather than the loan.
- **From a loan** — derive a scenario from a real production loan, showing what was read next to what was produced.
- **Results** — the LTV tester: a lender's eligibility matrix, one-cell launches, and what the EDU ledger computed for each run. See [The LTV tester](#the-ltv-tester) below.

### Database tables

Loan Lab's scenario library and run history are stored in two tables in loanlight-api's Aurora database. Both are vendored into `src/db/schema/loan-lab.ts`; the migrations belong to the loanlight-api repo.

**`loan_scenarios`** stores scenario specs. Key columns:

| Column | Type | Purpose |
|---|---|---|
| `slug` | `text` (unique) | Stable identity — presets carry their historical slug so `seedPresets()` can upsert without creating duplicates |
| `spec` | `jsonb` | A `ScenarioSpec` — validated by Zod on every read and write |
| `spec_version` | `integer` | Schema version, currently 1 |
| `source` | `text` | One of `preset`, `agent`, `derived`, `manual` |
| `source_prompt` | `text` | The prose prompt when the scenario came from an agent |
| `derived_from_loan_id` | `uuid` | Provenance pointer (never surfaced outside Octy — mild re-identification risk) |

**`loan_scenario_runs`** stores run history. Key columns:

| Column | Type | Purpose |
|---|---|---|
| `spec` | `jsonb` | The spec **actually** used — not a pointer, so editing a scenario does not silently rewrite what history claims was run |
| `seed` | `text` | Reproduces the exact borrower for this run |
| `destination` | `text` | `loanlight` or `encompass` |
| `status` | `text` | `running`, `succeeded`, `partial`, `failed`, `interrupted` |
| `loanlight_loan_id` / `loanlight_audit_id` | `uuid` | Set on the partner-API path |
| `encompass_loan_guid` / `loan_number` | `text` | Set on the Encompass path |
| `document_outcomes` | `jsonb` | Per-file upload outcomes |
| `heartbeat_at` | `timestamptz` | Written while the run is active; the reconciler moves abandoned `running` rows to `interrupted` after a deploy |

Octy tolerates the absence of these tables: `src/lib/loan-lab/scenario/store.ts` falls back to the in-code preset specs when the tables are unavailable, so scenario generation still works before the migration lands. Saving and run history are unavailable without the tables.

## The LTV tester

The Results tab (`ResultsPanel.tsx`, `ResultsLaunchControls.tsx`) generates a lender's matrix from its stored eligibility rules (`tester/matrix.ts`) and measures what EDU computes for each cell.

### One partner key per test lender

`LOANLIGHT_PARTNER_API_KEYS` is a JSON object of lender id → partner key, config only (`src/lib/loan-lab/tester/partner-keys.ts`). A matrix is generated for any lender, but launches only for a lender that has a key in the map, against that lender's own key (the token cache is per key). An absent or empty map reports `partner_keys_not_configured`; an invalid map or entry reports `partner_keys_malformed`. Neither state permits a launch. Stored results remain available.

A lender without an entry in a valid map reads `generate_only(no_partner_key)`; a matrix whose lender differs from the lender its key resolves to reads `generate_only(launch_lender_differs)`. A tester launch never falls back to the single `LOANLIGHT_PARTNER_API_KEY`.

On INT, key the map by `LOAN_LAB_INT_TESTER_LENDER_ID` (Demo Account CSO #6, `5916ace6-26c5-4038-8391-6c8d970d3ae2`, in `config/destinations.ts`):

```json
{"5916ace6-26c5-4038-8391-6c8d970d3ae2": "<partner key>"}
```

The nightly E2E cleanup lenders (`E2E_CLEANUP_LENDER_IDS`) wipe what they hold, so a scenario there would be deleted: they read `generate_only(cleanup_lender)` and never launch, even with a key in the map.

### Tester routes

All routes live under `src/app/api/loan-lab/tester/`, each behind `guardLoanLabRoute()` and `withLoanLabErrors`. The browser runs no tester rule; every view model is derived on the server.

- **`POST /api/loan-lab/tester/math`** — body `{ lenderId }`. Sweeps the lender's matrix in math mode (`tester/math.ts::runMathSweep`): each sweepable cell is one call to the partner evaluation route with the grid inputs, bounded by `MATH_TIMEOUT_MS`. No loan, no documents, no vendor cost. Returns `200 { sweep }` with `status: "swept"`, `sent` (cell id and run id) and `listed` (cells not sent, as `not_generable` or `unknown` with their reason). A refusal returns `409` whose `code` is the reason: `no_partner_key`, `launch_lender_differs`, an aborted preflight (`status: "aborted"`, `code` is the preflight reason), or a rules `unknown`.
- **`POST /api/loan-lab/tester/launch`** — body `{ lenderId, cellId, launch: "ab_pair" }` or `{ lenderId, cellId, launch: "staged", mode: "A" | "B" }`. One click launches one cell: an A/B pair (Mode A then Mode B on one seed and one clock value) or one staged run (stage 1, then stage 2 with the document set of `mode`). Returns `202 { runs }` on success. `409 { error, code }` otherwise: `busy` (a loan-backed tester run is already in flight for that lender), `no_partner_key`, `launch_lender_differs`, a cell that cannot launch, or a preflight failure code.
- **`GET /api/loan-lab/tester/results?lenderId=<id>`** — read only. Returns `persistence`, `results` (one item per stored scenario result, each with its derived `outcome`, the `report` a failed scenario files as an Octy bug report, and `newest`), `pairs`, `comparisons` (Mode A against Mode B per pair), `staged` (per staged run, its stages and transitions), `greyed` (target ledger inputs against the inputs Loan Lab wires), and `matrix` (the cells and the launch decision, or `rulesUnknown` when the rules cannot be read).

### Result labels and outcomes

Every result carries `test: "math" | "staged" | "A" | "B"`, `mode: "A" | "B" | null` and `stage: 1 | 2 | null`. A math result has no loan and no mode or stage; it shows as "math mode (not a loan)".

**Matrix cell outcomes** are `scenario` (launchable), `not_generable(<axis>)`, or `unknown(<reason>)`. When the lender's stored rules cannot be read at all, nothing launches and the reason is `rules_unreadable`, `no_rules`, or `rules_malformed`.

**Result outcomes** (`tester/outcome.ts::deriveOutcome`): `computed`, `incomplete`, `conflicting`, `stale`, `needs_review`, `unavailable(<reason>)`, `invalid_mode_a`, and `pending` (`launching` or `audit_running`). Every `unavailable` cause comes first, so a value is never shown when anything is unsure. A run that never reached a result shows its own state.

**Launch preflight** (`tester/decide-preflight.ts`) aborts for `destination`, `unknown`, `wrong_lender`, or `gate_off`. Locally it accepts only a loopback launch URL, collection URL, and database; deployed int accepts only the int destination and an int database.

### Request limits

The tester accepts at most 200 stored grid rows and 128 KiB of rules per request. Larger rule sets return `rules_too_large` before scenario generation or API calls; each continuation applies the same limits. Results stop at a 2 MiB stored-run window budget and an 8 MiB response ceiling. The response reports truncation at these limits; use its history cursor to read older results.

## Predicted findings and the fact catalog

`facts/catalog.ts` records what each loan fact means to LoanLight: where it lives in MISMO and in the Encompass entity, which documents it implies, and the loanlight-api rule that reacts to it (cited by path). A permanent resident implies a `permanent_resident_card` (`decl.status.citizenship`); alimony implies the family-law set (`decl.alimony.obligation`); renting implies `rental_history`.

`facts/predict.ts` turns any spec into the findings LoanLight should raise, from deterministic sources: the program's day-1 requirements in the vendored YAML against the documents the build produces, the catalog, and what the scenario was built to break (mismatches, appraisal defects, unsigned documents, and document dates against LoanLight's expiry rule). The preview shows them live, and flags a scenario whose declared `expect` disagrees. It is a prediction, not a grade: nothing yet compares it with the audit's actual result.

When a LoanLight rule changes, the catalog entry citing it is what goes stale. Update the entry, then the builders if a new fact needs emitting.

## Optional and Encompass-only fields

The form shows only what nearly every scenario needs. Two tiers sit behind **Add a field** (a search, not a catalogue):

- **Supported optional fields** (`fields/registry.ts`) — Loan Lab code builds them for both destinations and the fact catalog predicts their findings (alimony, marital status). A field is on the form exactly when the spec uses it. Adding one is a registry entry plus its control in `OptionalFields.tsx::FIELD_CONTROLS` — `OptionalFields.test.tsx` fails if either is missing.
- **Encompass-only fields** (`spec.encompassFields`) — raw Encompass paths from the vendored schema (`encompass/schema-index.ts`: approximately 8,700 scalar fields reachable without creating array rows; co-borrower fields, Encompass-assigned keys, and the generated borrower facts Encompass repeats are excluded). Checked before the run (`encompass/raw-fields.ts`), read back after it, never predicted, and absent from MISMO — so a LoanLight int run refuses the scenario (`409 encompass_only`) instead of sending it without them.

The scenario agent lists plain facts with no spec field in `analysis.unmapped`. The code searches the schema for candidates and a second small call picks one per fact, or none (`agent/propose-fields.ts`); the model can only choose from listed candidates. The result is shown as proposals to **Accept** or **Dismiss** — nothing is added automatically. A fact with no proposal is shown under **Map these yourself** with an inline schema search.

Guards in code, not prompt:

- `collectUnmapped` reads `unmapped` wherever the model put it, including nested in the spec.
- `withKnownGaps` detects co-borrowers, gifts, support received as income, and credit scores in the prose, and lists any the model did not name as unsupported. Such facts are never offered for mapping.
- `withoutProgramQuestions` turns a question choosing between loan programs into a stated assumption.
- The schema index leaves out generated borrower facts (name, SSN, birth date, income figures, credit scores) and all co-borrower fields — setting these by raw path would contradict the builder.

Accepted fields live on the scenario, so saving keeps them.

## Documents

The form's **Documents** section edits `spec.documents` through `scenario/documents.ts`. It starts from the **program's required set** (the day-1 list resolved against the lender YAML; the preview reports each document's `origin` because only the server reads the YAML): removing a required document excludes it, which LoanLight then flags missing; adding one the program does not require is an extra. **Exact set** switches to a plain list, starting from what the scenario produces so the switch changes nothing.

Predicted findings for documents the loan data implies (rental history for a renter) carry a `catalogType` and a one-click **Add** in the preview.

The agent maps document instructions the same way: "didn't provide" → `exclude`, "uploaded" (not required) → `extras`, "only X and Y" → an exact list, "N days old" → `perDocument.ageOffsetDays`, "unsigned" → `perDocument.signature`. A document Loan Lab cannot generate (green card, divorce decree, separation agreement, child support order, visa) is named as unsupported and will still be flagged missing.

**Expiry.** LoanLight counts a document's window to the estimated closing date, not to the day of the audit. Every run states a closing date 21 days out, under the shortest window a clean set carries (paystubs, 30 days), so a clean scenario expires nothing. `pdf/document-dates.ts` holds the rule and the dates for both the generator and the predictor.

**Appraisals and signatures.** An appraisal (`pdf/appraisal.ts`) can be added to any loan — no program requires one day 1. It is the scenario's own report: Form 1004 / 1073 / 1025 by property type, final opinion = the loan's property value, effective date = the document date. Clean by default; `documents.appraisal.defects` builds in poor condition, a distant comparable, a misstated proximity, or a missing E&O certificate. Documents on the YAML's `signature_required_documents` are signed in ink by default; `perDocument.signature: "unsigned"` leaves the signature off, and the preview predicts the missing signature as a finding.

## The scenario agent

`agent/generate.ts` makes the model show its work before the spec: split the prompt into loan-data and document facts, name the documents each implies, state every default it chose, and ask every question — but only ones whose answer changes the findings. Never the program, destination, or identity. The spec is built on the stated defaults, so it is runnable without answering; answering rebuilds it. The system prompt renders the fact catalog and each program's day-1 documents, so the model reasons from LoanLight's rules rather than guessing. The model does **not** author `expect` or predictions — those are computed from the spec after it answers.

## Errors

Every `/api/loan-lab/*` route is wrapped in `withLoanLabErrors` (`errors.ts`): an unexpected throw is logged as `[loan-lab] <route> failed (<code>)` and answered as JSON naming the cause — the upstream body for Encompass and the partner API, the Anthropic status and reason for the agent. A run that fails records the same message on its row. Nothing should reach the UI as a bare status code.

**Encompass rejections** get more detail, because Encompass's 400 body often does not name the field:

- `encompass/schema-check.ts` validates every payload against `config/encompass-loan-schema.json` (Encompass's loan-entity schema, captured by loanclone). The preview warns before **Run**; a rejection carries the fields the schema flags ("Schema check points at: …"). It is not a gate — the schema is a snapshot and Concept may accept a field it predates.
- Failures are logged as one line with the run id, seed, program, Encompass's request/correlation ids, the body (up to 4,000 characters), and the violations.
- `GET /api/loan-lab/runs/<id>/payload` rebuilds the payload a run sent from its spec, seed, and start time — with today's builder code, so a run made before a builder change may have sent something different (the response's `caveat` says so). Dates are day-granular, so with unchanged builders the rebuild is exact unless the run straddled a UTC midnight.
- `encompass/schema-check.test.ts` fails `pnpm test` if any preset's payload stops passing the schema.

## Cross-repo prerequisites

Two things live in **loanlight-api**, not in `octy`. Loan Lab degrades rather than breaks without them:

1. **`GET /api/v1/partner/whoami`** returning `{ lenderId, lenderName }` for the authenticated key. Without it the preflight cannot confirm the lender and refuses every run.
2. **The `loan_scenarios` and `loan_scenario_runs` tables.** Generate them with `pnpm db:generate:custom` in loanlight-api (hand-written `.sql` files break CI). Until the migration lands, presets still list (the store falls back to the built-in specs), but nothing can run: `POST /api/loan-lab/runs` answers `503 PERSISTENCE_UNAVAILABLE` because `startRun` writes a row before any work begins.

Also needs provisioning once, by whoever owns loanlight-api partner setup: the test lender row and its Encompass client-id mapping in int, a `partner_api_keys` row bound to it, and that key stored as a secret in both Octy environments.

## What was dropped from loanclone

The following loanclone features were not ported:

- **Clone Loan** — the Encompass GUID → clean → recreate → copy-docs wizard.
- **Load Test** — bulk staging, and the `$HOME`-browsing directory route.
- **`custom_upload` and `doc_set_builder`** — two non-generative modes; `documents.include` / `exclude` / `extras` cover the latter's purpose as data on the spec.
- **The MISMO-to-Encompass converter.** loanclone offered two paths into Encompass; Loan Lab uses the native-JSON path only. The converter was lossy — it silently dropped employer phone, previous-employment income, and HMDA race — so scenarios arrived carrying findings nobody asked for.

## Things worth knowing

- **The vendored lender config** (`config/default.yaml`) is hand-synced from loanlight-api, like the Drizzle schema. `findUnknownConditions()` fails the test suite if it gains a `day_1` condition the resolver does not understand.
- **Document type names disagree** between the YAML and the generator registry. `config/doc-type-aliases.ts` maps them and `findUnmappedDocTypes()` guards the gap. In loanclone this mismatch silently omitted the 1003, the paystub, and the W-2 from every YAML-driven document set — including the scenario called "Perfect Loan".
- **Listings are vendored**, not scraped. Six scenarios need real, publicly-resolvable addresses; loanclone fetched Zillow live. Refresh `config/listings.fixture.json` by re-capturing.
- **Runs are database-backed**, not in memory. Octy runs 2–4 ECS tasks, so a poll can land on a task that never heard of the run. A reconciler moves abandoned `running` rows to `interrupted` rather than leaving them stuck after a deploy.
- **Encompass runs read the loan back** after create and field writes (`encompass/read-back.ts`) — the key fields a scenario varies (loan amount, property value, purpose, occupancy, borrower profile, expense rows) plus every Encompass-only field — and name any it dropped or changed. Discarded fields ride on the run's `error` until `loan_scenario_runs` gains a dedicated column.
- **`scenario/regression.test.ts`** fingerprints every preset's MISMO, Encompass payload, and PDFs. A new capability must leave them unchanged; update the snapshot only when changing a preset's output is the point.

## Tester trap doors

- **An absent partner key means the legacy key.** In `loanlight/client.ts`, a call with no key (`undefined`) reads `LOANLIGHT_PARTNER_API_KEY`; `null` throws. Every call made for a tester lender — the preflight's `whoami`, create, documents, status, audit, and `collect`'s audit and access-URL reads — passes `partnerKeyFor(lenderId)` and stops when it is `null`, never `undefined`. A new partner call on a tester path that forgets the key silently talks as another lender. Enforced by: `decide-preflight.test.ts` O1-TWO-LENDERS, `collect.test.ts` COL-LENDER-KEY, `runner.test.ts` RUN-UNSUPPORTED and TR-PARTNER-KEY, `collector-io-guard.test.ts` IO-ENV-KEYS.
- **The tester preflight decides on the lender's own key, not a name.** The observation records `expectedLenderName` and the name the key answers with, but `decidePreflight` refuses only when the run's key does not resolve to the run's lender. Each configured test lender has its own name, so the name-based isolation in [Isolation model](#isolation-model) covers runs on the legacy key only: synthetic loans for a second tester lender are told apart by `LOANLIGHT_PARTNER_API_KEYS`, not by `OCTY_TEST_LENDER_NAME`.
- **A lender-tagged spec without a cell** (`tester: { lenderId }` only) takes the plain partner path and sends that lender's key; it is never created on the legacy key after a preflight that checked another.
