The Bug Reports console at `/bug-reports` is the operator surface where engineers triage reported audit issues and delegate them to Oz, the autonomous coding agent. It is the human side of the [Oz run lifecycle](/octy/oz-run-lifecycle): you pick a skill, attach context, launch a run, then come back to read the agent's summary and any PRs it opened.

The page lives in `src/app/(app)/bug-reports/page.tsx` plus its panel components (`LinearTicketPanel.tsx`, `RunDetailPanel.tsx`, `RunTimeline.tsx`, `ContextRunSelector.tsx`, `ModelPicker.tsx`, `IssueComments.tsx`).

## The issue list

The left side is a single, unified paginated table of `octy_issues` rows backed by `GET /api/bug-reports`. All reports — whether filed manually by engineers or filed autonomously by Oz/Octy runs — appear in the same list. Oz-filed rows are distinguished by a **tentacle indicator** in the first cell that sways on hover (`OctyIcons.tsx`, `BugReportPanelBody.tsx`). The earlier separate "Bug reports" / "Octy reports" tab split was removed in favor of this unified view.

Each issue carries aggregate counts (run count, latest run status, PR count, comment count). The anchor model is a three-tier ladder:

| Tier | `audit_run_id` | `loan_id` | Example |
|---|---|---|---|
| Loan-bound | present | present | Standard EPC audit |
| Loanless | present | null | Standalone portal appraisal (migration 0197) |
| Ad-hoc | null | null | Free-text report filed from **New Report** (migration 0311) |

Ad-hoc rows render an `AdHocReportCell` badge instead of the lender-implying `LoanlessLenderCell`. Their audit run column in the table displays a dash.

Filters are URL-driven, so a filtered view is shareable:

| Filter | Query param | Notes |
|---|---|---|
| Status | `status` / `intake_status` | Comma list. Default shows `new,acknowledged,delegated,ai_complete,in_review` (hides `closed`/`cancelled`). |
| Agent | `agents` | Comma list of agent types, each normalized to its canonical `agent_type` + LangSmith aliases (catalog-tolerant), matched against `related_traces[].agent_type`. |
| Lender | `lenders` | Comma list of lender UUIDs (resolved against `audit_runs.lender_id`). |
| Search | `q` | ILIKE over loan number or `audit_run_id`. |
| Sort | `sort` | `date_asc` or `date_desc`. |

The default page size is 20 (options 10/20/50/100). The `StatusChangerBadge` lets you change an issue's `intake_status` inline; it PATCHes `/api/octy-issues/[id]`.

<Info>
Issues are created from four surfaces: the loanlight-api portal, Octy's own Lookup BugReportPanel (both supply an `audit_run_id`), the **New Report** button on the Bug Reports page itself (ad-hoc, no `audit_run_id`), and **spot-check annotations** directly from the audit-run modal or IRIS analysis panel (see below). See [Issues, runs, labels API](/octy/issues-runs-labels-api) for the intake contract.
</Info>

## Spot-check annotations

Reviewers can annotate findings directly inside the audit-run modal or IRIS analysis panel and file them as bug reports in bulk without leaving the page.

**How it works:** turn on **Annotate** mode via the toolbar that appears in annotatable sections. Click any finding, field, or photo detail to attach a text note. When your notes are ready, **Create N bug reports** groups them by audit + agent context and submits them in one request. Normal page interactions (navigating sections, opening photos) keep working while notes are being added.

**Filing rule:** one report is created per unique combination of audit run, loan, lender, appraisal revision, and affected agent set. All notes in that group become numbered observations, preserving the reviewer’s exact text, captured field values, finding/field IDs, timestamps, and visible excerpt. Notes that span a shared section across multiple agents stay in one named group so none are duplicated. Separate audit runs and appraisal revisions stay separate even for the same agent.

IRIS photo annotations identify the agent as **IRIS photo analysis** and capture the actual appraisal revision and photo IDs — not the generic `appraisalEvaluation` agent type.

**IRIS as a first-class bug-report agent (b301167).** IRIS (`appraisalIris`) is now a fully supported affected-area option in bug reports, alongside the other agent types. When an audit run has an associated appraisal run, IRIS traces appear in the issue detail panel alongside audit-run traces. IRIS traces carry an `appraisalRunId` field (in addition to `auditRunId`) that identifies which appraisal revision the trace belongs to. The `traceMetadata` forwarded to the Oz prompt includes this `appraisalRunId` so the agent can look up IRIS-specific data tools scoped to the correct revision.

**Components:** `SpotCheckProvider` (app boundary, independent of `OctyAgentProvider`), `SpotCheckSurface` (record identity), `SpotCheckScope` (curated context per agent area), `SpotCheckRegion` (navigation ancestry for count badges), `SpotCheckTarget` (captures one meaningful detail). All components live in `src/components/common/spot-check/`.

**Draft lifecycle:** notes are saved in `sessionStorage` scoped to the account/origin/tab and survive navigation and reload. Text autosaves while typing. An unfiled-note badge appears globally. Closing an audit or changing the expanded appraisal row prompts to review or keep the draft. Browser exit warns while notes remain unfiled. Storage failures retain in-memory notes and offer JSON export.

**Submission:** `POST /api/bug-reports` accepts an optional `spot_check: SpotCheckPackage` payload alongside the existing manual-report contract. The server derives groups, validates package bounds and non-blank notes, checks audit/loan/lender associations, and inserts all reports in one Postgres transaction with a deterministic advisory lock to protect against duplicate submits after a lost response. Successful receipts replace the unfiled state with report links.

<Note>
No LoanLight API endpoint, migration, schema column, or permission is added by this feature. Persistence uses the existing `octy_issues` columns. If the connected API does not expose the appraisal revision table/column, only that filing operation returns `503` and retains the notes; other pages and non-appraisal reports remain usable.
</Note>

## Creating an ad-hoc report

The **New Report** button (top-right of the issue list toolbar) opens a `NewReportPanel` slide-out. You supply a description in plain text or markdown — there is no loan, no audit run, and no LangSmith trace to attach at creation time.

Once created, the report appears in the issue list and opens automatically. From the detail panel you can launch Octy against it exactly as you would any other report. The description becomes the primary issue context the agent starts from, so include everything it needs: links, IDs, expected vs. actual behaviour.

Loan- or run-anchored reports keep their richer entry point on the loan lookup page (`BugReportPanel`), where traces can be attached at creation time.

## The issue detail panel

Selecting an issue opens a right-hand drawer (`PanelShell`) with the issue meta (loan, audit run, dates, status, labels), the description, related agent runs as LangSmith trace chips, the comment thread, and the Trigger Octy form.

For ad-hoc issues (no `audit_run_id`), the panel skips the audit-run metadata fetch, shows "None — ad-hoc report" in the Audit Run field, and does not display an untraced-agents reconciliation (there are no `agent_runs` rows to reconcile against).

### Trigger Octy

<Steps>
<Step title="Name the run (optional)">
A free-text run name, max 80 characters. If you set it, the agent cannot overwrite it on completion — your label wins.
</Step>
<Step title="Attach previous run context (optional)">
`ContextRunSelector` lists prior runs on this issue that succeeded and have a non-null `summary`. Selected runs are loaded into a "Previous Run Context" section of the prompt, so a fix-and-PR run can build on an earlier root-cause run.
</Step>
<Step title="Review MCP servers">
LangSmith CLI access and the LangChain Docs MCP are shown as read-only checked. The Datadog MCP attaches automatically when the Datadog keys are configured (see [Environment variables](/octy/environment-variables)).
</Step>
<Step title="Pick a model">
`ModelPicker` is a cascading provider menu. The default is **`gemini-3.8-flash`** (Gemini 3.8 Flash). The chosen `modelId` is passed straight through to Warp's `config.model_id`. The Gemini group includes 3.8 Flash, 3.7 Flash, 3.6 Flash, 3.5 Flash, and 3.1 Pro. The GLM group includes GLM 5.3 Flash (Fireworks) and GLM 5.2 (Fireworks); GLM 5.1 was removed when Warp dropped it from its model catalog. Claude, OpenAI, Grok, and other groups remain available. All IDs are Oz slugs verified against `oz model list` and Warp's "Agent model choice" docs (2026-09-09).
</Step>
<Step title="Pick an affected area">
The **Affected Area** dropdown is populated by `GET /api/v1/audit_runs/:id/bug-reports/agent-options` (LOA-1669). Options are derived per audit run as the union of the run's expected plan (`audit_runs.agent_config`) and the observed `agent_runs` for that audit. Adding a new area is a backend change; the area must be present in `BUG_REPORT_AGENT_TYPES` in `shared-types`.

`income-analysis` was added to the `BUG_REPORT_AGENT_TYPES` closed union in `shared-types@1.22.0` (LOA-2316), making income traces valid in LangSmith for bug reports. The UI mapping (surfacing it as a selectable option in the dropdown) is a follow-on step.

`appraisalIris` is available as an affected area for any audit run that has an associated appraisal run with IRIS enabled. Oz investigations on IRIS issues have access to dedicated [IRIS data tools](/octy/oz-tool-api) that read both stored observations and the live read-time view from loanlight-api.
</Step>
<Step title="Pick a tentacle (skill)">
A radio over `OZ_SKILLS`: Root Cause Analysis, RCA Fix & PR, or Ad Hoc. See [Oz skills](/octy/oz-skills) for what each does.
</Step>
<Step title="Add custom instructions / attach comments">
Custom instructions apply to the fixed tentacles (RCA and fix-and-PR) as an "Additional User Instructions" section. The Attach comments checkbox folds the issue's comments into the prompt.
</Step>
<Step title="Launch">
`handleLaunchOcty` POSTs to `/api/octy-issues/[id]/oz-run`, which builds the prompt, launches the Warp run, writes an `octy_runs` row, and moves the issue to `delegated`.
</Step>
</Steps>

### Untraced agent runs (LOA-1910)

The `BugReportPanelBody` reconciles the audit's `agent_runs` ledger against the LangSmith traces attached to the issue. For every agent that has a ledger row but **no** LangSmith trace (excluding intentional `skipped` rows), the panel shows a **"No run recorded"** indicator next to the agent name. This highlights agents that started and failed before LangSmith could capture them, or were never instrumented — conditions where the trace chip alone would give a false all-clear.

The reconciliation is done by `untracedLedgerAgents()` (`src/lib/agent-types.ts`): it takes the set of traced agent types (from trace chip presence, not status) and the complete ledger, and returns the agents in the ledger that have no corresponding trace. Skipped rows are excluded because a `skipped` agent legitimately produces no trace.

### Live prompt preview

The panel assembles a live preview of the exact prompt the server will build. It calls `buildBasePrompt` client-side with placeholder tokens (and `datadogAvailable: true`) and appends the context, comments, and skill sections, mirroring the server. For the Ad Hoc tentacle the preview is an editable textarea seeded with the skill's pre-fill, which becomes the `customPrompt`.

<Tip>
The preview is the same code path the server runs, so what you see is what the agent receives (minus the real bearer token, which is injected server-side).
</Tip>

## Reviewing run history

The detail panel also surfaces the issue's runs (from `GET /api/octy-issues/[id]/runs`, newest first). `RunDetailPanel` and `RunTimeline` render each run's status, model, skill, and timeline. While a run is active, the UI polls `GET /api/octy-runs/[runId]/status`, which retrieves the live Warp state and persists changes (including the `oz_session_url` Warp session link).

`ACTIVE_OZ_STATUSES` is `queued`, `pending`, `claimed`, `in_progress`. When a run is active the panel warns that a run is in progress but still lets you launch another.

When a run finishes, the completion webhook stores its markdown `summary` and `pr_urls`, and advances the issue to `ai_complete` (only if it was still `delegated`). The summary renders as markdown in the run detail; PR links open against loanlight-api. From there engineers move the issue to `in_review`, `closed`, or `cancelled`.

<Note>
Per-run completion never silently overwrites an engineer's manual status — the `delegated → ai_complete` transition only fires when the issue is still `delegated`. See [Completion webhook](/octy/completion-webhook).
</Note>

## Linear ticket integration

Every Octy bug report owns at most one Linear ticket, regardless of how many Oz runs it accumulates. The dedup unit is the bug report, not the run.

**How a ticket is created:** at the end of an Oz run the agent calls the `attach-linear-ticket` Oz tool. Octy writes the ticket anchor in a race-safe conditional update (`WHERE linear_ticket_identifier IS NULL`) so concurrent runs on the same bug report can never create duplicate tickets.

**Where ticket data lives:** five columns on `octy_issues` (migration `0255`):

| Column | Purpose |
|---|---|
| `linear_ticket_id` | Internal Linear UUID. |
| `linear_ticket_identifier` | Human-readable id (e.g. `LOA-1234`). |
| `linear_ticket_url` | Deep-link into Linear. |
| `linear_ticket_attached_at` | When the anchor was written. |
| `linear_ticket_attached_by_run_id` | The `octy_runs.id` of the Oz run that attached the ticket. FK ON DELETE SET NULL. |

`linear_snapshot` (jsonb) is a read-through display cache of the ticket (state, assignee, priority, cycle, labels) refreshed by Octy on each Linear fetch. Linear stays the source of truth; staleness is display-only.

**`LinearTicketPanel`:** the issue detail panel shows a Linear tab when a ticket is attached. It displays the live ticket state (via `GET /api/linear/meta` and `GET /api/linear/search`) and lets engineers navigate directly to Linear for label and assignee management.

**Retiring in-house labels:** migration `0256` dropped `octy_labels` and `octy_issue_labels`. Labels now live on the Linear ticket and are mirrored in `linear_snapshot`. The previous in-house label assignments were not migrated — Linear provides a fresh taxonomy.

## Ask Octy

The Bug Reports page also exposes **Ask Octy** — an in-app chat panel that lets you describe an issue in natural language and have the agent file reports, look up loans, and attach traces without going through the manual Trigger Octy flow. The panel is opened via the **Ask Octy** button in the top-right area of the Bug Reports page or via the Octy icon in the app navigation.

Ask Octy and the Bug Reports console are complementary: use the chat panel to discover and file, use the console to manage the resulting issue queue and launch deeper Oz investigations. See [Ask Octy](/octy/octy-chat) for the full reference.
