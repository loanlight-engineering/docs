The Octy MCP server gives a coding agent read access to the full LoanLight data set — loans, audit runs, agent findings, lenders, taxonomy, IRIS, consolidation, routing, LLM experiments, costs, and more — plus two write surfaces: **bug reports** (investigations, runs, comments, status) and **audit observations** (durable data-quality records recorded with engineer confirmation). Every tool runs through the same operations layer as the web app, so authorization, audit, and PII masking apply identically on both surfaces.

For investigation runs specifically, the server builds the same instructions an Oz cloud run receives and lets you work a report locally at your own pace.

<Note>
The MCP endpoint is not used by Octy's own cloud (Oz/Warp) runs — Oz uses a token-authenticated HTTP tool API instead. See [the Oz tool API](/octy/oz-tool-api).
</Note>

## Architecture: operations layer

Every capability in Octy is an **operation** (op) defined once in `src/lib/ops/domains/<domain>/`. An op declares its id, domain, summary, Zod input schema, scope, effect, PII paths, guides, and handler. Adapters turn it into a server action, route handler, or MCP tool:

```
web page ─► server action ─┬─► adapter ─► runOp(op, actor, input) ─► op.handler(ctx, input)
web page ─► route.ts ────┤           validate · authorize · confirm · mask PII
MCP ─────► /api/mcp ──┘
```

- **Web adapter** passes the op value through unchanged; web sessions hold every scope.
- **MCP adapter** applies `present()`: trims the result, adds deep links and guide pointers, and masks PII for keys without `pii:read`.
- **Handlers** receive `ctx.actor` and the input. They never touch the HTTP request. `OpError(code, message)` is the only error surface.

Toolsets group related tools and are filterable via `?toolsets=<id>,...` on the `/api/mcp` endpoint. The **Who am I** page at `/whoami` is a visual reference for all tools, resources, guides, scopes, and errors, viewable as any API key or preset.

## How investigation runs work

```
teammate files a bug report —► Octy /bug-reports —► copy Report ID
                                                          │
engineer: /ll:octy-rca <id>  (Claude Code)                ▼
          $octy-rca <id>     (Codex)    POST /api/mcp  (Bearer octy_… — your own API key)
                                                          │
   octy_get_issue ─► octy_start_run ─► octy_query_dataset… ─► (operator decides) ─► octy_complete_run
     (+ playbook)         │                    │                                          │
          instructions + run tokens     run token on every call              summary + PRs on the report,
          (same code path as Oz)        scoped to this report                run closed, tokens dead
                                                                                          │
                                       a PR opened later ─► octy_record_run ─► follow-up record on the report
```

`octy_start_run` builds the investigation instructions server-side from the same sections an Oz run receives. An edit to the RCA prompt therefore reaches every local agent on its next run, with no skill update required. Only the tool mechanics differ: MCP tools instead of HTTP endpoints, the run token as a tool argument instead of a header, and completion split out as the operator's own step.

## Authentication and authorization

Every tool call passes up to three checks, in order:

1. **The API key** (`src/lib/mcp/auth.ts`). `Authorization: Bearer octy_…`, a key created on Octy's **API Keys** page. The key is the identity: its row in `octy_api_keys` names the key, its kind, its optional owner (name, email), and its scopes. No header names the caller.
2. **The key's scopes** (`src/lib/ops/scopes.ts`). The adapter derives each tool's required scope from the op; `tools/list` advertises only the tools the key may call. Calling another returns `SCOPE_DENIED`.
3. **The run token** (`src/lib/oz-token.ts`), for investigation tools that act for a specific run.

### Scopes

Scopes are grouped by domain. Every scope comes with a label and preset membership (`API_KEY_KINDS`).

**Investigation and run lifecycle**

| Scope | What it unlocks |
|---|---|
| `reports:read` | Read issues, runs, and dataset registry |
| `runs:start` | Start an investigation run |
| `runs:work` | Dataset queries, instructions, token refresh, Linear ticket (run token required) |
| `runs:complete` | Complete a run |
| `runs:renew` | Renew a lapsed run's token pair |
| `runs:record` | Record a follow-up on a closed run |

**Data reads (toolsets)**

| Scope | What it unlocks |
|---|---|
| `loans:read` | Loan lookup and per-loan audit history |
| `audits:read` | Audit run detail, agent status, timeline |
| `findings:read` | Agent finding detail across runs |
| `lenders:read` | Lender config, YAML, flags, entitlements |
| `pii:read` | Unmask PII fields (borrower names, SSN fragments, addresses). Without it, those fields are replaced with `[redacted]` and listed under `redacted`. |
| `taxonomy:read` | Classify-split taxonomy (categories, rules) |
| `consolidation:read` | Consolidation versions and drafts |
| `routing:read` | Routing config versions |
| `iris:read` | IRIS taxonomy, rules, concepts, and appraisal run data |
| `llm:read` | LLM experiments |
| `costs:read` | Token and billing cost data |
| `ops:read` | Ops layer registry (tool and guide catalog introspection) |
| `knowledge:read` | Explainers, glossary, and the developer guide |
| `observations:read` | Read audit observations for a loan/run/agent |

**Write surfaces (confirmation required)**

| Scope | What it unlocks |
|---|---|
| `observations:write` | Record and update audit observations (confirmation round-trip required) |

**Key kinds and presets**

A key's **kind** is a label plus a scope preset, editable afterwards:

| Kind | Default scopes |
|---|---|
| Local engineer | All scopes |
| Warp / cloud runner | `reports:read`, `runs:work`, `runs:complete` |
| Other | `reports:read`, `runs:record` |

## Confirmation round-trip

Ops that spend or cannot be undone (currently `observations:write`) require a confirmation from the engineer. The first call returns a `status: "confirmation_required"` result with a `preview` (summary + details) and a `confirm_token`; the agent shows the preview, waits for the engineer's yes, then calls again with the same arguments plus the token.

- The token (`oc1.<payload>.<mac>`) is HMAC-bound to the key, the op, the normalized arguments, and the target's version stamp. It expires after 10 minutes and is single-use.
- Web sessions skip the round-trip: the button click is the confirmation.
- Both calls are audited: the preview as `confirmation_required`, the action with `confirmed: true`.

## Guides: change guides for web writes

Every web write in each domain has a **change guide** — a machine-readable description of where to go in Octy, what to click, and what to enter. When a key lacks a write scope, the MCP server returns a `change` guide pointer instead of executing the action. Guides are also attached to read results as `guides` pointers so an agent always knows the next human-actionable step. The `/whoami` page renders every guide for reference.

## API keys — the /api-keys page

Everyone signed into Octy sees and manages every key: they are team infrastructure, not personal settings.

- **New key**: name (required), kind, owner name and email (optional), scopes, and **Verify PRs on GitHub** (on by default). The key is shown **once** — masked, with a show toggle and a copy button. Only its SHA-256 is stored.
- **Edit** an active key's name, kind, owner, scopes, or PR verification. Takes effect on its next call.
- **Revoke**: the key stops working on its next call. Keys are revoked, never deleted, so the activity trail keeps naming who did what.
- The list shows each key's prefix (`octy_XXXXXXX`), owner, scopes, who created it, and when it was last used (stamped at most once a minute).

The owner email matters: it is the operator recorded on runs and events, and — when it is on the team roster (`src/lib/github/team.ts`) — the `x-acting-user` sent to loanlight-api for the IRIS datasets. A key without a rostered owner acts as `system`.

## Tools and toolsets

Tools are organized into toolsets. `tools/list` returns only the tools your key's scopes cover. You can narrow further with `?toolsets=<id>,...`.

**Investigation and run lifecycle (no toolset filter required)**

| Tool | Scope | What it does |
|---|---|---|
| `octy_get_issue` | `reports:read` | Load one report: anchor, traces, Linear ticket, comments, every run (with token expiries for open local runs), and the playbook |
| `octy_get_run` | `reports:read` | A run's status, runner, summary, and optionally a local run's instructions again |
| `octy_start_run` | `runs:start` | Start a run (`root-cause-analysis`, `rca-fix-and-pr`, `ad-hoc`) → full instructions + `access_token` + `refresh_token` |
| `octy_list_datasets` | `reports:read` | The datasets `octy_query_dataset` can read (static registry metadata) |
| `octy_query_dataset` | `runs:work` + run token | Oz data tools, scoped to the run's bug report |
| `octy_fetch_instructions` | `runs:work` + run token | On-demand methodology instructions and the run's `completion` instructions |
| `octy_attach_linear_ticket` | `runs:work` + run token | Record the report's one Linear ticket |
| `octy_refresh_token` | `runs:work` + refresh token | New access token (60 min) while the 4 h refresh window is open |
| `octy_renew_run` | `runs:renew` | New token pair for an open run whose window lapsed, or from a new session |
| `octy_complete_run` | `runs:complete` + run token | Post the summary + PR links and close the run for good |
| `octy_record_run` | `runs:record` | Add a follow-up record (summary + PRs) to a report after its run closed |

**Data toolsets**

Each toolset corresponds to a domain in `src/lib/mcp/toolsets/`. The toolset's `description` and `flows` on `/whoami` (Tools tab) give the agent a one-paragraph orientation and typical call sequences.

| Toolset id | Scope | What it covers |
|---|---|---|
| `loans` | `loans:read` | Loan lookup, per-loan audit list |
| `audits` | `audits:read` | Audit run detail, agent status, issue timeline, evidence gate status |
| `findings` | `findings:read` | Finding detail for loans, audit runs, and agents |
| `lenders` | `lenders:read` | Lender config, YAML sections, feature flags, agent entitlements |
| `taxonomy` | `taxonomy:read` | Classify-split category tree, PII doc-type rules |
| `consolidation` | `consolidation:read` | Consolidation version list and active version |
| `routing` | `routing:read` | Integrations routing config versions |
| `iris` | `iris:read` | IRIS taxonomy, relevance rules, concepts, and appraisal run data |
| `llm` | `llm:read` | LLM model experiments |
| `costs` | `costs:read` | Token and billing costs by run and lender |
| `ops` | `ops:read` | Ops registry — tool catalog, guide catalog, scope list |
| `knowledge` | `knowledge:read` | Explainers, glossary, and developer guide |
| `observations` | `observations:read` / `observations:write` | Read and record audit observations |

IDs can be bare UUIDs or pasted Octy links (`/bug-reports?issue=<id>`). Investigation tools (**no browsing**): you need the report's ID; data needs a run token.

## The run token — same mechanism as Oz

A local run is an ordinary `octy_runs` row with `oz_run_id = "mcp:<operator>"` (`src/lib/mcp/run-source.ts`). It carries the same token columns an Oz run does. `octy_start_run` mints both tokens exactly like the cloud `oz-run` route and stores only their SHA-256 hashes. `validateOzToken` validates them on every tool call.

That gives a local run the same properties Oz runs have:

- **Scope** — data tools resolve the audit run from the run's bug report server-side. Unlike an Oz run on an unanchored report, a local run cannot name another audit run to read.
- **Ownership** — only the operator who started the run can act for it.
- **Time bound** — access token 60 min, refresh token 4 h. The agent refreshes on its own with `octy_refresh_token`; once the refresh window lapses, only the operator can renew the run.
- **Closure** — completion consumes the token. Nothing can be read or changed afterwards, and a closed run cannot be reopened. A later PR is a follow-up record; further work is a new run.

Tokens are surface-bound: the Oz HTTP routes reject a local run's token and the MCP server rejects an Oz run's (`RunSurface` in `src/lib/oz-token.ts`). Tokens are returned as fields of `octy_start_run`, never embedded in the stored instructions, so the prompt stored on the run holds no secret.

| | Cloud (Oz) run | Local (MCP) run | Follow-up record |
|---|---|---|---|
| `oz_run_id` | Warp's run id | `mcp:<operator>` | `followup:<operator>` |
| Auth | Per-run token, 60 min, 4 h refresh | Your API key + the same token | Your API key (`runs:record`) |
| Data scope | The report's audit run; unanchored runs may pass `audit_run_id` | The report's audit run only | None — write-only |
| Completion | The agent, at the end of its task | The operator, with `/ll:octy-complete` | Created closed |
| After 4 h | Run cannot be extended | `/ll:octy-renew` issues a fresh pair | — |
| Kill switch | — | **End run** in the run details (any signed-in user) | — |
| UI | Warp session link, who launched it | **Local · \<operator\>**, elapsed time, token state | **Follow-up · \<operator\>**, linked to the run it follows |

The MCP tools refuse to complete or renew a cloud run because Warp owns that lifecycle. To build on an earlier run, start a new one with it in `context_run_ids` (every earlier summarized run is included by default).

## Follow-up records — `octy_record_run`

A closed run is locked: nothing reopens it. Work that happens afterwards — usually the PR for a fix made later, outside a run — goes on the report as a **follow-up record**:

```
octy_record_run({ issue_id, summary, pr_urls?, parent_run_id?, run_name? })
```

- It creates an `octy_runs` row with `oz_run_id = "followup:<operator>"`, status `succeeded`, its token consumed at creation, and `context_run_ids = [parent_run_id]`. No instructions, no prompt, and no token is ever returned, so it opens no data.
- `parent_run_id` must be a run of the same report.
- **PR checks.** Every URL must be `https://github.com/<GITHUB_ORG>/<repo>/pull/<n>`. When the key has **Verify PRs on GitHub** on, each PR is looked up with the GitHub App first; a miss fails the call with `PR_NOT_FOUND` and nothing is written.
- **One record per PR.** If the report already has a follow-up carrying any of these PRs, the call returns that record (`already_recorded: true`) instead of writing a second one.
- The server instructs agents to use it: the `playbook`, the run instructions' closing section, and the completion instructions all direct agents to record later PRs with `octy_record_run`, never by starting a new run just to carry it.

## Writes: bug reports and audit observations

Over MCP, writes are allowed in two domains only:

1. **Bug reports** (`reports` + `runs` domains) — create, comment, status, anchor, Linear edits, dispatching and controlling investigation arms. This is the investigation-run surface documented above.
2. **Audit observations** (`observations` domain) — record a durable note about production loan, audit-run, or agent data that Octy noticed. Every observation write requires the confirmation round-trip (the engineer sees a preview and confirms before anything is written). Observations degrade gracefully: if `octy_audit_observations` does not yet exist in the database, the tool answers `FEATURE_UNAVAILABLE` and investigation continues unaffected.

Every other change — lender flags, YAML, entitlements, routing config, IRIS taxonomy, and so on — is answered with a **change guide**: the Octy link, the steps in the UI's own words, and what to verify afterwards.

## The activity trail — `octy_run_events`

Every operation on a report or run lands in `octy_run_events` (`src/lib/run-events/record.ts`): every MCP tool call (success, tool error, or `SCOPE_DENIED`), every `/api/oz/tools/*` call, every dispatch from the web app, and every **End run**. Each event records the run, the report, the API key, the actor (owner email or key name; the web user; `Warp agent`), the surface (`mcp`, `http`, `web`), the tool, its operation (`read`, `write`, `lifecycle`), its outcome, a target (dataset, ticket, PR), allowlisted arguments, a row count, and the duration. Never a token, never row data.

Recording never fails the call it records: if the insert fails, the whole event goes out as one `[run-event]` log line, so Datadog holds the trail until the table does.

The run details panel shows the trail as the run's **Activity** timeline (`GET /api/octy-runs/[runId]/events`). The report's run list shows who started each run from its launch event.

The schema for both tables is documented in [agent platform schema](/data-model/agent-platform-schema).

## Working a report locally

1. `/ll:octy-load <id>` — look at a report, its runs and their summaries, and the playbook. Starts nothing.
2. `/ll:octy-rca <id>`, `/ll:octy-fix <id>`, or `/ll:octy-adhoc <id> [task]` — start a run. The agent follows the server's instructions and does **not** close the run when it finishes; it presents its findings and stops.
3. Take as long as you like. The agent refreshes its own access token for 4 h; after that its next Octy call fails with `REFRESH_EXPIRED` and it asks whether to renew. Say yes and it renews; say no and the run waits for `/ll:octy-renew <run-id>`. Nothing else changes while you are away.
4. `/ll:octy-complete <run-id>` — when **you** decide the run is done (or should stop). The agent fetches the completion instructions, writes the summary, does the deferred Linear step, shows you the summary, and posts it. The run is closed for good.
5. `/ll:octy-record <id> [pr-url…]` — a PR opened after the run closed. The agent writes a short summary of what the PR changes, shows it, and records it on the report as a follow-up.

A run someone walked away from shows in the bug report as **tokens lapsed** once its refresh window passed, with how long it has been open and when Octy last heard from it. **End run** closes it: the agent loses access on its next call and the run cannot be renewed. It reads as `failed` with a note saying who ended it.

## Security posture

- **Your API key is your identity.** One key per person (or per runner), each with its own scopes, revocable on its own from the **API Keys** page. Only its SHA-256 is stored, and it is shown once. A revoked key fails on its next call.
- **Every dependency failure denies.** A key lookup that fails for any reason other than a missing table is a 503; a missing key, a wrong key, and a revoked key all return 401.
- **Everything is on the trail** — who (which key), what, on which report and run, when, and how it went.
- **Rate limits** (`src/lib/mcp/rate-limit.ts`): 10 failed keys per client address per 5 min, 240 messages per key per minute, 20 messages per batch. In-process, so the effective ceiling scales with the number of ECS tasks (typically 2–4).
- `/api/mcp` is exempt from the AuthKit middleware (`src/middleware.ts`) because the bearer key authenticates it.

### The legacy shared key (transition)

The shared `OCTY_MCP_API_KEY`, sent with an `X-Octy-Operator` email on the team roster, still works so nobody is cut off mid-run. It has every scope, and its calls are recorded with actor kind `legacy`. The header is a claim, not an identity — anyone holding the shared key can name any rostered email. Move to your own key; once everyone has, the legacy path and the `Octy/McpApiKey` secret go away.

## Setup (each engineer)

**First, your key.** Open Octy's **API Keys** page ([prod](https://octy.loanlight.com/api-keys)) and create a key: kind **Local engineer**, your name and LoanLight email. Copy it; it is shown only once.

**Claude Code, scripted (macOS).** From the `octy` repo:

```bash
pnpm mcp:setup        # or: bash scripts/setup-octy-mcp.sh
```

The script asks for the environment (prod or local) and your key. It then saves the key to the macOS Keychain, writes a `headersHelper` file that reads the key per connection, and registers the server with `claude mcp add-json --scope user`. It verifies the key is accepted before finishing. It is safe to re-run.

The menu also offers: **Switch environment** (prod ↔ local), **Change an API key**, **Show current setup**, and **Remove everything** (server, Keychain keys, header files). Each environment (`prod`, `local`) keeps its own Keychain key (`octy-mcp` / `octy-mcp-local`), so switching does not re-prompt for a key you already gave.

**LangSmith CLI.** The RCA instructions read traces with the `langsmith` CLI, so **Set up everything** also configures it. It installs the CLI if missing, asks for your LangSmith API key, and writes a `# >>> octy langsmith >>>` block to `~/.zshenv` (non-interactive shells, which agents use, never read `~/.zshrc`). Re-running replaces the block rather than adding another.

**Manual steps (Claude Code):**

Keep the key out of your shell profile and out of `~/.claude.json`: put it in the macOS Keychain.

```bash
security add-generic-password -a "$USER" -s octy-mcp -w   # prompts for the key
```

A `headersHelper` script runs on every connection:

```sh
#!/bin/sh
# ~/.claude/octy-mcp-headers.sh  (chmod +x)
printf '{"Authorization":"Bearer %s"}' "$(security find-generic-password -s octy-mcp -w)"
```

```bash
claude mcp add-json --scope user octy '{
  "type": "http",
  "url": "https://octy.loanlight.com/api/mcp",
  "headersHelper": "~/.claude/octy-mcp-headers.sh"
}'
```

Install the skills with `/plugin install ll@loanlight`: `/ll:octy-load`, `/ll:octy-rca`, `/ll:octy-fix`, `/ll:octy-adhoc`, `/ll:octy-renew`, `/ll:octy-complete`, `/ll:octy-record`.

**Codex** (`~/.codex/config.toml`) reads the key from an environment variable; export it from the Keychain in your shell profile:

```bash
export OCTY_MCP_API_KEY="$(security find-generic-password -s octy-mcp -w)"
```

```toml
[mcp_servers.octy]
url = "https://octy.loanlight.com/api/mcp"
bearer_token_env_var = "OCTY_MCP_API_KEY"
```

Install the skills with `bash install.sh` in `loanlight-codex-skills`: `$octy-load`, `$octy-rca`, `$octy-fix`, `$octy-adhoc`, `$octy-renew`, `$octy-complete`, `$octy-record`.

**Local Octy.** Apply loanlight-api's migrations to your dev database, create a key on `http://localhost:7873/api-keys`, and point the URL at `http://localhost:7873/api/mcp`. To smoke-test:

```bash
npx @modelcontextprotocol/inspector --cli http://localhost:7873/api/mcp \
  --transport http --header "Authorization: Bearer $OCTY_MCP_KEY" \
  --method tools/list
```

## Deploying

`octy_api_keys` and `octy_run_events` arrive by a loanlight-api migration (0142):

- Without `octy_api_keys`, only the legacy shared key works, and the **API Keys** page shows a feature-unavailable notice.
- Without `octy_run_events`, events go to the `[run-event]` log line only, and the Activity timeline says the log is not available here (not "no activity").

Migration `0164` adds `octy_audit_observations` and `octy_issues.report_kind`; migration `0165` adds `octy_runs.runner_*` and `octylink_actions`. Each degrades gracefully on an older database — see [agent platform schema](/data-model/agent-platform-schema) for per-table details.

Two secrets are opt-in through CDK context:

- `OCTY_MCP_CONFIRM_SECRET` — required for the confirmation round-trip on `observations:write`. Set `octyMcpConfirmSecretName` in CDK context. Without it, confirmable actions are refused.
- `GITHUB_WEBHOOK_SECRET` — required for the automated code-review webhook. Set `githubWebhookSecretName`. Without it, the webhook answers 503.

The ECS task still reads the legacy `Octy/McpApiKey` secret. It must exist in each account or the task will not start:

```bash
aws secretsmanager create-secret --name Octy/McpApiKey --secret-string "$(openssl rand -hex 32)"
```

## Transport

Streamable HTTP, stateless, JSON responses only (`src/lib/mcp/protocol.ts`, `src/app/api/mcp/route.ts`):

- `POST /api/mcp` accepts one JSON-RPC message or a batch.
- Notifications get `202`.
- `GET` and `DELETE` get `405`: there is no server-initiated stream and no sessions.

Being stateless matters because Octy runs several ECS tasks behind one ALB; the run token lives in the database, so any task can validate it. Supported protocol versions: `2025-06-18`, `2025-03-26`, and `2024-11-05`.

## Octylink

Octylink hosts the Hermes runner agents that power Octy's non-Oz bug runners. The **Octylink** page (`/octylink`) manages agents, roles, run queues, providers, automations, and host setup. Key intersection with the MCP server: Octylink agent API keys are minted with the correct scopes through `/api/hermes/mcp-key`, revoked on agent deletion. All admin changes are recorded in `octylink_actions` — see [agent platform schema](/data-model/agent-platform-schema).

Octylink is not yet deployed to int or prod. Until it is and `octylinkUrl` / `octylinkPublicUrl` / `octylinkApiKeySecretName` are set in the CDK context, every `/api/hermes/*` call and the side panel return 503 `hermes_not_configured`.

<Note>
Octylink is an internal infrastructure name. Agent-facing text in tools, guides, errors, and the side panel says "Octy" — never "Hermes" or "Octylink". A test enforces this in the octy repo.
</Note>

For the full Octylink reference — architecture, roles, run queue, automations, providers, and host operations — see [Octylink](/octy/octylink).
