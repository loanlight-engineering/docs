The **Agent Coverage** page at `/agent-coverage` documents the Octy standard: seven rules that define whether Octy can reliably debug an agent, and the current coverage status of every audit-pipeline agent, standalone agent, and portal feature against those rules.

The page source lives in `src/app/(app)/agent-coverage/` (`AgentCoverage.tsx`, `content.ts`, `model.ts`). Labels, data-tool counts, and billing metadata are read live from `src/lib/agent-types.ts` and `src/lib/oz-tools-registry.ts`; the coverage matrix itself is declared in `content.ts` and tested by `content.test.ts`, which asserts that every tool ID in the matrix is registered and every catalogue agent has a row.

## The Octy standard (N1–N7)

Octy can debug an agent when it can anchor a report on a real audit run, find that run's trace, see the model calls inside it, and read the agent's results and the human corrections to them. The seven rules formalise those needs.

| Rule | Short name | Requires |
|---|---|---|
| **N1** | Container | Every execution has a real `audit_runs` container and exactly one `agent_runs` row with the honest `trigger_source` (`epc`, `partner`, or `portal`) and its `agent_config`. |
| **N2** | Run → container | The agent's own run row carries the container's id, set when the row is created, so failed and in-flight runs are linked too. |
| **N3** | Trace found | The LangSmith root trace carries `metadata.auditRunId` set to that container, plus `agentType`, `lenderId`, the run's own id, and `triggerSource`. |
| **N4** | LLM detail | Every model call is a child span of that root, through a wrapped client or a traceable span, and through the PII anonymizer. |
| **N5** | Ledger | The `agent_runs` row moves `pending → processing → complete | failed` with its errors, `llm_config` pinned, and cost in `agent_runs.cost`. |
| **N6** | Octy knows it | A catalogue entry in `src/lib/agent-types.ts`, a section in the base-prompt architecture text (`oz-skills/index.ts`), and data tools for its results and human corrections. |
| **N7** | Reportable | A bug can be filed from the portal page that showed the result, from the audit tab, and from Octy's lookup and audit modal, anchored on the audit run. |

## Coverage statuses

| Status | Meaning |
|---|---|
| Fully supported | The rule is met |
| Partly supported | The rule is partially met; the gap is noted in the cell |
| Not supported | The rule is not met |
| Not applicable | The rule does not apply (e.g. a deterministic engine has no model calls) |
