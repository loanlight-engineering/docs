The Classify & Split config tool at `/classify-split-config` lets engineers edit the document classification configuration that the Pre-Audit-Classification agent reads, and validate changes with a live dry-run against loanlight-api. The data it edits is the [classify-split data model](/subsystems/classify-split-data-model).

## Config editing

The page is tab-based (`src/app/(app)/classify-split-config/`):

- **Categories & Rules** — the split categories and classification rules.
- **Classifications** — the classification types. The tab opens in **Coverage view** by default — a treemap of all split categories sized by segment count, heat-mapped by unknown-subtype share (white at 0%, brand red at 100%). Clicking a category tile splits the view to show its subtypes. Clicking a subtype (or **View documents**) drills into the ordinary classification table filtered to that slice. A **Show routing** toggle fetches each visible segment's routed Final container from the integrations service and surfaces it as an inline chip; the fetch is keyed by audit-run correlation ID (fan-out capped server-side). A **prev/next** row navigation allows stepping through individual classification records in the detail panel without returning to the list.
- **Confusion Map / Matrix / Graph** — visualizations of misclassification.
- **PII Doc-Type Rules** — the `pii_field_doc_type_rules` that drive PII scoping.
- **Dry Run** — run the live validation described below.

Edits are applied through server actions in `actions/` (`classifications.ts`, `classify-rules.ts`, `split-categories.ts`, `pii-doc-type-rules.ts`, `confusion-edges.ts`, `bulk-config.ts`, `config-context.ts`, `pending-changes.ts`, `staged-targets.ts`), with Zod schemas in `src/lib/schemas/`.

## Taxonomy staging (LOA-2564)

Every edit now goes through a **staged draft** before it modifies the live taxonomy. The classify-split engine never reads the staging table; a staged change is invisible to classify runs until it is explicitly promoted.

### Scopes

A **scope switch** in the page header toggles between **Live** and **Staged** views (`TaxonomyScope.tsx`). In live scope the page looks and behaves exactly as before — it renders the live tables and each editor saves directly. In staged scope the page renders the draft's `candidate_config` instead of the live tables, and every save writes into the open draft rather than to the live tables.

A header badge indicates when an open draft exists. The switch itself is present only when a draft is open; otherwise the page is always in live scope.

### Draft lifecycle

At most one draft is open at any time, enforced by a partial unique index `uq_classify_split_pending_changes_one_open` on `classify_split_pending_changes` (migration `0333`).

When an edit is saved in staged scope it is projected onto the open draft's `candidate_config` rather than inserted as a second independent fork. This avoids the problem where staging two edits in sequence created two parallel forks of live — applying one made the other's baseline stale. The draft's `base_config` (the snapshot of live when the draft was created) never moves, so the stale-baseline guard on promote keeps working.

Draft lifecycle states (`classify_split_pending_changes.status`):

| Status | Meaning |
|---|---|
| `pending` | Open; checks have run but no eval yet, or the draft changed since the last eval. |
| `verifying` | An eval is running. |
| `verified` | An eval completed; the draft has not changed since. |
| `applied` | Promoted to live. Terminal. |
| `discarded` | Explicitly discarded. Terminal. |

### Static checks

Every save recomputes `runTaxonomyChecks` (`src/lib/classify-split/taxonomy-checks.ts`) against the base and candidate configs. Findings are `blocker` or `warning`. The **Promote to live** button is disabled while any blocker is unresolved. The apply action re-runs checks at promotion time against the current live taxonomy (not just the snapshot) so a blocker introduced by an intervening edit also blocks promotion.

### Check against documents (staged targets)

When `checks.lane !== "none"`, the staging bar shows a **Check documents** link. It navigates to the Dry Run tab with `?source=staged&taxonomy=staged`, preloading real production documents that the taxonomy change most affects.

The `getStagedTargets` server action (`actions/staged-targets.ts`) selects documents from `document_classifications` using a two-bucket strategy derived by `staged-targets.ts` (`focusOf`, `pickBoundaryFirst`, `pickSpread`):
- **Target** documents — those whose stored result is on a classification that the draft changes (a boundary). These are the documents most likely to classify differently under the candidate taxonomy.
- **Control** documents — documents from the same split type that the draft does not touch (spread). These are expected to be unchanged; if they change, the edit has wider blast radius than intended.

Each selected document carries its stored result as a `baseline` (the `before`). Running the Dry Run against it produces the live result. The `StagedCompare` component renders both side by side, colour-coded by outcome (`unchanged`, `changed`, `added`, `removed`). A **stale** chip on a row indicates the stored result predates the last taxonomy promotion, so the baseline was produced by an older live taxonomy than the draft's base.

Up to 30 target documents are shown, selected from a pool of 400 recent classified rows. Test-tenant rows are excluded from the pool in deployed environments.

Target and control documents are drawn in **random order** by default (Fisher–Yates shuffle with an
injectable random source for reproducibility), so consecutive Check-documents runs sample different
loans rather than always landing on the most recent ones. The picker exposes a **Latest / Random**
switch to revert to recency ordering when you need a deterministic baseline.

The pool is also **deduped**: rows sharing the same storage path, or the same loan + filename
combination, collapse to one entry so a re-synced document does not occupy multiple slots.

<Note>
The old sample-based eval path (`run-eval.ts` / `EvalReportPanel`) was removed. The staged-targets approach uses real stored results as the baseline rather than re-running the live taxonomy, which is faster and makes the comparison deterministic.
</Note>

### Promote and discard

**Promote to live** (`applyPendingChange`) computes a targeted diff (`planApply`) between `base_config`, the current live taxonomy, and `candidate_config`. If anything the change touches has moved since the draft was authored, promotion is refused and conflicts are listed — nothing is overwritten. A successful promote runs each op (`category.create | update | delete`, `rule.create | update | delete | reparent`, `edge.create | delete`) inside a single transaction and writes a `pending_change_applied` audit row to `classify_split_config_audit`.

**Discard** marks the draft `discarded` and writes a `pending_change_discarded` audit row that records the diff summary, blocker/warning counts, and the eval verdict if one was run. Discards are audited because a deliberately rejected taxonomy change is often the most informative decision in the config history.

## Live dry-run

The Dry Run tab exercises the real loanlight-api classify-split pipeline against an uploaded document or a JSON payload, without going through the full audit flow.

### Request path

The browser POSTs to `POST /api/classify-split-config/dry-run` (`src/app/api/classify-split-config/dry-run/route.ts`). That handler proxies to loanlight-api's `POST /internal/dry-run/classify-split` (JSON or multipart file upload) and streams the response back to the browser as Server-Sent Events (`text/event-stream`).

The proxy uses `src/lib/loanlight-api-client.ts`, which calls `${LOANLIGHT_API_URL}` with:

- `x-internal-api-key: OCTY_INTERNAL_API_KEY` — the shared secret that must match loanlight-api's `InternalApiKeyGuard`.
- `x-acting-user: <email>` — the WorkOS user running the dry-run.

The client uses a 120-second timeout and surfaces failures as `ApiClientError`.

<Warning>
The dry-run is gated by `OCTY_INTERNAL_API_KEY`. If the secret does not match loanlight-api's `InternalApiKeyGuard`, the proxied request is rejected. See [Environment variables](/octy/environment-variables).
</Warning>

### Source kinds

The **picker** selects which documents to run:

| Source kind | How documents are chosen |
|---|---|
| `loan` (default) | Search by loan number; documents from the selected loan's `document_classifications`. |
| `local` | Upload a local file directly from the browser. |
| `staged` | Documents pre-selected by `getStagedTargets` (set automatically from the **Check documents** staging bar link). Each document shows its stored result as the baseline comparison. |

### Run modes

- `mode`: `split` (Phase 1 splitting only) or `full` (split + classify).
- `classificationMode` (optional): `per_segment`, `majority_bucket`, or `two_pass`.
- `preAudit` (optional): run through the pre-audit wrapper.

### SSE events

The stream emits typed `DryRunEvent` records:

| Event | Meaning |
|---|---|
| `step` | A pipeline stage started/progressed. |
| `result` | A classification result for a segment. |
| `heartbeat` | Keep-alive while the backend works. |
| `trace` | A LangSmith trace pointer for the run. |
| `error` | A failure (`BACKPRESSURE_TIMEOUT` or `LLAMACLOUD_FAILURE`). |
| `done` | Terminal event; the stream then sends `data: [DONE]`. |

<Warning>
A dry-run is not free of side effects. It writes **real rows** into the classify-split tables with `is_dry_run = true`. Filter on that column when querying, and do not treat dry-run output as ephemeral.
</Warning>
