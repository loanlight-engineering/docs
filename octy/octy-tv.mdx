Octy TV (`/octy-tv`) is a library of narrated explainers — one overview of the full LoanLight system and one per agent. They are not pre-rendered videos. Each explainer is a story (JSON data) plus small narration clips; the player draws the picture live on a canvas at the current theme and plays audio in sync.

The library and player live in `src/components/explainers/`. Stories live in `explainers/stories/`. The built manifests and catalog are in `src/lib/explainers/generated/`.

## Explainer kinds

Every explainer has a `kind`:

| Kind | What it covers |
|---|---|
| `product` | The LoanLight system as a whole (`loanlight-overview`). Featured prominently in the library view. |
| `agent` | A single audit-pipeline agent. One per agent type; identified by `agentType`. |

The library renders the product explainer as a featured card, then the agent explainers in a responsive grid. You can filter by kind and search by title, tagline, agent type, or chapter name.

## How it works

A story is a sequence of named chapters, each containing narration **cues** and a **visual layout** (cards, flow, record, checks, etc.). The renderer (`src/lib/explainers/renderer.ts`) takes a compiled manifest, a timestamp, and the active Octy theme palette, and draws the correct frame. Switching Octy between themes repaints the explainer mid-playback.

Narration is synthesised with OpenAI TTS (`gpt-4o-mini-tts`) and stored as content-addressed 48 kbps AAC clips in `public/explainers/voice/<hash>.m4a`. A clip's file name is a hash of its text and every voice setting, so unchanged lines are never re-synthesised.

The explainer renderer is versioned. The portal's `@loanlight-engineering/explainer-renderer` package must be at or above the story's `schema_version` to play it. As of schema 3 (renderer 1.2.0), the Credit, Appraisal, and Properties Check training videos have been updated with refreshed content and voice clips, and the Business Verification training video (`business-verification-training`) is newly published (schema 3). Videos built for schema 3 are silently excluded on portals still running renderer 1.1.x or earlier.

The player (`ExplainerPlayer`) assembles the clip sequence from the manifest and schedules them against the canvas animation. It exposes:

- A **chapter scrubber** segmented by chapter, with jump-to-chapter buttons.
- A **clickable transcript** that seeks to any cue on click.
- **Captions** toggled with the `CC` button.
- **Speed control** (0.75×, 1×, 1.25×, 1.5×).
- **Fullscreen** and `?t=<seconds>`/ `?scene=<slug>` deep links.

## The catalog

`CATALOG` in `src/lib/explainers/generated/index.ts` is the built list of explainer entries. Each entry carries `slug`, `title`, `tagline`, `kind`, `audience`, `agentType?`, `chapters`, and `duration`. The `ExplainersLibrary` component reads it client-side; no API call is needed.

Each explainer carries an `audience` field:

| Audience | Meaning |
|---|---|
| `"team"` | Internal, for LoanLight engineers and Octy. Shown in the Octy TV library. |
| `"customer"` | For underwriters and lender users; can be published to the portal's Training page. |

Current catalog covers:
- **Team explainers:** `loanlight-overview`, `pre-audit-classification`, `document-health`, `pii-validation`, `urla-extraction`, `property-data`, `red-flags`, `credit-evaluation`, `appraisal-evaluation`, `bank-statement-income`, `iris`.
- **Customer training videos:** `urla-1003-check-training`, `data-consistency-training`, `document-health-training`, `properties-check-training`, `credit-training`, `appraisal-training`, `bank-statement-income-training`, `business-verification-training`.

## Publishing to the portal

Customer-audience explainers (`audience: "customer"`) reach the lender portal's **Training** page as the **`@loanlight-engineering/training-videos`** npm package. The portal lists this package as a dependency; a portal deploy ships the videos, and a portal rollback rolls them back. There is no manual publish step in Octy.

### The training-videos package

`packages/training-videos/` in the Octy repository is the distribution package. It is built by `pnpm explainers:training-videos` and published automatically by `.github/workflows/publish-training-videos.yml` whenever a push to Octy's `main` branch changes what the package holds. Nobody bumps the version manually; the version is `1.0.<git commit count on main>`, so the registry always reflects `main`'s commit order.

The package contains:

| Path | Contents |
|---|---|
| `catalog.json` | Every customer video: `slug`, `title`, `description`, `agentType`, `sortOrder`, `schemaVersion`, `contentHash`, `hidden`, and `manifest` path. Never show a video whose `hidden` is `true`. |
| `videos/<slug>.json` | The video's manifest, rendered by `@loanlight-engineering/explainer-renderer`. |
| `voice/<clip>.m4a` | Narration clips, named by content hash. |
| `pages/...` | PDF page images at the paths the manifests reference. |

Only voiced customer videos are included. Octy's CI fails a PR that would leave one unvoiced.

### How a video reaches the portal

1. An author pushes the updated story and built manifest to Octy `main`.
2. `publish-training-videos.yml` builds the package (`pnpm explainers:training-videos`) and publishes a new `1.0.x` version to the npm registry.
3. A bump PR in `loanlight-api` updates the portal's `packages/app/package.json` dependency on `@loanlight-engineering/training-videos` to the new version.
4. The bump PR's CI runs `training-videos-check` (the `bin/training-videos-check` command in the package) against every shown video to confirm its features are live in prod and the portal's renderer version can draw its schema.
5. The portal deploys with the new package; the **Training** page reads the catalog directly from the bundled package.

### Bump PR check

`training-videos-check --head "$GITHUB_SHA"` runs in `loanlight-api` CI for any PR that updates the training-videos package. It reads the package's `dist/catalog.json` and `dist/checks.json`, checks the portal's `packages/app/package.json` for the `@loanlight-engineering/explainer-renderer` range, and for each shown video:

- Verifies all story `sources[]` commits are present in prod for the deployed app that ships each source path (Portal, API, Encompass, or Web App).
- Verifies the portal's renderer schema supports the video's `schemaVersion`.

The check token needs read access to `loanlight-api`, `octy`, and `loanlight-integrations` (Contents + Actions). CI's default token only covers `loanlight-api`, so the workflow mints one with `actions/create-github-app-token`.

<Note>
A video whose `hidden` field is `true` is never shown to customers, so the check skips it. Hidden videos appear in the catalog only to let the portal suppress them cleanly; they do not gate the bump PR.
</Note>

## Authoring and refresh

Stories and narration clips are committed to the repo. Everyday commands from the repo root:

```bash
pnpm -s explainers:build                  # dry run: validate, show cost of missing clips
pnpm -s explainers:build <slug> --yes     # voice missing clips, write manifests + catalog
pnpm -s explainers:stale                  # list explainers whose source paths changed since authoring
pnpm exec vitest run src/lib/explainers   # validate stories, manifests, and clip presence
```

`explainers:stale` reads each story's `sources[]` list (repo, commit, paths) and runs `git diff` to find staleness. Only changed explainers need re-authoring. `--yes` refuses to synthesise more than `--budget` (default $2) of audio at once.

See `explainers/AUTHORING.md` for the shape of a story file and the layout vocabulary.
