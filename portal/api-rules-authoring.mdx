Three modules author the rules that the audit pipeline evaluates: `portal-appraisal-rules`, `portal-credit-rules`, and `portal-income-rules`. They share a template-adoption pattern: a lender adopts a rule set from cross-module templates, then adds, updates, or deletes individual rules within a set. All endpoints use [`PortalAuthGuard`](/portal/api-auth).

Custom rules span four concerns: authoring (these modules), override (`portal-lenders`), display (`portal-appraisal` / `portal-credit`), and evaluation (`lib/*-pipeline/rules`).

## Rule codes, templates, and operators

Rule code format: built-in rules use `[A-Z]{2,5}_\d{3}`; custom rules use `CUST_[A-F0-9]{8}`; credit also uses `CRED_*` template codes. Templates live in the cross-module table `appraisal_rule_templates`, filtered by `module` (`appraisal` or `credit`).

The appraisal custom-rule evaluator supports these operators: `equals`, `not_equals`, `contains`, `not_contains`, `greater_than`, `greater_than_or_equal`, `less_than`, `less_than_or_equal`, `abs_less_than`, `abs_less_than_or_equal`, `regex`, `in`, `not_in`, `date_within_days`.

<Info>
USPAP rules were removed from active rule sets (LOA-726). `getAgencyAvailability` no longer surfaces `uspap`; only `fannie_mae` and `freddie_mac` are adoptable agency sources, even though `'uspap'` is still permitted in the type/CHECK for rendering historical rows.
</Info>

## isCompoundRulesEnabled gate

Compound (multi-condition) custom appraisal rules are gated by `isCompoundRulesEnabled(lenderId)`, which is **opt-in**, not default-enabled. At head it resolves from the umbrella `appraisal` flag (`isAppraisalEnabled`), so an absent flag row resolves to disabled (LOA-994). The `POST .../rule-sets/:setId/rules` endpoints honor this gate when adding a compound rule.

Credit has its own independent compound gate, `isCreditCompoundEnabled` (`credit_compound`, also default-OFF). Both live in `lib/appraisal-pipeline/rules/feature-gates.ts`. See [authentication and authorization](/portal/api-auth) for the full gate list.

**Condition depth cap (LOA-2227, #3351):** `MAX_AUTHORED_DEPTH` in
`dto/compound-condition.validator.ts` was raised from **3 → 9** to unblock the First Colony staged
bundle. The write-time validator rejects condition trees deeper than 9 (`condition_depth_exceeded_authoring`). The evaluation-time walker uses `MAX_CONDITION_DEPTH = 10`; the 9/10 split ensures anything the validator accepts is also evaluable (the walker charges +1 depth on `each→element` branches). History: 2 (LOA-775) → 3 (LOA-1763) → 9 (LOA-2227). The parity spec `KNOWN_BLOCKED` is now empty — all staged bundle customs are evaluable.

<Note>
The `use_client_rule_sets` subsystem was fully removed (LOA-820 T3). Anything referencing client-rule-set opt-out or `isClientRuleSetsExplicitlyDisabled` is stale. The only remaining rule write-gate is the compound gate above.
</Note>

### Staged bundles (super-admin)

A second controller under `portal-appraisal-rules/staged-bundles` mounts at `api/v1/portal/admin`. Class-level `@Roles("super_admin")`, throttle 100/min. Staged bundles are curated rule sets that internal staff apply to a lender.

| Method / path | Purpose |
|---|---|
| `GET /api/v1/portal/admin/staged-rule-bundles` | List staged appraisal rule bundles (`StagedBundleListItem[]`) |
| `POST /api/v1/portal/admin/lenders/:lenderId/staged-rule-bundles/:bundleId/apply` | Apply a curated bundle to a lender (HTTP 200) |

The `apply` endpoint upserts both `loan_programs` rows and the associated `appraisal_rules` (the credit twin `apply` does the same for `credit_rules`). As of LOA-1872 (migration `0257`), apply also seeds `loan_programs.match_program_aliases` — an array of canonical program-name residuals used by the alias-first EPC program resolver. A row whose bundle definition carries no aliases binds SQL `NULL` (not `'{}'`) so a subsequent re-apply cannot clobber previously-seeded aliases with an empty array. Re-apply is append-only: `DO UPDATE COALESCE(excluded.match_program_aliases, loan_programs.match_program_aliases)` preserves existing aliases on conflict.

**Apply preview (LOA-2005/LOA-2033).** The `apply` path now executes writes inside a transaction and rolls them back (`DryRunComplete`), collecting a `RuleChangeRecord[]` diff before aborting. Each record carries:

| Field | Description |
|---|---|
| `ruleCode` | The rule being changed |
| `scope` | `{ kind: "lender-wide" }` or `{ kind: "program", programCode }` |
| `field` | `"severity"`, `"thresholds"`, `"isEnabled"`, or `"rule"` (whole-row for custom writes/removals) |
| `fieldKey?` | For `thresholds`, the individual threshold key (e.g. `"min_score"`) |
| `before` / `after` | The stored and written values |
| `effect` | `"applied"` (value changed) or `"no-op"` (value already matched — inert writes are reported, not dropped) |
| `classification` | One or more of `"severity-change"`, `"threshold-change"`, `"rule-activation"`, `"rule-deactivation"`, `"rule-removal"`, `"rule-reset"`, `"shared-loan-programs"` |
| `shadowedBy?` | Program codes whose program-scoped rows wholesale-override this lender-wide write |

This shape is defined in `common/staged-bundles/rule-change-record.ts` and built by `RuleChangeLog` in `common/staged-bundles/rule-change-log.ts` — one shape across all three services (appraisal, credit, eligibility) per PRD P8.

**Bundle versioning (LOA-2033/RuleOps D6).** Every bundle now carries a positive-integer `version` field plus a SHA-256 `checksum` computed over canonical bundle content (`common/staged-bundles/bundle-version.ts`). The checksum is committed to a per-service manifest (`emit-appraisal-bundle-manifest.ts`, `emit-credit-bundle-manifest.ts`, `emit-eligibility-bundle-manifest.ts`) and CI fails when bundle content and manifest disagree (`detectManifestDrift`). A content change without a version bump is also caught (`detectMissingVersionBumps`). Rule-set versions stamped from a bundle apply carry `source=bundle_apply, bundle_id=X, bundle_version=N`.

## portal-eligibility-rules

Eligibility rules govern per-lender LTV grid eligibility (loan-amount/FICO/occupancy/DSCR matrix rows), geographic bars, and LTV modifier stacks. They run only for loan-data channels (EPC / LOS / partner integrations + API) — portal appraisal-only runs have no URLA-derived loan axes and are gated out at the engine call site.

Two tables store authoring state for the eligibility system:

**`eligibility_rule_sets` / `eligibility_rules`** — the rule authoring model, mirroring the credit/appraisal shape (`rule_sets` + `rules` with `code`, `category`, `thresholds`, `evaluateFnKey`, `operator`, `fieldPath`, `condition`, and optional `loanProgramId`). Key differences from credit/appraisal: no `severity` column on the rule (severity is purely a function of `outcome`, computed by `eligibilitySeverity()`). Unique partial index on `(rule_set_id, name) WHERE is_active = true` prevents duplicate active names per lender.

**`eligibility_configs`** — a per-lender JSON config (one row per lender, unique) that carries the full eligibility engine input: `grids` (per-program LTV matrix rows keyed by `rowId`), `geoBars` (geographic bar rules), `ltvModifiers` (condo cap, cash-out cap, multi-unit/FL-condo/declining-market reductions), `programClassifier` (doc-type and name-regex program matching), and `ficoStrategy` (per-program FICO selection strategy). Loaded and Zod-validated on every read by `EligibilityConfigLoaderService`.

Grid row band axes (LOA-1778 adds three new columns alongside the existing `ficoMin`/`ficoMax`, `dscrMin`/`dscrMax`, `unitsMin`/`unitsMax`, and `purpose`/`occupancy`):

| Axis | Values | Notes |
|---|---|---|
| `docType` | `"FULL"` \| `"ALT"` | Closed enum — same aliased-collapse hazard as `purpose`/`occupancy`; `normalizeDocType` maps to exactly these tokens. |
| `dscrNoRatio` | `true` (literal) | Matches only when the borrower supplied no DSCR ratio. Cannot be combined with `dscrMin`/`dscrMax` — the validator rejects the combination. |
| `creditEventTrack` | `"STANDARD"` \| `"RECENT_EVENT"` | Closed enum; `normalizeCreditEventTrack` maps to exactly these tokens. |

Omitting an axis makes the row a wildcard for that dimension. Using `dscrNoRatio: true` alongside numeric DSCR bounds is a validation error at the persistence boundary.

<Note>
`programClassifier` and `ficoStrategy` are schema-valid and persisted but **not yet consumed at runtime** (forward-staged, LOA-1763 §B4). `determineProgram` still uses in-code doc-type/name regexes; `selectRepresentativeFico` still uses the in-code `FIRSTCOLONY_FICO_STRATEGY`. Do not treat them as live overrides until a later ticket wires the processor plumbing.
</Note>

`EligibilityConfigLoaderService.resolveByLenderId` emits the `eligibility_not_applied` `warn` log event when it resolves to `null` without applying eligibility. The `missingSurface` field identifies the cause:

| `missingSurface` value | Meaning |
|---|---|
| `rule_set` | No adopted (active) eligibility rule set for this lender. |
| `config` | No `eligibility_configs` row for this lender. |
| `both` | Neither an active rule set nor a config row exists. |

This log event (LOA-1957) replaced two silent `return null` paths that were previously byte-identical in Datadog to an applied lender with zero findings. An unapplied lender is a deploy state, not a fault — hence `warn` not `error`.

### Program input manifest (LOA-1967)

Migration `0282` adds a nullable `input_manifest` jsonb column to `eligibility_configs`. A **program input manifest** declares, per program and per eligibility check, every input the LTV engine reads: where each value comes from, whether it is raw or derived, what effect it applies, and which source wins when more than one can supply it.

The manifest is a **sibling** to the rest of `eligibility_configs` — parsed by its own Zod schema (`ProgramInputManifestSchema` in `database/schema/_payloads/eligibility-input-manifest.types.ts`) independently of `EligibilityConfigSchema`. A malformed manifest degrades the provenance card for the affected program without breaking the lender's grade.

<Note>
`NULL` is the normal state until a lender's adopter ticket stages a manifest. Eligibility grading continues without one but cannot produce a data-provenance card.
</Note>

**Schema shape.** The manifest carries `{ version: 1, programs: Record<string, ProgramChecks> }`. Version is pinned to `1`; a future shape change produces a hard parse failure on old rows and a 400 on write. Program codes are open lender vocabulary (not a closed union).

Each program declares exactly one check key today. `ProgramChecks` is `{ LTV: { inputs: ProgramInput[], stacking: StackingConfig } }`. The `LTV` check is the only supported check in v1; additional checks extend this object.

**Input sources (precedence = array order):**

| Tag | Supplied by |
|---|---|
| `LOS` | LOS-delivered loan metadata (MISMO XML) — values present at ingestion on the `loans` table |
| `URLA_AGENT` | Facts the URLA-Extraction agent derives from the 1003/MISMO after ingestion (e.g. loan amount, purpose, occupancy, state, county from URLA §4; FICO from `credit_runs.extracted_data`). These are NOT on the `loans` table at ingestion; tagging them `LOS` would assert a false readiness that blocks the resolver from waiting on extraction (LOA-1983). |
| `APPRAISAL_AGENT` | Appraisal-Evaluation agent output |
| `CREDIT_AGENT` | Credit-Evaluation agent output |
| `INCOME_AGENT` | Income agent output |
| `LEASE_OR_FORM_1007` | Lease or Form 1007 extracted data |
| `USER_PROVIDED` | Reviewer-entered override (ships with LOA-1987; until then a `USER_PROVIDED`-only input is a blocking gradability deferral) |

**Input effects:**

| Effect | Meaning |
|---|---|
| `SELECT` | Picks the LTV grid row. No magnitude. |
| `CAP` | Applies a `min()` ceiling to effective max LTV. Requires a `magnitude`. |
| `REDUCE` | Subtracts from effective max LTV. Requires a `magnitude`. Multiple REDUCE inputs stack; mode is `ADDITIVE` in v1. |
| `DISQUALIFY` | Ends the program outright. No magnitude. Optional `appliesWhen` gate. |

**Magnitude types** (for `CAP` and `REDUCE`):
- `FIXED` — `{ type: "FIXED", valuePct: number }`. LTV percentage points, bounded `[0, 100]`.
- `BANDED` — `{ type: "BANDED", axis: string, bands: MagnitudeBand[] }`. A step function that reads a numeric loan attribute (`axis`) and maps it to an LTV point value. Each band carries inclusive `min`/`max` bounds and a `valuePct`. Gaps between bands mean no magnitude in that range. Overlapping bands are rejected at the persistence boundary.

**Provenance.** Every input carries a `provenance` discriminated union:
- `{ kind: "RAW" }` — value comes directly from a declared source.
- `{ kind: "DERIVED", derivation, derivedFrom: string[] }` — value is computed from operand input codes. Derivations: `DSCR | BANK_STATEMENT_INCOME | DTI | ASSET_SUFFICIENCY | VALUE_BASIS`.

**Gradability.** `manifestGradability(manifest, program, check)` (`lib/loan-eligibility/input-manifest.ts`) returns whether the manifest can be graded for `program` + `check` and lists any deferrals. Blocking deferrals prevent grading entirely:

| Deferral kind | Blocking | Triggered when |
|---|---|---|
| `NO_MANIFEST` | Yes | Column is null |
| `PROGRAM_NOT_DECLARED` | Yes | Program code absent from manifest |
| `NO_INPUTS_DECLARED` | Yes | `inputs` array is empty |
| `USER_PROVIDED_ONLY` | Yes | An input has no system source (LOA-1987 pending) |
| `USER_PROVIDED_SECONDARY` | No | `USER_PROVIDED` is present alongside a system source |
| `UNRESOLVED_DERIVED_FROM` | Yes | A `derivedFrom` operand is not declared, or the operand chain loops |
| `UNKNOWN_AXIS` | No | An `axis`, `magnitude.axis`, or `appliesWhen.axis` is outside the engine's emitted vocabulary |

The helper is pure — it never logs, never throws, and never influences grading. It returns a report; the caller acts on it.

## RuleOps: automatic bundle application and rule exports

**RuleOps Trigger 1** (commit `c2f8b1d`, PRD `packages/api/docs/ruleops-trigger1-export-build-prd.md`) automates post-deploy appraisal bundle reconciliation so engineers no longer need to re-apply staged bundles by hand in a narrow window after each production deploy.

### How it works

A lender assignment declaration maps lender slugs to an ordered array of bundle IDs. After each deploy, a standalone CDK reconciler task runs inside the VPC on the deployed image, resolves each lender by slug (with an `expectedName` cross-check), applies bundles in the declared order, and verifies convergence with a two-pass gate: pass 2 must see exclusively `no-op` records before the run is declared converged.

Key design decisions:
- **Appraisal only.** Credit bundles are additive-only and cannot reach a fixed convergence point, so credit is out of scope.
- **A converged apply is not an empty diff.** `RuleChangeLog.push` emits a record for every declared write and labels it `no-op`. The convergence test is *every record is `no-op`*, never `changes.length === 0`.
- **A reconcile failure alerts; it does not fail the deploy.** Rule convergence is a separate operational concern; the alerting discriminator is `reconcile_incomplete`, not a negation of `reconcile_converged` (which fires on every healthy rule rollout).
- **Composition is not atomic across bundles.** One transaction per `applyBundle` call; a mid-composition failure leaves earlier members committed. The failure event names the partial state.

### Current deployment state

<Warning>
The assignment declaration **ships empty** in both `int` and `prod`. Populating it requires the LOA-2260 blast-radius gate (impact budget, per-dimension diff scoring, `refused_budget`) as a precondition. Until that gate lands, the reconciler runs successfully and exits having resolved zero lenders. The mechanism is fully built and tested; going live is a separate gated step tracked as **LOA-2260**.
</Warning>

### Rule-system export

Each bundle apply captures a versioned snapshot of the lender's rule state and ships it to S3 (`rule_set_exports` table, migration `0301`). The export:

- Is serialized **inside the apply transaction** (CPU only, no network), then shipped to S3 post-commit. This closes the race a post-commit re-read would open while keeping an S3 round-trip out of an open Postgres transaction.
- The capture sits inside a **SAVEPOINT**, not a bare `try`/`catch` — a bare catch would return a success summary over a database that kept nothing (Postgres aborts the whole transaction on the first statement error and runs the eventual `COMMIT` as a ROLLBACK without raising).
- Migration `0302` backfills `luxury-wse-credit`'s lender slug, required for the assignment declaration.

`rule_set_exports` schema:

| Column | Type | Description |
|---|---|---|
| `id` | uuid | Primary key |
| `lender_id` | uuid | FK to `lenders` (cascade delete) |
| `rule_set_id` | uuid | The rule set this export covers |
| `rule_set_version` | integer | Version at time of capture |
| `s3_bucket` | text | Versioned S3 export bucket (3-year retention) |
| `s3_key` | text | Object key |
| `s3_version_id` | text | S3 object version |
| `content_sha256` | text | SHA-256 of the exported content |
| `created_at` | timestamp | When the export was taken |

### Datadog monitors

Two monitors ship with the reconciler (`observability/datadog/`):
- `ruleops-reconcile-failed` — fires on `reconcile_incomplete` events.
- `ruleops-rule-export-lost` — fires when an S3 export does not land within the expected window.
