The partner results viewer is a separate UI under `/results/audits/[auditId]` that shows audit results to partners and the Encompass (EPC) iframe without a WorkOS login. It authenticates with a short-lived view JWT carried in a cookie. It is not under the `(app)` route group.

## Routes

`/results/audits/[auditId]` with sub-routes `1003-check`, `credit`, `data-consistency`, `document-health`, `property-data`, `appraisal`, and `exchange`. It renders with `@loanlight-engineering/shared-ui` `Sidebar`/`SidebarLayout` and the "audit-catalyst" theme.

The `appraisal` sub-route (`/results/audits/[auditId]/appraisal`) was added in LOA-1994. It renders `AppraisalSection` — the same component the overview's standalone-appraisal branch uses — so both display identically. The sidebar nav shows the appraisal item when a run is linked, the ledger reports pending or failed, or the appraisal fetch failed; it is hidden for audits with no appraisal run. The sidebar badge counts non-passing compliance outcomes (FAIL + WARNING); see [appraisal sidebar counting](#appraisal-sidebar-and-badge).

<Note>
The `credit` page now renders the shared `CreditLiabilitiesView` component (the same view used by the staff `credit-results` page), so partner and staff credit results stay in sync. Routes are unchanged.
</Note>

## Single authorization point

The layout `results/audits/[auditId]/layout.tsx` is the only authorization point. It authorizes via the `ll_results_view` cookie (a JWT verified by `verifyViewToken`, which must match the requested `auditId`) or mock mode.

When unauthorized, the layout renders bare `{children}` so `page.tsx` can show `<ResultsAccessDenied>`. This avoids a fetch → 401 → redirect loop.

<Note>
The `urlaCompleteness` field is tri-state: `null` (not run) vs `{rules_engine_result:{...}}` (loaded) vs `{rules_engine_result:null}` (deferred). Consumers MUST guard with `=== null` before applying `?? 0` to `failed_count`.
</Note>

## View tokens

`src/lib/results-access-token.ts` mints and verifies HS256 JWTs (`jsonwebtoken`):

- **Purposes:** exchange (`partner-results-exchange`, `epc-results-exchange`) and view (`partner-results-view`, `epc-results-view`).
- **Claims:** `{ auditId, lenderId, loanId, lenderCode, purpose, embedContext?, iat, exp }`.
- **TTL:** `VIEW_TOKEN_TTL_SECONDS = 120`, with `CLOCK_TOLERANCE = 5`.
- **Functions:** `mintViewToken`, `verifyViewToken`, `verifyExchangeToken`, `decodeViewPurpose`.
- **Cookie:** `RESULTS_VIEW_COOKIE = "ll_results_view"`.
- **Secret:** `PARTNER_RESULTS_JWT_SECRET` (required in prod, with a dev fallback).

A short-lived exchange token is swapped for a view cookie at `/results/audits/[auditId]/exchange`. See [results and access URLs](/partner-api/results-and-access-urls) for the partner-facing exchange flow.

## BFF data routes

The viewer's data API proxies the portal-audits BFF. Each sub-section maps to a Next.js API route under `app/api/v2/audits/[auditRunId]/<section>/route.ts`. The `appraisal` section was added in LOA-1994: `GET /api/v2/audits/[auditRunId]/appraisal` proxies `portalApiClient.get(".../appraisal", ...)` via `proxyPortalAuditsRoute(request, context, "appraisal")`.

Since LOA-2085 (#3227), a `POST` write route is also present:

| Route | Purpose |
|---|---|
| `POST /api/v2/audits/[auditRunId]/bank-statement-income/export` | Bank-statement income QI export for partner/staff audit surfaces. Proxies `proxyPortalAuditsWrite(request, context, "bank-statement-income/export")`. CSRF-gated; authenticates with the view token or session. |

This route is used by the **Export** button on the `/results/audits/[auditId]` income section (LOA-2085). The button is visible on any `status === "completed"` audit, even when `editable: false`. For read-only viewers (read_only staff, EPC), the export modal hides the notes field (`canAuthorNotes={false}`) to prevent a 403 from the notes-write path; the export itself still works.

The section `"bank-statement-income/export"` is listed in `PORTAL_AUDITS_WRITE_SECTIONS` (the CSRF allowlist in `packages/app/src/lib/portal-audits-write-sections.ts`).

## Appraisal sidebar and badge

The appraisal sidebar item is controlled by `resolveAppraisalPresentation()` in `results-data-context.tsx`, which gates on three signals in priority order: (1) the ledger override (`appraisalEvaluation` agent status) — if `not-run`, the item is hidden; (2) `appraisalError` with no payload — the item shows so a failed projection request does not silently disappear; (3) otherwise visibility follows `appraisal != null`. The badge counts non-passing compliance outcomes (`FAIL` + `WARNING` from `complianceResults`), or falls back to `findings.length` for pre-migration-0021 runs. This matches the EPC frontend's `countAppraisalFindings` logic (LOA-1995).

## Middleware carve-out

The viewer's data API (`/api/v2/audits/:id/<section>`) needs to be reachable by partners who hold a view token but no WorkOS session. The portal `middleware.ts` carves this out:

```ts
const PARTNER_AUDITS_V2_PATH = /^\/api\/v2\/audits\/[^/]+(?:\/[^/]+)+$/;
```

For a `GET` that matches this pattern with no WorkOS session (or with a partner token present — the `ll_results_view` cookie or `Authorization: Bearer`), the middleware bypasses WorkOS entirely. The route handler then authenticates in-handler via `portal-audits-proxy.ts` in priority order: portal session, then `ll_results_view` cookie, then Bearer. Staff who have a `wos-session` fall through to `withAuth` so the `x-workos-session` header is still injected.

<Warning>
The regex requires a sub-segment past the id (`(?:\/[^/]+)+`). `/api/v2/audits/:id` alone is NOT carved out — it stays gated behind WorkOS. This is enforced by `scripts/check-v2-audits-auth.sh`.
</Warning>

<Note>
The legacy `BEARER_AUDIT_PATH` carve-out for `/api/audits/*` plus a Bearer header was removed (LOA-894). Only the v2 `PARTNER_AUDITS_V2_PATH` carve-out remains.
</Note>

## Encompass iframe embedding

For `/results/audits/` paths, the middleware reads `ENCOMPASS_IFRAME_ORIGINS` and appends a `frame-ancestors` CSP directive while dropping `X-Frame-Options`, so the EPC plug-in can iframe the viewer. See [the Encompass integration overview](/integrations/encompass-overview).
