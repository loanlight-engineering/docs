The portal accepts large document uploads for appraisal, credit, income, and bank-statement analyses. There are two upload paths depending on the tool, and the backend parses multipart with Fastify's native `req.parts()`.

## Two upload paths

<Tabs>
  <Tab title="Server actions to S3 (appraisal, credit)">
    Appraisal and credit uploads go straight to S3 from a Next server action — there are no presigned URLs.

    - `src/lib/actions/upload-appraisal.ts` (`uploadAppraisalPdf`): 200 MB cap, `.pdf` extension plus a `%PDF-` magic-header check, UUID-validated `runId`, and S3 key `appraisal/<effectiveLenderId>/<runId>/<sanitized>`.
    - `src/lib/actions/upload-credit.ts`: the credit equivalent.

    The bucket env is `S3_UPLOAD_BUCKET`.

    <Note>
    The `PORTAL_TEST_PLAN` notes an earlier mismatch where the env was referenced as `PORTAL_S3_BUCKET`; the current variable is `S3_UPLOAD_BUCKET`.
    </Note>
  </Tab>
  <Tab title="Form-data POST proxy (income)">
    Income uploads use a form-data POST proxy through the BFF rather than a direct S3 server action.

    <Note>
    The income upload requires a UUID `loanId` (`@IsUUID()` on `CreateIncomeRunDto`). `formatUploadError` surfaces per-field validation errors in the upload UI.
    </Note>

    **Upload timeout.** Form-data proxies that carry files use `UPLOAD_TIMEOUT_MS = 1_200_000` (20 minutes) defined in `src/lib/constants/upload.ts`. Plain JSON reads and writes must keep their own short timeouts — only `fetch` calls whose body is a `FormData` carrying files should use this constant.
  </Tab>
  <Tab title="Chunked multipart sessions (bank statements)">
    Bank-statement uploads use a durable **upload session** (LOA-3055). The portal creates a session, streams each PDF to S3 in 8 MiB chunks, and submits the batch when all files are complete.

    Each PDF may be up to **250 MiB**. Because files travel as independent chunks rather than one combined request, there is no aggregate request-size cap for bank statements — the 260 MB body-size limit in `next.config.ts` no longer constrains a bank-statement batch.

    Retry resends only failed chunks while retaining completed files and form settings. Sessions are durable for up to 24 hours; a cleanup cron removes expired or cancelled sessions from S3. See [bank-statement-upload](/portal/api-bank-statement-dscr#bank-statement-upload) for the full API surface.

    <Note>
    The bank-statement **Loan ID** is free-text (≤255 chars), not a UUID (#2426, LOA-1577). On enqueue, `resolveLoanLink` links a real `loan_id` only when the value is a UUID matching a loan in the tenant; otherwise the raw value is stored verbatim in `borrower_files.loan_reference` with `loan_id` left null (migration `0195`).
    </Note>
  </Tab>
</Tabs>

## Body-size limits

`next.config.ts` raises the upload ceiling well above the largest per-request cap:

- `experimental.serverActions.bodySizeLimit: "260mb"`
- `experimental.middlewareClientMaxBodySize: "260mb"`

The 200 MB appraisal cap fits comfortably within this limit. Bank-statement uploads now use chunked multipart sessions with individual 8 MiB chunks, so the 260 MB ceiling no longer constrains how much total data a bank-statement batch can carry.

## Backend multipart parsing

The backend (loanlight-api, Fastify) parses multipart uploads with Fastify's native `req.parts()` async iterator.

<Warning>
The backend does NOT use `multer`. Upload controllers iterate `req.parts()` directly (for example `portal-dscr-agent.controller.ts` and `lender-guideline-documents.controller.ts`). Code or docs referencing `multer` for these routes are wrong.
</Warning>
