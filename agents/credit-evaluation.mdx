The Credit-Evaluation agent (`creditEvaluation`) is a fully implemented, 11-node compiled
LangGraph that extracts a credit report, computes facts, evaluates the lender's credit rules,
and persists a `credit_runs` row. Liabilities and DTI are part of this agent — there is no
separate liabilities agent.

<Note>
The legacy Octy system prompt lists `creditEvaluation` as a "stub, not yet implemented." That
is wrong. The agent is fully built: an 11-node graph plus the `lib/credit-pipeline` library
(extraction, a Zod facts schema, 26 rules CRED_001–CRED_030, summaries, risk projection), the
`portal-credit` NestJS module, and a BullMQ worker with heartbeat and orphan recovery. The only
genuine stub is [Liabilities-Assessment](/agents/liabilities-assessment).
</Note>

## How it runs

The agent has two entry paths.

<Tabs>
<Tab title="Solo run (portal)">
A standalone credit run is created from the portal via `POST /api/v1/portal/credit/run`
(`PortalCreditController`, base path `api/v1/portal/credit`). The DTO `CreateCreditRunDto`
carries `inputS3Key` (required, path-traversal guarded), optional `loanId`, `ruleSetId`,
`grossMonthlyIncome`, and `selectedRuleSources[]`.

`PortalCreditService` now creates a portal `audit_runs` container and one `creditEvaluation`
`agent_runs` ledger row at run creation (LOA-3372). The controller then inserts a `credit_runs`
row with status `pending`, `origin = 'portal'`, and `audit_run_id` set to the new container,
and enqueues a job on the BullMQ queue `credit-extraction`. `CreditProcessor`
(`modules/portal-credit/credit.processor.ts`, `@Processor("credit-extraction")`) claims the
run with a compare-and-set (`pending → running` plus a `claimToken` and heartbeat), downloads
the PDF from S3, and calls `LangGraphService.createCreditEvaluationGraph`.
</Tab>
<Tab title="Audit-driven run (pipeline)">
During an audit, `AuditAgentsExecutor`
(`integration-events/services/audit-agents-executor.service.ts`) runs credit evaluation inline
in Phase 2 alongside PII and property data. It fans out over the loan's classified credit-report
documents and calls `LangGraphService.createCreditEvaluationGraphWithSharedAuditRun`, attaching
the run to the parent [audit run](/concepts/audit-run) with `isAuditDriven: true`. Each run
upserts a `credit_runs` row keyed by `(auditRunId, auditedCreditDocumentId)`.

Credit evaluation only runs when the loan has at least one document whose
`classification_type` is in the credit-report allowlist (see below). If none is classified yet,
the executor skips credit — a per-agent skip never fails the audit run.
</Tab>
</Tabs>

`LangGraphService.createCreditEvaluationGraph` mints an `auditRunId` (and creates an audit run
when `loanId` is present), builds the graph, and races `app.invoke` against
`CREDIT_GRAPH_DEADLINE_MS` — an `AbortController` wall-clock backstop set strictly below the
BullMQ worker lock (`CREDIT_EXTRACTION_LOCK_DURATION_MS`). The graph's own `aggregate` node
persists the `credit_runs` row; the service does not.

### Credit-report classification allowlist

Audit-driven runs are gated on document classification. A document drives credit evaluation only
when its `classification_type` is one of the values in
`integration-events/constants/credit-report-classifications.ts`:

```ts
export const CREDIT_REPORT_CLASSIFICATION_TYPES = [
  "credit_report",
  "credit_report_trimerge",
  "credit_report_single",
] as const;
```

`AuditAgentsExecutor.hasClassifiedCreditReportForLoan` checks for at least one matching
[classify-split](/subsystems/classify-split) segment before enqueueing the agent, and the
fan-out iterates over those documents.

## The graph

The graph is linear:

```text
__start__ → prepare → detectScanned → ocr → extractText → extractStructured
  → mergeCandidates → validate → computeFactsSummaries → evaluateRules
  → generateAiSummary → aggregate → __end__
```

A parallel loan-view computation runs after the graph for audit-driven credit runs: `generateLoanNarrative` and `CreditLoanProjectionService` produce a loan-level view from the URLA extraction (see [Multi-borrower loan view](#multi-borrower-loan-view) below).

<AccordionGroup>
<Accordion title="prepare — cross-tenant guard">
If `loanId` is undefined, looks up the `credit_runs` row by `(pipelineId, lenderId)` and reads
`gross_monthly_income` and `rule_set_id`. If `loanId` is set, verifies the loan is owned by the
lender, reads `credit_report_date`, `credit_reference_number`, `loan_type`, and
`loan_program_name` from the `loans` row, and throws `CrossTenantGuardError` on mismatch. This
guard never soft-degrades. The audit-driven path keeps the orchestrator-seeded
`grossMonthlyIncome` but always reads the fresh credit metadata from the DB.

`isDscrLoan({ loanType, loanProgramName })` sets graph state field `dscrLoan: boolean | undefined`:
`true` when the loan is a DSCR program, `undefined` (not `false`) otherwise — a defined
`false` would turn CRED_001's "no loan context" `SKIP` into `NEEDS_INFO`.
</Accordion>
<Accordion title="detectScanned — digital vs scanned">
Loads the PDF with pdfjs and extracts text items. A page counts as "digital" when it has at
least `SCANNED_PAGE_THRESHOLD` (5) text items; the document is treated as scanned when digital
pages are at most half the total. Emits `isScanned` and `textItems`.
</Accordion>
<Accordion title="ocr — inert pass-through">
Returns `{}` and does nothing (LOA-1101). The old `ocrmypdf` preprocessing was removed and the
binary is absent in production; Reducto OCRs scanned PDFs natively in `extractStructured`. Do
not re-add OCR here.
</Accordion>
<Accordion title="extractText — text-layer candidates">
`generateCreditTextCandidates` from `textItems` (or a single `rawText` item). Records
`layersUsed` of `["ocr_text"]` or `["pdf_text"]`.
</Accordion>
<Accordion title="extractStructured — Reducto extraction">
When a Reducto client is present, `generateCreditReductoCandidates` runs over the PDF bytes.
Records `layersUsed` of `["reducto"]`. Skipped when no client is configured.
</Accordion>
<Accordion title="mergeCandidates — candidate merge and fact build">
Merges candidate maps in the order corrections → text → reducto
(`mergeCandidateMaps(injectCorrections(corrections), textCandidates, reductoCandidates)`), so
for same-priority ties corrections win over text, which wins over Reducto. Then
`buildFactsFromCandidates` produces `facts`. Records `["user_corrections"]` when corrections
exist.
</Accordion>
<Accordion title="validate — non-fatal schema check">
`CreditFactsSchema.safeParse(state.facts)`. On failure it logs and proceeds with the raw facts;
validation never aborts the run.
</Accordion>
<Accordion title="computeFactsSummaries — summaries and coverage">
`computeSummaries` produces `factsSummary` and coverage percent
(`computeCoverageFromFacts` against `COVERAGE_THRESHOLD`). This node must return
`facts.summaries` merged into facts, or six rules silently misfire.

As of LOA-2188 follow-up: `buildFactsFromCandidates` no longer fabricates `report.pulled_at` from the audit-run clock. The field is an optional, nullable fallback for a future real producer; `report_date` remains primary. Date-dependent credit rules use a single `resolveCreditReportReferenceDate` helper. A missing anchor returns `NEEDS_INFO` only when the date can change the verdict — anchor-independent outcomes (e.g. collections below the unwindowed cap) remain gradable. Coverage percent now reads extracted `report_date` rather than the previously fabricated timestamp, so values may differ from pre-deploy for runs where `report_date` was absent.

**Extraction coverage vs. compliance coverage (LOA-3291).** The `coveragePercent` this node computes and the `aggregate` node persists measures *extraction* coverage — how much of the facts schema the pipeline filled in. *Compliance rule coverage* — how many checks ran, passed, and need review on the portal — is a distinct quantity derived on read at serve time from the labelled `complianceResults` rows via `creditCoverageFromRows` (`audit/check-labels/response-fields.ts`). The stored `coveragePercent` column is not the source of truth for portal badge counts.
</Accordion>
<Accordion title="evaluateRules — DB-backed rule evaluation">
Resolves `loanProgramId` for program-scoped credit rules (LOA-1080) and calls
`evaluateWithCreditRules`. The DB evaluator is authoritative; this node does no rule-set
pre-lookup. Returns `complianceResults`, `ruleSetId`, `ruleSetVersion`, `scopedGrossMonthlyIncome`, and `dtiIncomeSuppressed`. The node threads
`loanAmount`, `creditReportDate`, `creditReferenceNumber`, `applicationBorrowers`, and
`dscrLoan` from the graph state into `CreditRuleContext`. `loanAmount` is used by CRED_024;
`creditReportDate` and `creditReferenceNumber` are the assertion side for CRED_029/030;
`applicationBorrowers` is the per-person roster used by CRED_001/002/003 for multi-borrower
consistency checks (see [Multi-borrower loan view](#multi-borrower-loan-view)).

**DSCR loan DTI suppression (LOA-3146).** DSCR loans qualify on property cash flow, not DTI.
When `dscrLoan === true`:
- **CRED_014** (DTI Ratio) and **CRED_025** (Max DTI + Residual Income) yield `SKIPPED` with
  reason `"Not applicable: DSCR loans qualify on property cash flow, not DTI"`.
- **CRED_024** (Credit-event Seasoning LTV Cap) ignores the `max_dti` threshold condition; the
  LTV and loan-amount conditions still apply.
- No `dtiRatio` is computed, persisted, or shown in the loan narrative for DSCR runs.

**Per-borrower credit group DTI scoping (LOA-2741).** On a multi-application loan, the
dispatcher hands every credit document the same loan-level `grossMonthlyIncome` because the
document's owning credit group is only knowable after that document's borrowers are extracted.
`mergeCandidates` resolves the group; `evaluateRules` applies it via `scopeDtiAxesToCreditGroup`:
- When the report resolves to a credit group that has qualifying income, DTI rules use that
  group's income (`scopedGrossMonthlyIncome`) and the group's `hasNonOccupantCoBorrower`
  indicator. The scoped values are also threaded into `generateAiSummary` so the DTI header
  and the AI narrative agree with the rule verdicts.
- When the report cannot be placed in a credit group and the MISMO declared grouping, DTI
  income is **suppressed** (`dtiIncomeSuppressed: true`) rather than divided by a population
  the report does not represent. Rules that require income (`CRED_014`, `CRED_025`) return
  `NEEDS_INFO` in this case.
- A loan whose MISMO declared no grouping keeps the flat loan-level scalar (prior behavior).
</Accordion>
<Accordion title="generateAiSummary — DTI and narrative">
Computes `dtiRatio = totalMonthlyDebt / grossMonthlyIncome`, guarding `grossMonthlyIncome > 0`.
When `dscrLoan` is true the ratio is not computed and `dtiShown` is `false`, so DTI is omitted
from the per-person loan narrative lines. `generateCreditSummary` produces `aiSummary` (skipped
when no OpenAI client is configured).
</Accordion>
<Accordion title="aggregate — persist">
Builds the completed payload (status `completed`, `extractedData` = facts, `complianceResults`,
`overallRisk` via `computeOverallRisk`, `aiSummary`, `coveragePercent`, `isScanned`,
`layersUsed`, `dtiRatio`, `grossMonthlyIncome`, `ruleSetId`/`ruleSetVersion`,
`auditedCreditDocumentId`). The solo path runs `UPDATE credit_runs` where status is in
(`pending`, `running`) and never writes a null `ruleSetId`. The audit path runs
`INSERT … ON CONFLICT` with `setWhere: ne(status, 'reviewed')`. Then it seeds key-field reviews
via `keyFieldReviewsService.seedForRun({ agent: "credit", … })`.
</Accordion>
</AccordionGroup>

The trap-door invariants for these nodes are catalogued in `creditEvaluation/CLAUDE.md`:
the `facts.summaries` merge, no rule-set pre-lookup, the DTI guard, the inert `ocr` node,
preserving `ruleSetId`, the merge order, the cross-tenant guard, the audit upsert `setWhere`,
and the persist branch keyed on `isAuditDriven`.

## CreditFacts schema

The extracted facts conform to `CreditFactsSchema`
(`lib/credit-pipeline/schemas/credit-facts.schema.ts`, `schema_version: "CreditFacts.v0"`). Top
level: `report`, `borrowers` (≥1), `bureaus` (1–3), and optional `disputes[]`, `tradelines[]`,
`inquiries[]`, `public_records[]`, `collections[]`, `alerts[]`, and `summaries`. The report-level
`disputes[]` array (`ReportDisputeSchema`: `status` in `active | resolved`, `creditor`,
`raw_remark`) backs rule CRED_023, and `report.is_first_time_homebuyer` backs CRED_022.
`PublicRecordSchema.resolved_date` (the discharge/dismissal/satisfied date, extracted by the
Reducto generator) drives the credit-event seasoning in CRED_018.

Selected enums:

| Field | Values |
|---|---|
| `EvidenceSchema.source_method` | `pdf_rule_based`, `pdf_table_model`, `pdf_regex`, `pdf_ocr`, `mismo_xml`, `vendor_json`, `pdf_hil_confirmed`, `reducto_extract`, `reducto_table` |
| `BureauNameEnum` | `experian`, `equifax`, `transunion` (+ `unknown`) |
| `AccountTypeEnum` | `mortgage`, `installment`, `revolving`, `charge_card`, `student_loan`, `auto`, `credit_card`, `heloc`, `personal_loan`, `line_of_credit`, `collection`, `alimony`, `child_support`, `other` |
| `AccountStatusEnum` | `open`, `closed`, `paid`, `charged_off`, `collection`, `foreclosure`, `repo`, `settled`, `deferred`, `unknown` |
| `PublicRecordTypeEnum` | `bankruptcy`, `tax_lien`, `judgment`, `foreclosure`, `short_sale`, `deed_in_lieu`, `civil_claim`, `other` |
| `InquiryTypeEnum` | `hard`, `soft`, `unknown` |
| `AlertTypeEnum` | `fraud_alert`, `active_duty_alert`, `id_theft_statement`, `ofac_notice`, `file_freeze`, `other` |

`ScoreSchema.score_value` is an integer 300–900 with a refine for FICO ≤ 850. The `summaries`
block carries `liabilities` (`total_monthly_debt`, housing/installment/revolving debt, secured
and unsecured balances), `delinquencies`, `utilization`, `counts`, `score`
(`representative_score`, `representative_bureau`, `meets_threshold`, `bureau_spread`), and
`tradeline_type_rollups[]`. The Work Number / TWN "Income Qualify" addendum fields on
`EmploymentSchema` drive rule CRED_016.

**CRED_022 — First-Time Homebuyer Program Eligibility (LOA-2739 / LOA-3223)**

CRED_022 is scoped to DSCR loans only. Previously it could fire on non-DSCR Purchase/PrimaryResidence loans when MISMO carried `<HomeownerPastThreeYearsType>No</HomeownerPastThreeYearsType>`, causing `deriveIsFirstTimeHomebuyer("NO") === true` and a false `FAIL`. The defect was scope, not derivation logic: the first-time homebuyer eligibility signal is an underwriting consideration only on DSCR programs. A non-DSCR loan where the borrower self-declares non-ownership yields `SKIPPED`.

**FTHB rebuttal from housing tradelines (LOA-2723).** `mergeCandidates` now runs a second
pass — `rebutFirstTimeHomebuyerFromHousingTradelines()` (`lib/credit-pipeline/derivations/first-time-homebuyer.ts`) — after the URLA ownership-interest declaration check. When the borrower has at
least one **open** housing tradeline (`account_type === "mortgage"` or `account_type === "heloc"`
with `account_status === "open"`) on their credit report, the rebuttal overwrites
`borrower.is_first_time_homebuyer` to `false`, regardless of what the URLA Section 5 declaration
stated.

The rebuttal abstains — preserving the current FTHB value — in three cases:
- `applicationBorrowerPartyCount` is absent (solo/portal credit path or URLA extraction failed).
- `applicationBorrowerPartyCount` is greater than 1: a multi-borrower application may carry
  housing tradelines that belong to a co-borrower, not the primary. The rebuttal does not attempt
  to reconcile bureau `borrower_id`s against URLA ordinals.
- The borrower has no open housing tradelines.

`applicationBorrowerPartyCount` is a graph state field, seeded by `urla-extraction-graph-runner.ts::
buildUrlaHandoff` from the URLA extraction result and threaded into `mergeCandidates`.

**Configurable lookback (LOA-3223).** CRED_022 rows can carry an optional `fthb_lookback_months`
threshold (integer 36–60). At the default of 36 (or absent), the rule grades on the persisted
`borrower.is_first_time_homebuyer` flag from `mergeCandidates`, matching today's behavior.
When set above 36, the rule computes an *effective* per-subject FTHB flag at evaluate time
without mutating the persisted flag — CRED_025 and every other rule that reads
`borrower.is_first_time_homebuyer` are unaffected.

A subject is cleared (FTHB → not FTHB) by either of two evidence sources:

- **A — credit report.** A mortgage, HELOC, or co-op tradeline attributed to that subject and
  dated inside the extended window. Single-subject reports attribute tradelines only when nothing
  suggests a second person was collapsed into the report. Two-subject reports use the
  `WHOSE` designator (`B`/`C`/`J`) to assign rows: `B` → first subject, `C` → second subject,
  `J` (joint) → both.
- **B — public property records (ATTOM).** For subjects path A could not clear, `evaluateRules`
  fetches ATTOM sales history (`AttomService.fetchSalesHistoryOnce`, one 15-second budget per
  graph) and checks for a recorded conveyance deed naming the subject as a whole party at one of
  their own addresses, dated inside the window. Only the match itself is persisted to
  `facts.ownership_records` (borrower id, owner label, URLA extraction id, basis, deed date):
  no names, addresses, or raw payloads.

Clearing is blocked when a subject's §5 answer is "No" and any evidence (tradelines or deed)
shows ownership within 36 months — CRED_022 stays `FAIL` regardless of the extended window.
A subject whose FTHB flag an underwriter corrected is never cleared by evidence.

Correction replay never calls ATTOM. It re-checks each persisted `ownership_records` entry
against the current window, the veto, and the corrections, without a new vendor call. The
`fthb_lookback_months` threshold on CRED_022 is editable from the portal's credit rules table:
a **CRED_022-only** "Edit Rule" dialog accepts whole months between 36 and 60 (the only rule
with a working per-row editor — no generic rule editor exists).

**CRED_017 — Housing Payment History (LOA-2722)**

CRED_017 previously could silently `PASS` a borrower with no payment history on any housing tradeline — or could `PASS` one who had delinquencies. Root cause: `summarizeIncidentMonths` set `sawUsableIncidentDate` only inside the incident loop, so an empty incident list left the flag unset, and OR-accumulation across tradelines let a single undated late cancel abstention. Fix: the rule now tracks two new signals — `unplaceableLateCount` (lates with no usable date) and `hasUnboundedHousingLates` (an undated late at or above the severity floor). A borrower with housing tradelines but no payment history abstains as `NEEDS_INFO`. A borrower with an undated late surfaces as `FAIL`; the rule never PASS-es silently again.

**CRED_029 — Credit Report Date Consistency** and **CRED_030 — Credit Reference Number Consistency** (LOA-1759)

Both rules compare Encompass-asserted loan fields against the extracted credit report. Migration `0261` adds `loans.credit_report_date` (text) and `loans.credit_reference_number` (text) — both nullable, populated by `loanlight-integrations` once the Encompass field entitlement lands. The rules are seeded by migration `0262` and backfilled into every active credit rule set at `WARNING` severity. Until the entitlement is mapped the columns are `NULL`, the rules' `skipForContext` gate fires before the required-fields precheck, and every lender sees a clean `SKIPPED` — never `FAIL`, never `NEEDS_INFO`.

- **CRED_029** warns when the credit report's `pulled_at` date differs from `loans.credit_report_date` by more than `tolerance_days` (default 1).
- **CRED_030** warns when the credit report's reference number matches neither `loans.credit_reference_number` nor the reference the report was reissued from.

**CRED_024 — Credit-event Seasoning LTV Cap** (`lib/credit-pipeline/rules/definitions/seasoning-ltv.ts`, LOA-1570 / LOA-1762)

Distinct from CRED_018 (which fails unseasoned events): CRED_024 governs the mid-tier band — an event seasoned past the hard floor but still within the configurable window (default 24–36 months) is eligible only up to a purpose-scoped LTV cap (Purchase 75% / Refinance 70%). It consumes `CreditRuleContext.ltv`, `purpose`, and — since LOA-1762 — `loanAmount`.

LOA-1762 added five optional threshold keys to the existing four:

| Key | Default | Purpose |
|---|---|---|
| `tier_min_months` | 24 | Lower bound of the mid-tier window |
| `tier_max_months` | 36 | Upper bound of the mid-tier window |
| `max_ltv_purchase` | 75 | Purchase LTV cap (%) |
| `max_ltv_refinance` | 70 | Refi LTV cap (%) |
| `foreclosure_tier_min_months` | — | Optional separate min for foreclosure events only |
| `foreclosure_tier_max_months` | — | Optional separate max for foreclosure events only |
| `max_loan_amount` | — | Optional loan-amount condition; reads `CreditRuleContext.loanAmount` |
| `max_dti` | — | Optional DTI condition; computed from `grossMonthlyIncome` + facts |
| `min_own_funds_pct` | — | Accepted but no data source yet; always routes to NEEDS_INFO |

Rows carrying only the original four keys behave byte-identically to pre-LOA-1762 behavior (the five new keys are all optional). A second-pass re-evaluator (`reevaluateCred024OnAppraisedLtv`) patches CRED_024's entry in an already-computed `complianceResults[]` after the appraisal worker completes with the true appraised-value LTV — the only rule whose basis moves between first and second pass.

### Finding citations

Since LOA-2213 (#3329), breach findings for several rules name the offending account(s) in the
finding message. The new `citation.ts` module (`lib/credit-pipeline/rules/definitions/citation.ts`)
appends a citation in the form `, including <Creditor Name> (xxxx).` — using the creditor name
plus masked account number.

Two citation shapes exist:

- **Short-circuit rules (CRED_004, CRED_005)** — the first matched tradeline is named. The message
  reads as a representative example (`"including…"`) rather than an exhaustive list, because
  these rules stop at the first hit and may not accumulate every offending account.
- **Accumulating rules (CRED_015, CRED_017, CRED_021, CRED_026)** — the full offending
  set is already held by the rule (these rules filter rather than short-circuit), so up to
  `MAX_CITED_ACCOUNTS` (3) accounts are cited, sorted by amount descending. Overflow is expressed
  as `+N more`. Rules that cite by dollar amount also sort entries deterministically to avoid
  diff churn across re-evaluations.

**CRED_006 (Active Delinquency)** was simplified in #4038: the finding no longer names individual
past-due accounts. The message reports the count and total owed — for example,
`"2 tradeline(s) currently past due totaling $3250.00."` — without account citations.

The AI summary generator (`generateCreditSummary`) strips account citations before sending text to
OpenAI, preserving the egress control: tradeline identity never leaves the LoanLight boundary.

<Note>
The citation text is appended to the existing finding sentence; it does not change the rule verdict
(`FAIL` / `WARNING`), the rule code, or any persisted schema field. The `complianceResults`
shape and the credit rules table columns are unchanged.
</Note>

### Rule evaluation

`evaluateWithCreditRules` (`rules/evaluator.ts`, delegating to `evaluateWithDb`) is DB-backed:

<Steps>
<Step title="Load the active rule set">
Loads the lender's active `credit_rule_sets`. It honors a `requestedRuleSetId` when that set is
active and lender-owned; otherwise it picks the most recent active set ordered by
`desc(createdAt), desc(id)`.
</Step>
<Step title="Load and overlay rules">
Loads `credit_rules` for that set ordered by `(code, loanProgramId, id)`, then applies
`applyProgramOverlay` so a program-scoped rule replaces the lender-global rule with the same
code.
</Step>
<Step title="Evaluate each rule">
A disabled rule yields `SKIPPED`. For built-in rules a context-applicability gate runs first: a
rule whose registry definition has a `skipForContext` that fires (e.g. CRED_001 on an
`occupancyType === "INVESTMENT"` loan — LOA-1652) yields `SKIPPED` **before** the required-fields
precheck, so an inapplicable rule never leaks a `NEEDS_INFO`. Otherwise missing required fields
yield `NEEDS_INFO`, then the evaluator dispatches `CREDIT_RULE_FN_MAP[evaluateFnKey]` with merged
and validated thresholds.

Custom rules (`evaluateFnKey === "custom"`) evaluate only when the `credit_custom_eval` feature
flag is enabled for the lender (`isCreditCustomEvalEnabled`): a compound rule (`rule.condition`
present) runs through the shared appraisal `evaluateCompoundRule` walker with the credit
`getRuleFieldValue` resolver and `CREDIT_RULE_FIELD_REGISTRY` injected, and a simple custom rule
runs `evaluateCreditCustomRule`. With the flag off, a custom rule yields `SKIPPED`.
</Step>
</Steps>

A breach verdict (`FAIL` or `WARNING`) is normalized to the rule's configured DB `severity` —
this is **bidirectional**: a rule that intrinsically emits `WARNING` (e.g. CRED_021) surfaces as
`FAIL` when the lender configures `severity: "FAIL"`, and vice versa. Non-breach verdicts (`PASS`,
`NEEDS_INFO`, `SKIPPED`, `PENDING`) pass through unchanged.

Outcomes are `PASS`, `FAIL`, `WARNING`, `NEEDS_INFO`, or `SKIPPED`. The evaluator returns
`{ results, ruleSetId, ruleSetVersion }`, returns empty results without `db` and `lenderId`, and
never throws.

**Skip reasons (LOA-3291).** Every `SKIPPED` and `NEEDS_INFO` result now carries a
`reason: CreditSkipReason` field (`lib/credit-pipeline/rules/types.ts`) explaining why no
verdict was reached. The five codes are:

| Code | Meaning |
|---|---|
| `disabled_by_lender` | The lender turned this rule off; it was not evaluated |
| `does_not_apply` | The rule is inapplicable to this loan or context |
| `missing_data` | A required field was absent (`NEEDS_INFO` cases) |
| `configuration_problem` | The rule definition or thresholds are invalid |
| `rule_error` | Evaluation itself threw an error |

A `SKIPPED` result with no explicit reason defaults to `does_not_apply`
(`evaluateResultReason`, `lib/credit-pipeline/rules/skip-reason.ts`). Human-readable text for
each code lives in `audit/check-labels/credit-reason-text.ts` (server-side only; the wire
carries the `reason` code and the existing row `message` remains the display text).

**RuleOps fence role on Aurora (LOA-3373).** The `ruleops_fence_*` database role that guards
raw-SQL writes to rule tables can now be provisioned by `DbInitUser` on Aurora PostgreSQL 16.
Aurora does not add the creator membership edge that standard PostgreSQL creates automatically;
the `ruleops-scanner-utils.ts` canary now accepts a fence role with no creator edge while still
rejecting unexpected membership or creator edges with `INHERIT` or `SET`. `DbInitUser`'s
`bootstrapVersion` was bumped to `"4"` to reflect this change.

The rule operators on `credit_rules.operator` use the 16-value union pinned by
`credit_rules_operator_check`. Migration `0190_credit_operator_abs_parity` added `abs_less_than`
and `abs_less_than_or_equal` to bring credit to operator parity with appraisal, so credit and
appraisal now share the same 16 operators. Each rule may use exactly one rule type: a `condition`
JSONB, an `operator` + `fieldPath`, or none (`chk_credit_rule_type_exclusive`).

## Data model

The credit subsystem lives in `database/schema/credit-runs.ts`, `credit-rule-sets.ts`, and
`credit-rules.ts`. See [the financial data model](/data-model/financial-data-model) for the full
catalog.

<ResponseField name="credit_runs" type="table">
One row per run. Carries `status` (`pending | running | completed | failed | reviewed`),
`extractedData` (facts), `complianceResults`, `aiSummary`, `isScanned`, `coveragePercent`,
`overallRisk`, `dtiRatio` (real), `grossMonthlyIncome` (real), `ruleSetId`/`ruleSetVersion`,
`auditRunId`, `origin` (`portal | audit`, see below), `selectedRuleSources[]`, `layersUsed[]`,
`auditedCreditDocumentId`, recovery columns (`lastHeartbeatAt`, `claimToken`,
`recoveryAttempts`, `errorCategory`), `deletedAt` (soft delete), and `summary_reconciliation`
(jsonb, nullable — see below). Two partial unique indexes —
`(auditRunId, auditedCreditDocumentId)` and `(auditRunId)` where the document id is null —
both gated on `deleted_at IS NULL`. `buildCreditRunsConflictArgs()` chooses the upsert target.

**`origin` (LOA-3372, migration `0197`).** Identifies which lane wrote the row: `'portal'` or
`'audit'`. The audit lane's writers omit this column and rely on the `DEFAULT 'audit'`; a DB
trigger stamps `'portal'` on a row inserted without a container (`audit_run_id IS NULL`) during
a rolling deploy. `CreditProcessor`'s recovery sweep and the orphan-sweep partial index now key
on `origin = 'portal'` instead of `audit_run_id IS NULL`. Historic portal rows were backfilled
to `'portal'` at migration time.

**`summary_reconciliation` (LOA-3320).** After extraction, the agent extracts the credit report's
own summary tables and compares them against totals computed from the extracted tradelines. Proven
discrepancies are stored here as `CREDIT_SUMMARY_TABLE_MISMATCH` findings. This field is internal:
it does not affect credit rule outcomes (`complianceResults`), risk values, or any lender-facing
payload. Uncertain comparisons (where an LLM judge is needed) are resolved before storage except on
shadow runs, where judge calls are skipped.
</ResponseField>

<ResponseField name="credit_rule_sets" type="table">
Lender-scoped, versioned rule sets (`lenderId`, `name`, `version`, `templateVersion`,
`isActive`, `createdBy`). Partial unique `(lenderId, name)` where active.
</ResponseField>

<ResponseField name="credit_rules" type="table">
Per-rule definitions (`ruleSetId`, `sourceTemplateId` — intentionally not an FK, `code`, `name`,
`category`, `severity` (`FAIL | WARNING`), `thresholds`, `requiredFields[]`, `formTypes[]`,
`evaluateFnKey`, `operator`/`fieldPath`/`expectedValue`/`condition`, `source`, `failMessage`,
`passMessage`, `isEnabled`, `loanProgramId`).
</ResponseField>

Human-in-the-loop tables: `credit_corrections` (field edits) and `credit_rule_overrides`
(override outcome `PASS | FAIL | WARNING | NEEDS_INFO | SKIPPED`).

**CRED_031 — Minimum Usable Score Count**

Fires when a borrower's credit report contains fewer than the configured `min_score_count` of usable bureau scores. A score whose bureau cannot be named (unknown bureau) is not counted as usable. Outcomes: one usable bureau score = `FAIL`; two or three usable scores = `PASS`; zero usable scores, or a score with an unidentifiable bureau = `NEEDS_INFO` (existing pre-threshold behaviour). The rule cannot distinguish a bureau with no file on the borrower from one that was never pulled; the threshold is set to reflect the minimum that guidelines require, not the number of bureaus expected.

**CRED_026 — Aggregate Collections Cap (Medical/Window Carve-out) (LOA-2391)**

CRED_026 applies the `window_months` carve-out only when both `window_months` is configured and a reference date is available (`resolveCreditReportReferenceDate`). When `window_months` is set but the reference date cannot be resolved (`windowUnresolvable`), dated collections may or may not fall inside the window once an anchor arrives — so the rule cannot include them as reliable lower-bound evidence.

A bug (LOA-2391) caused the rule to count **all** readable collections in the lower-bound path when `windowUnresolvable`, including dated rows that the window might later exclude. The fix adds an `isCertainUnderEveryAnchor` helper: a collection is *certain* only when `windowUnresolvable` is false, or when its `opened_date` is not parseable by `parseCreditDate` (i.e. the row has no usable date and cannot be placed relative to any anchor).

Current evaluation paths when `windowUnresolvable`:

- **Unreadable amounts present:** the lower bound counts only `certain` collections with a non-negative amount. The finding message appends "(collections with no usable opened date only)" to identify the scope.
- **All amounts readable, undated-only total ≥ cap:** emits `WARNING` — collections with no usable date breach the cap even before the window can be applied.
- **All amounts readable, full pre-window total < cap:** emits `PASS` — the window can only shrink the qualifying set further.
- **All amounts readable, full total ≥ cap but dated collections contribute:** emits `NEEDS_INFO` ("Reference report date is unavailable for the collection window carve-out.") — the anchor is required before the rule can breach.

## Multi-borrower loan view

`CreditLoanProjectionService` (`lib/credit-pipeline/projection/`) builds a loan-level view from the URLA extraction alongside the per-report credit runs. It resolves the correct per-person numbers on loans with multiple joint-credit groups.

**How it works:**

- Builds a person/credit-group roster from the 1003 (URLA) extraction when present, falling back to report-derived groups when URLA is absent.
- Matches each credit run's subjects onto the roster via `subject-matching.ts` (Jaro-Winkler ≥ 90, suffix stripping for Jr/Sr/II/III/IV, SSN last-4 tiebreaker + contradiction rules).
- Per-person score, liabilities, income, and DTI are computed using only the subjects belonging to that person's `borrower_id`.
- Loan-level qualifying FICO (lender-configurable method) and combined liabilities + DTI sit on top.

**Override propagation (LOA-3291).** When the loan roster is built, active reviewer overrides
(from `credit_rule_overrides`) are applied to each report's `complianceResults` before findings
are attributed to people. `CreditLoanProjectionService.buildRoster` accepts an `overridesByRun`
map and passes it to `buildFindings → applyOverrides`, ensuring person-level badge counts on the
loan page reflect the same verdict the reviewer applied, not the original evaluation.

**Supersession:** reports within a group are ordered by `pulled_at desc → credit_runs.created_at desc → credit_runs.id asc`. Superseded reports' findings carry `superseded: true` and are excluded from all badge counts.

**CRED_001/002/003 per-borrower consistency:** the `applicationBorrowers` context field threads the URLA person roster into the evaluateRules node. Each report's subjects are compared against their _own_ application borrower rather than all borrowers on the loan, eliminating false name-consistency failures on co-borrower reports.

**Loan-level findings:**

- `CRED_L01` — qualifying FICO vs. the lender's configured minimum (`≥` is a pass). Computed by the projection, not stored as a `credit_rules` row.
- `CRED_L02` — combined DTI vs. the lender's configured maximum (`≤` is a pass). Suppressed entirely when `dtiShown` is false. `dtiShown` is false only when `loan_type` is exactly `DSCR`.

**Loan narrative:** `generateLoanNarrative` produces a loan-level narrative plus one paragraph per person, stored in `audit_runs.credit_loan_narrative` (jsonb, nullable). Status is `ready | pending | failed`. A manual retry is available via `POST /api/v1/portal/audits/:auditRunId/credit/loan/narrative/retry` (proxied from the portal BFF at `/api/v2/audits/[auditRunId]/credit/loan/narrative/retry`). Registered as `creditEvaluation.loanNarrative` in `creditEvaluation/llm-steps.ts` (group must equal `creditEvaluation` for the router's config freeze to resolve it).

The generation call is capped at `LOAN_NARRATIVE_MAX_TOKENS = 4096` output tokens — sized for one loan paragraph plus one per person. When the model hits this ceiling (`finish_reason === "length"`), the JSON is truncated mid-write and fails to parse. The automatic retry is **skipped** in this case: a second attempt against the same roster and the same ceiling produces the same outcome. The retry runs only for transient failures (vendor errors, malformed JSON that is not due to truncation). A truncated run writes `status: "failed"` and should be investigated via the manual retry endpoint.

**Lender setting:** `credit_qualifying_fico_method` in `lender_feature_flags` — `lowest_middle` (default) or `primary_wage_earner`. Configurable via the credit rules admin select.

**FICO selection strategies (LOA-3314).** The loan's representative qualifying FICO is chosen by
`selectRepresentativeFico` (`lib/loan-context/fico-selection.ts`) from a `FicoSelectionSeed`
(a set of `FicoPerson` objects — one per credit person with a borrower id and a FICO — and
`FicoCandidate` objects — one per 1003 borrower with their monthly income state). Three named
strategies are defined:

| Strategy | How it picks |
|---|---|
| `HIGHEST` | The scored person with the highest FICO across all borrowers. |
| `LOWEST_MID` | The scored person with the lowest FICO across all borrowers (the traditional qualifying FICO). |
| `PRIMARY_WAGE_EARNER` | The borrower with the unique highest 1003 monthly income. Each candidate must own exactly one scored person (matched by `ownerLabel`); a tie, a missing income field, or an unmatched person returns an unknown reason rather than guessing. A loan with exactly one borrower selects that borrower without reading income. |

The strategy is resolved from a `FicoStrategyConfig` (a `program → FicoStrategyName` map
plus a required `default`), stored per lender in `eligibility_configs.ficoStrategy`. The active
program's own entry is used; when the program is null, the `default` is used. A missing entry
for the active program is `strategy_miss` (not a fallback to another lender's policy).

When `PRIMARY_WAGE_EARNER` cannot pick a winner, `FicoUnknown` records the reason
(`income_tie`, `income_missing`, `income_unreadable`, `borrower_unmatched`, `no_score`,
`application_missing`). The most severe failure is reported first, using the precedence order:
`application_missing` → `borrower_unmatched` → `no_score` → `income_unreadable` →
`income_missing` → `income_tie`.

Custom credit-rule authoring lives in a separate `portal-credit-rules` module
(`PortalCreditRulesController`): natural-language parsing (`credit-nl-parse.service.ts`), a
dry-run preview (`credit-preview.service.ts`), the credit field registry, a compound-condition
validator (`credit-condition-validator.ts`), and per-lender staged bundles
(`staged-bundles/`, e.g. `firstcolony-credit`, `luxury-wse-credit`). A long pasted rule that the
parser splits into two is persisted in `credit_rule_split_drafts` (migration
`0189_credit_rule_split_drafts`, a credit-specific table — do not reuse the appraisal
`rule_split_drafts`).

Program-scoped behavior is expressed through these bundles plus `applyProgramOverlay`. The
`luxury-wse-credit` bundle, for example, runs CRED_011 (Recent Inquiries) in **report-only** mode
lender-wide — the `report_only` threshold flips the rule to surface the 12-month hard-inquiry
count for review with no limit — and disables CRED_011 entirely on the DSCR investor-cash-flow
programs (`PCF`, `SCF`) via `isEnabled: false` program overlays.

## Reliability and recovery

`CreditProcessor` writes are scoped by a `claimToken` and keep a heartbeat
(`CREDIT_HEARTBEAT_INTERVAL_MS`). A startup reconcile plus a periodic orphan sweep
(`CREDIT_ORPHAN_SWEEP_INTERVAL_MS`) recover stale `pending`/`running` portal runs
(`origin = 'portal' AND deleted_at IS NULL`), re-enqueue them with `addBulk` (jobId
`recover:<id>:<attempts>`) up to `CREDIT_MAX_RECOVERY_ATTEMPTS`, then terminally fail. There are
two orphan legs: stale-heartbeat (older than `heartbeatCutoff`) and null-heartbeat
(`startedAt < windowCutoff`). Runs that are still heartbeating past
`CREDIT_SILENT_RUN_BUDGET_MS` are alert-only — termination is owned by the in-process
`CREDIT_GRAPH_DEADLINE_MS` deadline, which sits strictly below the BullMQ lock.

**Graceful shutdown (LOA-3412).** On SIGTERM, `shutdownGracefully` (`src/graceful-shutdown.ts`)
stops the `SqsConsumerHost` from accepting new SQS messages, waits for `BullWorkerShutdown`
to drain all in-flight BullMQ jobs (including credit runs), then calls `app.close()`. This
ensures a credit run in progress is not killed mid-graph during a rolling deploy.
