The Property-Data agent (`Property-Data`) extracts the subject and borrower addresses from the
MISMO XML, fetches property data from external providers, and consolidates it into a single
`ConsolidatedProperty` per property. It is a LangGraph compiled graph under
`langgraph/agents/propertyData/`, built by `buildGraph(options)` with
`{ progressEvents, zillowUrlFinder, hasData, attom, llama }`.

The agent is invoked from `property-data-graph-runner.ts` via `createPropertyDataGraphWithSharedAuditRun(...)`. The graph itself
only returns state and instrumentation; **the runner writes all DB rows**, not the graph.

The `ConsolidatedProperty` objects this agent produces are the primary input to the
[Property-Red-Flags agent](/agents/property-red-flags).

## Graph topology

```text
__start__ → extractAddresses → validateAddresses
  validateAddresses → fetchProperty   (Zillow URL + HasData scrape + ATTOM property, bundled)
  validateAddresses → fetchHazard     (ATTOM natural-hazard)
  validateAddresses → fetchRedfin     (Redfin gap-fill; gated by ENABLE_REDFIN_SOURCE; enabled in int + prod since LOA-2091)
  fetchProperty / fetchHazard / fetchRedfin → consolidate   (true barrier join)
  consolidate → aggregate → __end__
```

The three source fetches run as equal-depth parallel siblings under one shared wall-clock ceiling.
`fetchProperty` bundles Zillow + ATTOM so the instrumentation channel is written once per
super-step.

A fourth concern — **listing screenshot capture** — runs as a side effect inside `fetchProperty`
(Zillow) and `fetchRedfin`, not as a separate node, so it never adds to the wall-clock ceiling.
See [Listing screenshots](#listing-screenshots) below.

<Info>
**Wall-clock ceiling.** `PROPERTY_DATA_CEILING_MS = 10 minutes`. `withWallClockCeiling(...)` races
each fetch against `graphStartedAt + ceilingMs`; on exceed it resolves to `null` (a no-data
sentinel) and emits `property_data_wall_clock_abort`. Real fetch errors still propagate to the
caller's try/catch.
</Info>

## Stages

<Steps>
<Step title="extractAddresses">
If subject + borrower address overrides are present, uses them directly (REO addresses always come
from the override). The REO override carries only Section 3 properties whose
`occupancyType === "INVESTMENT"` — `transformToPropertyAddresses` filters out every other occupancy
type upstream (LOA-751), so retained primary residences and second homes never become phantom
`investment` rows downstream. Otherwise runs an LLM extraction over the MISMO 3.4 XML
("MISMO 3.4 XML ADDRESS EXTRACTION EXPERT" prompt): the subject property address from
`//SUBJECT_PROPERTY/ADDRESS` and the borrower current address from the borrower party's current
residence. `monthlyRent` is extracted only when the borrower address has a unit. The LLM does not
extract Section 3 REO addresses.

**Multi-borrower support (LOA-3123).** `transformToPropertyAddresses` reads **every borrower's**
address and Section 3 REO entries, not just Borrower 1's. Each borrower's current address becomes
a separate `borrowerResidences` entry (attributed by 1-based borrower index). Borrowers who share
the same address and unit are collapsed into one entry; borrowers in different units of the same
building stay separate. On a refinance, a co-borrower's address in the subject's building is
treated as the subject property. Each residence is gated on its **own** borrower's own-or-rent
answer — a blank answer is treated as unknown, never borrowed from Borrower 1. Investment Section 3
entries from all borrowers feed the REO channel, deduplicated across borrowers.
</Step>

<Step title="validateAddresses">
Requires subject street/city/state, else skips and emits `EVENTS.WORKFLOW.ERROR`. The borrower
address is required for non-refinance loans; a missing borrower address on a REFINANCE continues
subject-only.
</Step>

<Step title="fetchProperty — Zillow + HasData + ATTOM">
`zillowUrlFinder.findPropertyUrl(...)` resolves a Zillow detail URL (direct Zillow search first, SerpApi fallback — see the SerpApi accordion under External providers);
`hasData.getPropertyDetails(...)` scrapes the listing, photos, and zestimate; `attom.getPropertyData(...)`
fetches official records. The borrower fetch is gated by `shouldFetchBorrower(state)`, and there is
a REO loop per `reoAddresses`.

A subject-only Zillow listing screenshot is captured here via `ListingScreenshotService.captureIfMissing`
and stored on the `subjectZillowScreenshot` state channel whenever a `ListingScreenshotService` is
injected and the subject Zillow URL passes the unit gate.
</Step>

<Step title="fetchHazard">
`attom.getNaturalHazard(...)` for the subject (borrower + REO gated). Writes only the natural-hazard
channels, disjoint from the instrumentation channel.
</Step>

<Step title="fetchRedfin (enabled in int + prod)">
Gated by `ENABLE_REDFIN_SOURCE === "true"`. Since LOA-2091 this variable is set `"true"` in integration and production environments — the step is no longer off by default.

Redfin URL discovery uses a two-stage path (LOA-3270): a HasData direct listing search runs first, and SerpApi is the fallback.

1. **HasData direct listing search (primary).** `buildRedfinListingKeyword` constructs a search keyword from the address. `HasDataService.getRedfinListingDetails` requests HasData's Redfin listing-search endpoint with unit and locality validation (street number, street name, unit match, ZIP5 or city+state). A mismatch or shape rejection falls through to SerpApi. The direct path is subject to the same shared per-run budget as the Zillow direct path (max 6 attempts, 120 s cumulative, 45 s per attempt).
2. **SerpApi fallback.** When the direct path returns nothing or is skipped, `ZillowUrlFinderService.findPropertyUrl(input, "redfin")` searches Google (`site:redfin.com`, detail path `/home/`) and scrapes the resolved URL via `HasDataService.getRedfinPropertyDetails`.

Each lookup emits one `property_data_url_discovery` INFO event with `site: "redfin"`. A null result from either path degrades to a no-op merge. Redfin data is consumed by two separate merge paths: `mergeCandidates` can source the current listing, last sale, price history, or estimate from Redfin when Zillow supplies none; `mergeRedfin()` additively fills tax, property facts, and coordinates — never overwriting a non-null incumbent from HasData/Zillow or ATTOM (LOA-3272).

A subject-only Redfin listing screenshot is captured here via `ListingScreenshotService.captureIfMissing`
and stored on the `subjectRedfinScreenshot` state channel. Zillow and Redfin screenshots are
captured independently because these two nodes run as parallel siblings in the same super-step.
</Step>

<Step title="consolidate">
`consolidateProperty({ address, hasData, attom, zillowUrl, redfin })` produces a
`ConsolidatedProperty`. Two distinct merges run here (LOA-3272):

**Listing merge (`mergeCandidates`).** Before the consolidated object is built, each source
(Zillow, Redfin, ATTOM) is turned into a `ListingCandidate` and passed to `mergeCandidates`.
For each listing group (`currentListing`, `lastSale`, `priceHistory`, `photos`, `estimate`, `apn`,
`hoa`), the merge takes the value from the first source in that group's priority list that supplied
it, and records the winning source in `listing.sources`. Priority by group:
- `currentListing`, `priceHistory`, `photos`, `hoa`: Zillow → Redfin
- `lastSale`, `estimate`: Zillow → Redfin → ATTOM
- `apn`: ATTOM → Zillow → Redfin

This means a property card shows one label and one source per number — e.g., if Zillow has no
current listing but Redfin does, Redfin supplies `currentListing` and `listing.sources.currentListing
=== "redfin"`. The ATTOM AVM is never shown as an estimate label to reviewers; only Zillow
("Zestimate") and Redfin ("Redfin Estimate") are labelled.

**Domain gap-fill (`mergeRedfin`).** After the listing merge, `mergeRedfin()` fills null incumbents
in three domains — tax/assessment, property facts, and coordinates — additively. It never
overwrites a non-null value from Zillow or ATTOM. The tax fill is year-aware (LOA-3343): when an
ATTOM assessed value is present but `taxAmount` is null, Redfin fills `taxAmount` only from the
Redfin record for that same assessment year — never from a newer or older payment, so the
`{taxAmount, taxYear}` pair always describes the same year.

ATTOM for official records (ownership, mortgages, title, liens, sales/assessment history, AVM).
Subject↔borrower proximity is computed by haversine; `proximity.flagged = miles > 50`.
One `consolidateProperty` runs per REO address.

**ATTOM subject parcel verification (LOA-3026).** After ATTOM data is fetched, `verifyAttomSubjectParcel`
checks that the returned record actually describes the property on the loan file. When two conditions
are both true, the record is marked **unverified** (`attom_parcel_mismatch`) and withheld from the
consolidated result everywhere (AVM, assessment, sales history, and all other ATTOM fields):

1. The loan file describes an improved residence (`FinancedUnitCount` 1–4, or an attached/detached,
   site-built, primary-residence or second-home property).
2. The ATTOM response has **both** no building data (no living area, beds, or baths) **and** a
   land-type label in `propertyType`, `propType`, or `propLandUse` — recognized land words:
   `miscellaneous`, `vacant`, `unimproved`, `land`, `lot`. (`"RESIDENTIAL (NEC)"` is not a land
   word; ATTOM uses it on improved homes.)

An APN mismatch alone never rejects a record because MISMO and ATTOM format APNs differently often
enough that a mismatch is weak evidence. This change prevents a wrong-parcel AVM (for example, an
adjacent vacant lot whose AVM is strong) from reaching the valuation decision or red-flag rules.
</Step>

<Step title="aggregate">
Logs the instrumentation summary and returns `{ completed: true }`.
</Step>
</Steps>

## Listing screenshots

`ListingScreenshotService` (PR #4313) captures and stores a subject-property listing screenshot
as audit and compliance evidence. It is **not** a data source — it records what the Zillow or
Redfin listing showed at audit time, separate from the structured property data `HasDataService`
scrapes.

**Enablement.** Listing screenshots run automatically for every lender (LOA-3256 removed the per-lender `listing_screenshot_enabled` opt-in flag). The Zillow screenshot fires whenever a `ListingScreenshotService` is injected into the graph and the Zillow URL resolves a valid unit-gate. The Redfin screenshot is gated by `ENABLE_REDFIN_SOURCE` — a killswitched lender skips the Redfin node entirely and receives no Redfin screenshot.

**One per (loanId, source), reused across audit runs.** The S3 key is deterministic:
`property-data/{loanId}/subject-{source}-listing` (no file extension; `ContentType` at PutObject
time is the authoritative format). `captureIfMissing` does a `HeadObject` check first. A cache
hit returns `{ s3Key, sourceUrl, capturedAt, reused: true }` with no new HasData call.

**Two channels.** `subjectZillowScreenshot` and `subjectRedfinScreenshot` are disjoint graph-state
channels for the same reason `redfinSubject` is a separate channel from `property`: the Zillow
and Redfin fetches are parallel siblings, so a shared channel would cause a reducer conflict.
Only the subject property gets a screenshot; borrower and REO addresses do not.

**Failure handling.** Any failure (missing bucket config, `HeadObject` error, HasData capture
failure, `PutObject` failure) resolves to `null` — a missing screenshot never blocks the
primary property fetch.

## Borrower-fetch gate

`shouldFetchBorrower(state)` decides whether to fetch the borrower's current address:

- Non-refinance → fetch.
- Refinance and borrower address equals subject → skip (duplicate).
- Refinance, different address, `housingExpenseType === "OWN"` → fetch (Property-Red-Flags Rule B
  needs ownership data).
- Refinance, different address, RENT or unknown → skip.

## External providers

<AccordionGroup>
<Accordion title="ATTOM (AttomService)">
`baseUrl = https://api.gateway.attomdata.com`, env `ATTOM_API_KEY` (header `apikey`).
`getPropertyData()` fans out **11 endpoints** in parallel (`/property/basicprofile`,
`/property/expandedprofile`, `/assessmenthistory/detail`, `/saleshistory/expandedhistory`,
`/property/detailowner`, `/property/detailmortgageowner`, `/property/detail`, `/sale/detail`,
`/attomavm/detail`, preforeclosure detail, and `/propertyapi/v1.0.0/property/buildingpermits`) with a unit-qualified lookup and street-only fallback. The building-permits endpoint is subject-scope only — not fetched for the borrower or REO addresses. Its result is consolidated into `ConsolidatedProperty` as `buildingPermits` (array of permit records, each with `status` and other jurisdiction-specific fields) and `buildingPermitsAvailability` (`"affirmed_empty"` when ATTOM confirmed the lookup ran with no records; `"unavailable"` on error or no-match). These two fields drive the [`UNPERMITTED_RENOVATION`](/agents/property-red-flags) red-flag rule (LOA-539). The success-log denominator reflects the 11-endpoint set for subject scope (10 for borrower/REO).
`getNaturalHazard()` is a 2-step v4 flow (`property/detail` → `geoIdV4` →
`/v4/neighborhood/community`) parsed into a FEMA flood zone + hazards. 30s timeout, 3 retries with
backoff.
</Accordion>

<Accordion title="HasData (HasDataService)">
Env `HASDATA_KEY` (header `x-api-key`). `getPropertyDetails(zillowUrl, ...)` and
`getRedfinPropertyDetails(url)`. Scrape timeout `HASDATA_SCRAPE_TIMEOUT_MS` (default 300000ms),
retry budget `HASDATA_RETRY_BUDGET_MS` (default 600000ms), max 3 attempts. Errors:
`HasDataError`, `HasDataUpstreamStatusError`, `HasDataRetryExhaustedError`.

Since LOA-1745 (#2695), `scrapedAddressMatches` is **unit-aware**: when the expected subject address
names a unit, the scrape result must resolve to the **same** unit (normalized so `#811` ≡ `APT 811`
≡ `Unit 811` ≡ `811`). A different or missing unit is an `address_mismatch` scrape miss — fail
closed, so ATTOM populates the property profile instead of silently substituting the wrong unit's
data. Unit-less (single-family) subjects are unchanged. Additionally, a `FOR_RENT` listing no
longer populates `currentListPrice` with its monthly rent; rent routes through `rentZestimate` only.

**Rental vs sale decoupling (LOA-3129).** `PropertyDetails`, `ConsolidatedProperty.listing`, and
`property_data_results` now carry `isListedForRent` (bool) and `askingRent` (monthly rent amount)
as separate fields from `isListedForSale`. A for-rent listing sets `isListedForRent = true`,
`isListedForSale = false`, `currentListPrice = null`, and puts the monthly rent in `askingRent`.
An empty status stays unknown for both flags. The same treatment applies to Redfin for-rent pages.
`askingRent` is stored in `property_data_results.asking_rent` (migration `0200`), a new column
distinct from `monthly_rent` (which records what the borrower pays at their current address).
</Accordion>

<Accordion title="SerpApi / Zillow URL finder (ZillowUrlFinderService)">
Env `SERPAPI_KEY`, `serpApiUrl = https://serpapi.com/search`.
`findPropertyUrl(input, site = "zillow" | "redfin")` resolves a Zillow or Redfin detail URL via
a two-stage discovery path for Zillow, and the existing SerpApi path for Redfin.

**Zillow URL discovery (LOA-3243)** runs inside `resolveZillowProperty`, which is the common
helper for subject, borrower, and every REO lookup. On each lookup it first attempts the direct
Zillow address-search path, then falls back to SerpApi:

1. **Direct Zillow search (primary).** `buildZillowSearchUrl` constructs
   `https://www.zillow.com/homes/<street>[-UNIT-<unit>],-<city>,-<ST>-<zip>_rb/`.
   `HasDataService.getPropertyDetailsForDiscovery` makes one no-retry request and validates
   the response strictly — checking street number, street name (`compareStreetIdentity`),
   unit match, and locality (ZIP5 first, then city+state). A mismatch or
   unrecognized shape falls through to SerpApi. The direct path is skipped for unit
   formats the search cannot reliably handle (e.g. `1/4`, `3-B`, `Lot 5`, `bldg 2 apt 5`,
   or a unit after a comma) and when the budget is exhausted (max 6 attempts and 120 s
   cumulative per run, each attempt cut off at 45 s).
2. **SerpApi fallback.** When the direct path returns nothing or is skipped, the existing
   Google search runs: filters to `site:zillow.com/homedetails`, matches street-number +
   city + unit in titles. Returns `null` on no exact match.

Each lookup emits one `property_data_url_discovery` INFO event. A `serpapi_error` reason
distinguishes an HTTP error or timeout from a genuine miss. There is no per-lender flag —
direct search runs for every lender.

**Redfin URL discovery (LOA-3270)** now runs a HasData direct listing search first, with SerpApi as fallback. `HasDataService.getRedfinListingDetails` executes a Redfin listing-search endpoint call and validates the top result by address (street number, street name, unit, ZIP5 or city+state). When the direct path is skipped or returns nothing, `findPropertyUrl(input, "redfin")` falls back to a Google search (`site:redfin.com`, detail path `/home/`) and scrapes the URL via `getRedfinPropertyDetails`. The Redfin direct path shares the same per-run budget as the Zillow direct path.

Since LOA-1745 (#2695), when the subject address includes a unit, the unit is included in the
SerpApi query so the specific unit's zpid is ranked above the building-level record.
</Accordion>
<Accordion title="Mashvisor (MashvisorService) — rental market data">
Env `MASHVISOR_API_KEY`. Provides short-term rental (STR) and long-term rental (LTR) market data for the subject property via three endpoints defined in `mashvisor-request.ts` (LOA-1579):

| Endpoint | `zip` param key | Sends lat/lng |
|---|---|---|
| `rento-calculator/lookup` | `zip_code` | Yes (ATTOM coords) |
| `rento-calculator/list-comps` | `zip_code` | Yes |
| `long-term-comps` | `zipcode` | No |

The `rento-calculator` endpoints use `zip_code`; `long-term-comps` uses `zipcode`. Sending the wrong key causes the vendor to return city-level comps instead of ZIP-scoped ones (LOA-1579 probe confirmed: `zipcode` key on a rento endpoint drops in-ZIP comp count from 30 to 0).

Lat/lng are sent for the two rento-calculator endpoints only when the ATTOM coordinates are finite, in-range, and not the `(0, 0)` null-island sentinel (a failed geocode emits `(0, 0)`, and forwarding it as the strongest match signal would corrupt address matching).

**Coordinate resolution via ATTOM `basicProfile` (LOA-1899).** `mashvisorFetch` now calls `attom.getBasicProfile(address)` first to resolve the subject property's lat/lng, falling back to the `ConsolidatedProperty.coordinates` already in state if the `basicProfile` lookup fails or returns `(0, 0)`. The prior behavior forwarded the coordinates from the `ConsolidatedProperty` that had been built earlier in the same `fetchProperty` super-step — but because `fetchProperty` and `mashvisorFetch` run in parallel, the `ConsolidatedProperty` coordinates could be populated from a data source that arrived after Mashvisor was already called (the original fix in #2861 added the guard but it never fired because the value it guarded was always `(0, 0)` at call time). The `basicProfile` endpoint is the minimal ATTOM shape used solely for coord resolution; its owner/mortgage/assessed/tax payload must not be forwarded to `ConsolidatedProperty` (it is a narrowly typed internal artifact).

URL shaping and all per-endpoint config live in `mashvisor-request.ts`, which is also imported by the `scripts/mashvisor-capture.ts` capture harness so the harness cannot drift from production.

NYC borough normalization: when `state` is `NY` or `New York`, borough names (`Brooklyn`, `Bronx`, `Queens`, `Staten Island`, `Manhattan`) are rewritten to the city value `New York` for the Mashvisor lookup. This rewrite is **New York State only** — real cities named Manhattan or Brooklyn exist in other states (Manhattan KS, Brooklyn OH) and must not be rewritten.

LTR comps are capped to the 10 nearest properties (LOA-1869) so the median LTR rent computed downstream is derived from the nearest-neighbor set rather than a noisy market-wide slice.
</Accordion>
</AccordionGroup>

## ATTOM unit scope detection (LOA-2724)

When the subject property includes a unit number, ATTOM may return building-level records instead
of unit-level records — for example, an `ExaStr` (exact street, no unit) `matchCode` — producing
property facts, ownership, and sales history that describe the whole building rather than the
borrower's unit. `resolveAttomUnitScope()` (`consolidation/unit-scope.ts`) detects this condition
and stamps the consolidated record so downstream consumers can surface it to reviewers.

**Scope types:**

- `PropertyDataScope` — `"unit"` (ATTOM resolved the specific unit) or `"building"` (ATTOM resolved the building or a wider parcel). Absent when the subject has no unit (`undefined`).
- `BuildingScopeReason` — one or both reasons can fire independently:
  - `"attom_did_not_resolve_expected_unit"` — the loan names a unit but at least one contributing ATTOM record either has no `situsUnitValue`, a street-only `matchCode` (`ExaStr`), or a unit token that differs from the expected unit.
  - `"attom_multi_parcel_record"` — the ATTOM response carries a `multiApn` value, indicating a building-spanning parcel regardless of whether a unit was requested.

**How scope is determined:** `resolveAttomUnitScope()` iterates the `property[0]` entry of every contributing ATTOM endpoint (all except `propertyDetail`, which is fetched but never merged). A record `confirmUnit` only when it has a non-street `matchCode` **and** its `situsUnitValue` equals the expected unit token. The function fails closed: a single non-confirming record marks the whole consolidation `"building"`. Both reasons can accumulate on the same response.

**Effect on the consolidated record:**

- `ConsolidatedProperty` gains `dataScope?: PropertyDataScope` and `dataScopeReasons?: BuildingScopeReason[]`.
- When `dataScope === "building"`, `describeBuildingScope()` pushes a human-readable flag into `consolidated.flags[]` explaining which unit was expected, which (if any) ATTOM resolved, and the raw `matchCode` values.
- Sales-history red flags in the Property-Red-Flags agent are gated on unit scope: flags that compare sale prices against the subject unit's value are suppressed for building-scoped records.
- `computeCoverageBuckets` receives `dataScope`; when `"building"`, the `unitScope` bucket is set to 0, reducing `attomBucketsPercent` by one-tenth.

<Note>
`"building"` scope does not suppress other Property-Data coverage buckets or ATTOM data. It is an advisory annotation: the consolidated property profile is still populated from ATTOM, but reviewers and downstream rules can see that the facts describe the building, not the unit.
</Note>

## ConsolidatedProperty and coverage metrics

`attomExtractAll(attomData)` extracts ids (attomId/apn/fips), coordinates, property facts (beds,
baths, living sqft, year built, stories, condition, exterior, PUD), lot (size, zoning, pool),
ownership (owners, absentee, vesting type, trust indicator, owner-occupied resolution), mortgages,
title, liens (foreclosure + preforeclosure), sales history, assessment history, tax history, and
AVM valuation.

**ATTOM owner type — explicit individual (LOA-2689).** `property_data_results.owner_type` previously stored `"corporate"` or `null`, making an owner ATTOM identified as an individual indistinguishable from one ATTOM did not comment on. The consolidator now records the provider's exact `Y` or `N` corporate indicator on each owner entry (`corporateIndicator`). The stored `owner_type` resolves as `"corporate"` for Y, **`"individual"`** for N, and `null` when ATTOM is silent. The consolidated `corporate` boolean used by red-flag rules is unchanged.

**ATTOM preforeclosure fix (LOA-3319).** The preforeclosure request was previously sent to a dead path keyed by address. It now calls `GET /propertyapi/v1.0.0/preforeclosuredetails?attomid=<id>` — id taken from the expanded profile or the basic profile — as a sequential second wave after the address batch. With no recognised id, no request is made and coverage is false. A 200 response is coverage only when `property.PreforeclosureDetails` carries object `Default` and `Auction` arrays. The consolidator reads `property.PreforeclosureDetails`, lender from `lenderNameFullStandardized`, opening bid from `recordedAuctionOpeningBid`, and drops 0 and negative amounts before building lien entries.

**ATTOM trust indicator and entity-owner resolution (LOA-2737).** Owner names and the trust
indicator now resolve from one ordered list of owner blocks so the name source and indicator source
cannot drift apart. The trust indicator sits on the owner _entry_ at
`assessment.owner.owner1.trustIndicator` with the literal value `"Name is a Trust"`; reading
the parent block or comparing against `"Y"` (both previous bugs) resolved permanently `false` and
silently suppressed the `if_entity_vesting` document requirement for all trust-vested loans.
The owner block selection now requires a block that actually names an owner — a block can carry an
indicator with no name, and selecting it would satisfy the ownership guard while producing an empty
owner list.

Entity owners are now cross-checked against the vesting deed: a named party on the deed that
vested title in a trust or LLC is a legitimate match even when the ATTOM owner field shows the
entity name rather than the borrower's name. USPS street-suffix normalization (e.g. "Way" ≡ "Wy")
is also applied to suppress false-positive `SUBJECT_OWNER_BORROWER_MISMATCH` findings where
address variations differ only in suffix abbreviation.

**Assessment history selection (LOA-3343).** `latestAttomAssessment()` (`consolidation/propertyConsolidator.ts`) selects the current assessment as the record with the highest `tax.taxYear` from ATTOM's assessment history array, because ATTOM does not guarantee order. Undated records rank last; ties keep source order. This means `assessmentCurrent` always reflects the most recent tax year on record, not the first entry ATTOM returns.

`computeCoverageBuckets()` produces 10 buckets — `ids`, `coordinates`, `ownership`, `mortgages`,
`assessmentCurrent`, `assessmentHistory`, `salesHistory`, `propertyFacts`, `lot`, `freshness` — and
`attomBucketsPercent = round(present / 10 * 100)`. Missing buckets are the ones with a value of 0.

## Persistence

The runner (`property-data-graph-runner.ts`), not the graph, writes these tables in
`src/database/schema/property-data.ts`:

<ResponseField name="property_data_runs" type="table">
`id`, `audit_run_id`, `loan_id`, `document_id`, `rerun_allowed` (default false), `created_at`.
</ResponseField>

<ResponseField name="property_data_raw" type="table">
Full JSONB payloads: HasData/listing/valuation/rent/proximity, `consolidated_subject`,
`consolidated_borrower`, `consolidated_reo`, Zillow URLs, and ATTOM payloads. The consolidated blobs
carry `naturalHazard` as a discriminated union that is never omitted (`{coverage:true,...}` or a
`{coverage:false, fetchedAt}` sentinel). `hasdata_responses` (JSONB, migration `0157`) stores every
raw HasData API response for the run, keyed by operation (`zillow/property`, `redfin/listing`,
`redfin/property`, etc.) with `accepted: true` on the response the run ultimately used.
</ResponseField>

<ResponseField name="property_data_results" type="table">
One row per property, with a `property_type` CHECK of `subject | current_home | investment`. Carries
the consolidated facts (address, coordinates, beds/baths, AVM, last sale, owner,
photos), coverage metrics (`subject_coverage_percent`, `borrower_coverage_percent`,
`*_missing_buckets`), and `county_fips` as TEXT (leading-zero-safe). `estimate_source` (TEXT,
migration `0157`) records which data source produced the property's valuation estimate
(`zillow`, `redfin`, `attom`, or `null` when no estimate resolved). `estimate_low` and
`estimate_high` (numeric, migration `0178`) store the low/high bounds from the winning estimate
source; `null` for Zillow Zestimate (no range supplied) and for any source that returns no
bounds. `listing_sources` (jsonb, migration `0178`) stores the `ListingSources` map from
`mergeCandidates` — each key is a listing group name and the value is the source that won it
(e.g. `{"currentListing":"redfin","estimate":"zillow"}`). `null` on rows written before
LOA-3272. `is_listed_for_rent` (boolean, default `false`, migration `0200`) and `asking_rent`
(numeric, nullable, migration `0200`) record the rental listing status and monthly asking rent
for each property row (LOA-3129); `asking_rent` is distinct from `monthly_rent`, which records
what the borrower pays at their current address.
</ResponseField>

<Warning>
With multi-borrower support (LOA-3123) a joint application now produces **one `current_home` row per
borrower residence** rather than one row for Borrower 1 only. A co-borrower's row is labelled
`Current Home (Borrower 2)` in the portal. REO rows are `"investment"`. The subject row is
`"subject"` (`source_order: 0`); rows are persisted whenever borrower data was fetched, regardless
of loan purpose.
</Warning>

## `PropertyDataResponse` — `locationType`

`locationType?: string | null` was added to `PropertyDataResponse` in `shared-types@1.21.1` (LOA-1952). The field carries an Urban / Suburban / Rural classification derived by joining ATTOM's county FIPS + census tract against USDA's RUCA reference table. Two distinct absent states:

- `null` — the field was never measured (a row written before the feature shipped).
- `"Unknown"` — the classifier ran but could not resolve the property's identifiers to a census tract.

The two states are deliberately distinguishable. `null` is permanent for any row whose consolidated blob was absent when the producer wrote it, not purely a legacy state — every property type writes this from its own blob.

<Note>
The `flood_zone` column was removed end-to-end (migration `0086`, PR #4319 / LOA-2175): the
`property_data_results.flood_zone` column was dropped, the `FemaFloodZone` extractor type and
`floodZoneFromHazard` helper were deleted from three write sites, and `PropertyDataResponse.floodZone`
was removed from `shared-types@2.0.0`. The underlying ATTOM natural-hazard payload (`naturalHazard`
jsonb in `property_data_raw`) is unaffected; only the denormalized column and its DTO projection are gone.
</Note>
