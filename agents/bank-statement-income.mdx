The `bankStatementIncome` agent is a 9-node compiled LangGraph that implements the bank-statement income analysis pipeline — extraction, validation, categorization, fraud detection, deposit classification, anomaly detection, income-trend analysis, and aggregation — in a single blob-free `Annotation.Root` graph. It replaces the monolithic `postProcess` function in the legacy `bank-statement.processor.ts` (PR #2865, LOA-1711).

## The 9-node graph

The graph follows the legacy `bank-statement.processor.ts` extraction-loop execution order exactly. Edges are all unconditional; `aggregate` is the terminal node:

```text
prepare → extractStructured → validate → categorize → detectFraud →
classifyDeposits → detectAnomalies → checkIncomeTrend → aggregate
```

State is carried in `BankStatementIncomeStateSchema` (`buildGraph.ts`) — a **blob-free** `Annotation.Root` (no PDF bytes, buffers, or paths in state channels). PDF bytes, the per-file s3Key span map, and the PDF-access closure are injected through `buildGraph(deps)`, never through state or `config.configurable`.

<AccordionGroup>
<Accordion title="prepare">
Reads `borrower_files` from the DB to resolve the run's `lenderId`, `loanId`, and `borrowerType`, then emits a `PreparedRunRef` (ids and scalar status only — no blobs).
</Accordion>
<Accordion title="extractStructured">
Calls `structureWithReducto` (injected via `deps.structure`) with the closure-held `pdfBuffer`. Returns the full `ExtractionResult` (statements + metadata) and writes `statements` onto state.
</Accordion>
<Accordion title="validate">
Runs `ValidationService.validate` against the extracted statements and writes a `ValidationResult` onto state. Pure; no I/O.
</Accordion>
<Accordion title="categorize">
Calls `CategorizationService.categorizeStatement` (Plaid PFC enrichment) for each statement. Writes `enrichments`, `categorized`, `failed`, and `skipped` onto state.
</Accordion>
<Accordion title="detectFraud">
Runs PDF-integrity and font-consistency fraud checks. PDF bytes arrive via `deps.readPdfBySourceKey(s3Key)`, which resolves the worker's already-downloaded temp file — **not** an S3 re-fetch. Attribution is file/s3Key-keyed, not statement-keyed (one PDF can produce multiple statements). Returns `fraudFindings`.
</Accordion>
<Accordion title="classifyDeposits">
Classifies each extracted deposit (`deposit_classification`) by `borrowerType`. Pure; no I/O.
</Accordion>
<Accordion title="detectAnomalies">
Runs large-deposit, anomaly, income-basis (audit P2), and business-type overlay analysis via `AnomalyDetectionService`. Threads `category_detailed`, `income_excluded_reason`, and — when a business-type profile is active — the profile's p2p treatment and band thresholds into each detection pass.

Also receives `rejectedPeriods` from the extraction state — statement periods the model identified as incomplete or out-of-window (mapped from `extraction.rejected_periods` to `{ accountNumberMasked, coveredMonths }`). `AnomalyDetectionService` uses this list to exclude rejected periods from the anomaly window, so a statement that the extractor rejected does not silently dilute income or fire spurious anomaly findings.

**Page geometry removal and `qualification_period_mismatch` (LOA-2655, migration `0038`).** Previously, statements whose stored page numbers sat outside the PDF's actual page count were rejected outright, which silently dropped the oldest months in multi-month PDFs. This check has been removed. The rejection list (`rejectedPeriods`) now comes exclusively from the extractor's own window judgment, not from page geometry. Instead, when the number of income months the graph derived differs from the reviewer's `income_qualification` setting (in either direction), the agent emits a non-blocking `qualification_period_mismatch` warning finding (`severity: "warning"`, `statementId: null`) with an evidence payload carrying `included_months` and `rejected_months`. The finding appears in the portal's **Issues Found** panel under the **Program Rules** chip and is dismissible across recompute runs. `EXTRACTION_CONTRACT_VERSION` was bumped from 1 to 2 as part of this change; the Redis extraction checkpoint invalidates stale payloads automatically.
</Accordion>
<Accordion title="checkIncomeTrend">
Checks the month-over-month income trend (audit F2). Threads `incomeExcludedReason` and `borrowerType` through the `toTrendStatements` adapter so the eligibility matrix is borrower-type-aware. No DB access — all inputs come from graph state.

Income is bucketed by **sequenced month** derived from `statement-month-sequence.ts` (LOA-8ae7017
/ LOA-2280), not by per-statement midpoint heuristic. The sequencer anchors once per account on
the first statement and assigns each contiguous successor the next calendar slot — N contiguous
statements occupy N consecutive months by construction. A gap advances the cursor by the cycles
the elapsed time implies, so genuine missing months still fire. Parallel `detectAnomalies` uses
the same sequencing so the two nodes agree.

The divisor for qualified monthly income is the count of **distinct sequenced months** across the
included statements. Every documented month appears as a zero-filled row when it has no eligible
deposits, so `months_analyzed == monthly_data.length == included_months` by construction.

<Note>
Before LOA-2280, month identity came from `getRepresentativeMonth` (calendar month containing the
statement period’s midpoint). On an account whose cycle closes mid-month, consecutive periods
collapsed onto one label — e.g. `2025-09-17–2025-10-16` and `2025-10-17–2025-11-15` both
labelled October — producing false “Statement missing” rows, an under-counted divisor, and
overstated qualifying income (~20% on the reported file). Both API and app implementations
derive month identity from the same sequencer; a cross-package sync spec (`statement-month-
sequence-sync.spec.ts`) keeps them aligned.
</Note>
</Accordion>
<Accordion title="aggregate (terminal)">
Assembles the `AggregateWritePlan` — per-table write-batches for `borrower_files`, `bank_statements`, `transactions`, `income_filters`, and `findings` — and returns it. The node itself performs **no DB write** (IC-3/D9). Two additional detectors run inline inside aggregate's glue wrapper (NOT registered StateGraph nodes, so the topology stays at 9 nodes): `detectBalanceFindingsNode` (NSF + negative-balance at extraction time) and `detectContinuityFindingsNode` (balance-continuity fraud). Their outputs thread into `AggregateInput` directly.

A third inline pass, `detectReciprocalCounterparties` (LOA-2314), also runs inside aggregate and persists `reciprocal_counterparty` findings (severity `info`, `statement_id = null`) via the write plan. The `FINDING_TYPE_SET` and `VALID_FINDING_TYPES` allowlists are kept in sync by a drift spec.

<Note>
`reciprocal_counterparty` is currently **switched off**: the detector still runs and still persists findings, but the finding type has been removed from the portal Issues Found allowlist and the export Risk Summary catalog (#4030). It surfaces in the AI summary narration and the income editor (which bypass the allowlists) but nowhere else. Restoring both allowlist entries turns it back on.
</Note>

`collectLegs` applies two gates before any name enters the candidate set (#3905):
- **Non-person marker gate** — names containing institution/entity/transfer vocabulary (`bank`, `credit union`, `chk`, `sav`, `confirmation`, `transfer`, `llc`, `inc`, `corp`, etc.) are dropped immediately. A related party is a person; an institution or boilerplate name cannot be one.
- **Spending-rail gate** — legs whose `category_detailed` matches a Plaid PFC purchase primary (e.g. `FOOD_AND_DRINK_*`, `GENERAL_MERCHANDISE_*`, `TRANSPORTATION_*`) or whose `category` matches a spending word are dropped. This catches a clean merchant name that no entity marker can reach. `RENT_AND_UTILITIES_*` is deliberately excluded — rent to a related-party landlord is a plausible reciprocal. Both gates fail-open: a missing or null category never drops a leg.

Both gates are advisory-only deny-lists (which income/liability passes forbid for safety), acceptable here because the `reciprocal_counterparty` finding is `info` severity: it moves no income and writes no disposition, so a false reject drops only a finding. To support the spending gate, `ReciprocalRow` now carries `category` and `categoryDetailed`, populated by both callers — the extraction adapter and the service recompute path.

The `bank_statements` write-plan rows now carry `source_page_start` and `source_page_end` (migration `0328`) when the extraction model reported them. These are 1-based page numbers validated by `isValidPdfPageNumber` (from `loanlight-shared/bank-statement/pdf-page`) before entry into the write plan — out-of-range or non-integer values are dropped rather than persisted.
</Accordion>
</AccordionGroup>

## Write plan and persistence

`aggregate` produces an `AggregateWritePlan`. The **worker** (`bank-statement.processor.ts::analyzeWithGraph` → `writeResults`) is the sole DB persister. No node may write to the DB — any node that takes a `DrizzleDB` uses it read-only (tenant guards, basis lookups).

The worker's `writeResults` persists the same five table families: `borrower_files`, `bank_statements`, `transactions`, `income_filters`, and `findings`. The graph replaces the deleted `postProcess` function; everything after `writeResults` is unchanged.

## Reducto extraction checkpoint (LOA-2517)

Each file's validated `ExtractionResult` is persisted to Redis keyed by `(borrowerFileId, sourceFileHash, EXTRACTION_CONTRACT_VERSION)` before `writeResults` runs. On a BullMQ retry, a checkpoint hit serves the cached result and skips the paid `structureWithReducto` call; only the not-yet-checkpointed file(s) re-extract. The TTL is bounded: at least `BANK_STATEMENT_LEDGER_DEADLINE_MS` (120 min) and at most `PII_BOUND_MS` (3 h). Keys are deleted after `writeResults` succeeds to tighten the PII window; TTL self-expiry is the backstop.

The checkpoint uses a dedicated ioredis client. Without it, a transient Reducto slowdown on a single file of a batch audit would fail the entire audit and re-bill Reducto for work it had already done, because a single `writeResults` after the loop meant there was nothing to resume from.

Two additional Datadog monitors cover extraction retries and budget exhaustion (added in LOA-2517; monitor names are in `observability/datadog/`).

## LangSmith tracing (LOA-2653)

`bankStatementIncome` emits a LangSmith trace on every run. The trace metadata carries only `{ auditRunId, agentType }` — no borrower-derived fields — with the shared anonymizer wired as `hideInputs`/`hideOutputs` and bank-statement PII keys in `PII_KEY_DENYLIST` as defense-in-depth. The Octy audit-run modal surfaces a **Bank-Statement-Income** card for these runs. Tracing is controlled by the `LANGSMITH_TRACING` environment variable.

## NSF / overdraft finding behavior

### Count as the headline (LOA-2313)

`detectNsfFinding` now describes the finding by the **total transaction count**: `"N NSF/overdraft transactions detected"` (singular when `N === 1`). Earlier versions embedded a sample of occurrence dates in the description; those dates moved exclusively to `evidence.sample_transactions`. Every surface that renders an `nsf_overdraft` finding derives the display sentence from `evidence` via `nsfDescriptionFromEvidence` — `distinct_days` is read first (see below); `count` is the fallback. Persisted rows written before LOA-2313 retain their stored description; only the append-recompute path rewrites one.

### View Transactions link (#4030)

`nsf_overdraft` and `large_deposit` rows now carry a **View Transactions** link in the Issues Found panel. Clicking it applies the matching transactions filter and scrolls to it. Both filters already existed in `INCOME_STATUS_OPTIONS`; the link is a pointer, not a separate definition of which transactions match. The link renders once per finding group, never per member row.

<Note>
A "View Transactions" link on a `large_deposit` row can land on an empty table if the finding was written before `evidence.transaction_id` existed on that row. The link renders on finding type alone; no per-finding reachability check exists yet.
</Note>

### Same-day occurrence collapsing per lender (LOA-2315)

A per-lender `nsf_same_day_occurrence` feature flag controls whether multiple NSF fees on the same calendar day are counted as **one occurrence**. When enabled:

- `detectNsfFinding` collapses same-day transactions before counting. The description changes to `"The account had NSF/overdraft activity on N day(s)."` — matching the phrasing of the adjacent `negative_balance` finding.
- `evidence.distinct_days` carries the collapsed day count (the discriminator for `nsfDescriptionFromEvidence`).
- `evidence.count` always carries the **raw transaction total**, regardless of the setting, so historical comparison is preserved.
- `distinct_days` is excluded from the reviewer-feedback signature: the key's presence or absence changes with the admin toggle, while `count` and `sample_transactions` remain the stable identity.

Collapsing happens over the transaction set handed in at the time of the call (post-exclusion `included` set for recompute; full statement set for the graph node) — never before exclusion filtering.

The flag is registered in the admin Flags tab (`KNOWN_FLAGS` + `KEY_MAP` + `FeatureFlags`) and resolves `false` when no `lender_feature_flags` row exists.

## Parity with the legacy pipeline

The port restores several extraction-time finding categories that the legacy hard-swap (T11) had dropped:

- **NSF and negative-balance** (`detectBalanceFindingsNode`): reuses `detectNsfFinding` / `detectNegativeBalances`, the same pair the append/recompute path uses.
- **Balance continuity fraud** (`detectContinuityFindingsNode`): reuses `FraudDetectionService.checkContinuity`. Its input is sourced from raw `ParsedStatement` balances (pre-`?? 0` coercion) via the `deps.continuityStatements` closure, so the legacy unparseable-balance warning remains reachable.
- **Income-basis veto** (P2 + F2): credits flagged `incomeExcludedReason ∈ {refund, self_transfer, family_transfer, account_transfer}` drop from the income basis even when `deposit_classification === "income_deposit"`, mirroring `bank-statement.processor.ts` post-#2860.

### Finding rule changes (#4030)

**Balance Rollover message rewritten.** `fraud_continuity` findings now display the account and both balances:

> Balance mismatch between statements ending in 2345: Dec 2025 (ending balance: $1,000.00) → Jan 2026 (starting balance: $800.00) — $200.00 difference.

The sentence is **derived from evidence on read**, not from the persisted `description` column, so existing findings read the new message immediately without a reprocess. `continuity-description.ts` (API) and `continuity-summary.ts` (app) are a sanctioned cross-package mirror pair, kept in sync by `continuity-summary-sync.spec.ts`.

**`validation_balance_mismatch` renamed to "Statement Transactions Mismatch".** The finding type key is unchanged; the display label and message are new:

> Statement transactions do not reconcile for the statement ending in 2345: Jan 1 – Jan 31, 2026 (starting balance: $1,000.00) + 4 transactions (+$500.00) = $1,500.00 expected, but the ending balance is $2,000.00 — $500.00 difference.

The message names the **statement period** (not a month label), which is correct at extraction time before `sequenceStatementMonths` has run. Like the rollover message, it is derived on read (`balance-mismatch-description.ts` / `balance-mismatch-summary.ts`).

**`negative_balance` added to the export Risk Summary catalog.** `negative_balance` findings have been produced since LOA-1688 and rendered in the portal, but had no export catalog entry. Files with negative-balance days now include them in the partner Risk Summary.

**`fraud_pdf_integrity` severity changed to critical.** Embedded JavaScript and overlay-capable annotations are active tamper mechanisms; the finding was already `critical` at the signal level but the finding boundary had flattened it to warning. Font-consistency (`fraud_font_consistency`) remains a warning.

**Three producerless export checks removed.** `income_classification`, `llm_source_mismatch`, and `validation_duplicate` were present in the export risk catalog but no code writes those finding types, so they produced a permanent misleading PASS on every file. They are removed from the catalog. The four types remain in `VALID_FINDING_TYPES` and the DB `CHECK` constraint (an `ALTER TYPE` to tighten them requires verifying no legacy rows exist in production). They are now named exemptions in the catalog guard.

**Voided checks and `refund` display identity (LOA-2686):** A voided check is detected by the VOID token **together with check context** (either order, bounded window), e.g. `Void Official Check#` / `Voided Ck #`. When matched, the credit is stamped `income_excluded_reason = "refund"` — re-using the existing `refund` disposition rather than adding a new reason code. `refund` is now also a **reviewer-selectable dropdown entry** and has a visible display identity alongside `SELF_FAMILY_TRANSFER` and `ACCOUNT_TRANSFER`. Selecting "Refund" stamps `income_excluded_reason` directly (not a category override), matching the LOA-2543 disposition-stamp pattern. The v2 categorization pipeline picks up the same VOID/Voided detection via `REFUND_SHAPE_PATTERN`.

**Account selection — which accounts feed income (LOA-2657):** When an upload contains multiple accounts, the graph determines which accounts contribute to qualifying income before aggregating. The decision is topology-first, materiality-second:
- Accounts with **staggered coverage** (one starts where the other ends) are treated as one continuous stream — interpreted as a bank switch.
- Accounts with **concurrent coverage** (overlapping months) are compared over their shared window. An account is **immaterial** and dropped when its deposits represent less than 10% of the window total, or when it has deposits in fewer than a third of the shared months. Concurrent material accounts are **never summed**; the account with the larger income sets the qualifying figure, and each other account is presented as its own worksheet contributing nothing to the total.

`bank_statements.income_inclusion_override` (boolean, nullable, migration `0046`) lets a reviewer override the auto-detected inclusion decision. The cross-account decision is recorded as an `account_selection` finding type (migrations `0047`/`0048` — expand/contract pair widening `finding_type_check`).

**P2P sender names without "from" (LOA-2683):** `extractP2pSenderName` previously anchored on `/\bfrom\b/` only, so banks that print the sender directly after the rail (`ZELLE <NAME> <phone>`) produced no sender name and the family/self exclusion never fired. A rail-anchored parse (Zelle, Venmo, Cash App, PayPal, Popmoney, QuickPay) is now applied alongside the existing `from` parse, with a newline-tolerant anchor and middle-name reconstruction. The new parse is gated to `direction === "inbound"` — the outbound and `descriptionFirst` expense paths are unchanged.

**Balance-rollover continuity keyed on account (#4030, supersedes LOA-2690):** `detectContinuityFindingsNode` previously keyed continuity on the printed mask alone, which caused false-positive `fraud_continuity` criticals whenever one mask covered two accounts (e.g. a credit union issuing a business checking and a primary share account under the same member number). The account key is now built on two components:

1. **Shared account identity** (`accountIdentityBucketKeyOf` from `statement-month-sequence.ts`): canonical last four, composing `bank|suffix` only where the same suffix is observed across multiple institutions. Two unrelated sub-accounts with the same last-four get distinct keys; two renderings of the same account (`****6177` / `XXXX6177`) get the same key.
2. **Printed account heading** — appended to the key **only where one identity carries two or more distinct headings**. This scoping is load-bearing: `account_name` is LLM-extracted and nullable. Appending it unconditionally would give a statement whose heading failed to extract its own singleton bucket, causing the check to return `insufficientData` and silently go dark. The same key is handed to `sequenceStatementMonths` so the month labels the findings print agree with the account grouping.

A companion guard, `monthsAreConsecutive`, was added to `checkContinuity` to prevent pairing two statements of the same calendar month (which can occur once an interposed statement from another sub-account is correctly moved to its own bucket). The `account-sequence.ts` module introduced in LOA-2690 was deleted; `continuityAccountKeyOf` in `detectContinuityFindings/node.ts` replaces it.

### Portal upload defaults

Two portal defaults changed in the same fix (LOA-2280):
- **Upload modal** — `EMPTY_BANK_STATEMENT_CONFIG.borrowerType` is now `business` (was `personal`). The modal and its reset path both derive from this constant, so the Business-only Expense Factor and Ownership inputs render by default (prefilled at 50% / 100%).
- **Transactions table** — the initial filter on the bank-statements explorer, statement-analyzer tab, and `/results` income editor is now **All Deposits** (credits only). Clearing the chip falls back to All Transactions.

### PFC category corrections and counterparty ledger

Two post-categorization passes run inside the `categorize` node after Plaid PFC enrichment, in order (LOA-2197). Both apply to **credits only** and skip any row whose `category_detailed` is disposition-gated (i.e. a code the income-exclusion pass keys on, such that rewriting it would silently re-admit excluded income).

### 1. Deterministic corrections (`applyPfcCategoryCorrections`)

Gated on the `pfc_corrections_enabled` lender feature flag (opt-in, default off — see
[Feature flags](/lender-config/feature-flags-and-entitlements)).

Five structural rules forcibly override any Plaid category for credits that match a known pattern. When a rule fires, `transactions.category_rule` is set to the rule name and `transactions.category_detailed_vendor` preserves the original Plaid detailed code for display.

| `category_rule` | Pattern | Forced `category` / `category_detailed` |
|---|---|---|
| `wire` | `\bwire\b` in the description, but **not** exclusively inside an ACH payer name field | `TRANSFER_IN` / `TRANSFER_IN_WIRE` |
| `counter_credit` | Counter-credit and branch-deposit keywords (e.g. `counter credit`, `over-the-counter`, `teller deposit`) | `TRANSFER_IN` / `TRANSFER_IN_DEPOSIT` |
| `corporate_ach` | ACH structural marker + CCD or CTX SEC code | `TRANSFER_IN` / `TRANSFER_IN_DEPOSIT` |
| `payroll` | ACH consumer entry class (`PPD`/`COR`) + company identifier that matches the known payroll-originator list **and** a payroll-token in the entry-descriptor field position (LOA-2548) | `PAYROLL` / `INCOME_WAGES_SALARY` |
| `rental` | Credit from a known rental/payout platform originator (e.g. Airbnb Payouts) in the ACH company-identifier field (LOA-2548) | `INCOME_RENTAL` / `INCOME_RENTAL_INCOME` |

The `payroll` rule requires three things together — a consumer entry class, a company identifier from the known-originator registry, and a payroll token in the entry-descriptor position (not anywhere in the description). This prevents mislabelling ACH transfers from companies whose names contain payroll-adjacent words. The rule does **not** fall back to description keywords because `signature.ts::extractEntryDescriptor` returns `null` for ACH-shaped rows that do not expose their entry descriptor in the `DES:` field position; where the descriptor is unreadable, the rule does not fire.

The `rental` rule reads no rail — it is purely a payout-platform registry match on the ACH originator-ID field.

The `wire` rule includes a precision guard: a `wire` token that appears **only** inside an ACH payer name (e.g. a paycheck from `INSTEEL WIRE PRODUCTS`) is not treated as a wire descriptor. The guard reads the `ORIG CO NAME:` field by offset, not by text value, so a payer name that happens to print twice (once truncated in the prefix, once in full in the field) is correctly handled.

**FR-5 rung — sender naming and shape reading.** The `Online Transfer` rung (FR-5) in `CreditCategorizationV2` now derives the sender identity through a bank-agnostic parser (`transfer-sender.ts`) that strips the verb phrase, reference markers, masked account, and account-product phrase, leaving a clean sender string. The outcome depends on the sender shape:
- **Person-shaped sender** (name followed by an initial-like trailing discriminator): `Account Transfer — <name>`. The Self/Family disposition downstream keys on the name.
- **Organisation-shaped sender**: `Customer Payment — <name>`.
- **Only a masked account** (no printed name, e.g. `x0849`): `Account Transfer — x0849` (unchanged). Treating every online transfer as the borrower's own account had previously excluded valid third-party payments.

**R8 (own-account rail) runs above FR-5.** The borrower's own masked account number is an account identifier, never a "sender", so the own-account check fires before FR-5 assigns a sender string — preventing the borrower's own last-4 from being rendered as a person name.

**Positional (label-less) NACHA records** (anchor pattern `<Company> <Entry Descr> <YYMMDD> <Ind ID> <Ind Name>`) are now recognized as ACH credits regardless of bank (`positional-ach.ts`). These records may print the *receiving* account's mask rather than the payer — R4.4a, which handles these rows, is ordered above the own-account check to avoid misclassifying the receiving mask as a source.

**Receiver guard moved to the pipeline.** The old in-resolver `INDN:` check that caught echoed receiver names abstained the whole result and missed Chase's `Ind Name:` field. The guard now runs in `ladder.ts::applyResolverContext` (on every consumed result, including cache hits) and replaces an echoed receiver name with the structurally parsed payer instead of discarding the answer entirely. This fixed 377 production rows that had rendered a payee's own name as its own payer.

**Mechanism registry.** Afterpay, Affirm, Klarna, and Sezzle are BNPL processors — they settle merchant sales, never disburse consumer loans. The resolver's `Loan — <platform>` guess is replaced by a deterministic `Merchant — <platform>` mapping from the mechanism registry.

**Merchant Service settlements and CCD DEPOSIT rail (LOA-2764).** Two gaps caused unbranded payment-processor credits to land on a bare `Deposit` instead of `Merchant Settlement`. (1) `mechanism.ts::PROCESSOR_ENTRIES` did not include `merchant service` (singular), so the `Merchant Settlement` mechanism rung never fired for entries like `MERCHANT SERVICE MERCH DEP`. The singular token is added; the plural `merchant services` is deliberately excluded to prevent over-claiming a business whose name contains "Merchant Services". (2) `rail.ts::classifyRail` returned `counter_mobile` for entries whose entry type printed as `CCD DEPOSIT,` rather than `CCD ID:`, so the ACH rail was not recognised. Two patterns close this: `CCD DEPOSIT` joins `ACH_SEC_CODE_PATTERNS` and a leading `ACH Deposit` joins `ACH_DEPOSIT_RENDERING_PATTERNS` (leading-only, to avoid over-classifying a trailing mention). With both gaps closed, a row matching the mechanism registry is claimed structurally as `Merchant Settlement` with no resolver call.

**W2 resolver payroll evidence gate (LOA-2774).** A resolver `W2` proposal whose transaction group carries no payroll token in any descriptor is now demoted — the row rides the name-only ladder instead, and the demotion is logged at INFO (matching the `Rental Income` arm). The gate uses `classifyPayroll` with bureau stripping (`stripMatch`) to avoid a bureau name in the descriptor self-corroborating: `adp payroll` as a match entry is stripped whole, so `ADP Payroll Fee` (a charge *by* the bureau) does not count as payroll evidence. Structural `W2` from rule R17 is untouched. The memo persistence strategy was also corrected: `applyResolverContext` now returns two forms — `effective` (evidence-gated, answered for this group) and `storable` (ungated, persisted to the memo) — so a cached demotion never outlives the group that was demoted for it. The same fix applies to the `Rental Income` arm. Memo entries written before this fix that persist a `null` proposal continue to replay correctly by re-deciding against the replaying group's own evidence.

### 2. Counterparty ledger (`applyCounterpartyLedger`)

The counterparty ledger groups credits by **counterparty signature** — a versioned string key (prefix `v2:`) that identifies the originator by structural ACH or wire fields, not by free-text description. For credits whose signature is not yet in the per-file ledger, the pass votes the modal `category_detailed` across all that counterparty's credits in the file and seeds `counterparty_category_ledger` (migration `0289`).

On subsequent bank-statement runs against the same `borrower_file_id`, existing ledger entries are re-applied without another Plaid round-trip. `transactions.category_rule` is set to `'counterparty_ledger'` on rows corrected this way.

Source priority (highest wins, never downgrades a higher source):
1. `override` — a human-authored correction persisted in the ledger
2. `rule` — a deterministic `applyPfcCategoryCorrections` match
3. `plaid` — the majority-vote result from this run's enriched rows

<Note>
Rule-corrected rows (`category_rule != null` and not `'counterparty_ledger'`) are excluded from ledger seeding: they already have an authoritative category and should not block a future human override from writing a `source: 'override'` entry via the normal rank guard.
</Note>

## Concurrent batch handling and the backlog queue (LOA-2639)

Prior to LOA-2639 the `POST /api/v1/portal/bank-statements/enqueue` endpoint rejected any submission from a lender who already had a batch processing, returning `409` with a per-lender five-minute lock. That lock has been removed. Concurrent batches from the same lender are now absorbed by the existing BullMQ queue rather than rejected at the entry point.

**Concurrency facts:**
- `concurrency: 1` on the bank-statement BullMQ worker is a **per-task** setting, not fleet-wide. The API task runs at `desiredCount: 2, maxCapacity: 12`, so 2–12 bank-statement batches can process concurrently, including from one lender.
- Every write in the job is keyed by `borrower_file_id` — findings, transactions, `bank_statements`, `income_filters`, `transaction_category_overrides`, and `counterparty_category_ledger`. Two concurrent batches touch disjoint rows and are safe.
- Genuine deduplication (same `correlationId` / same `borrower_files` content-address) still rejects at the batch-UUID claim check; the removed 409 only blocked distinct submissions.

**`waiting_on` field (`lib/bank-statement/waiting-on.ts`):**

`resolveWaitingOn` derives a `BankStatementWaitingOn` discriminator from the row without clocks or thresholds:

| `waiting_on` | Condition | Portal label |
|---|---|---|
| `"dependency"` | `status === "queued"` (parked lane — Reducto circuit held) | Waiting to resume — this will continue automatically |
| `"backlog"` | `status === "processing"` **and** `processingStartedAt IS NULL` (queued, worker not yet claimed) | Queued — this will start automatically, and your upload is safe |
| `null` | All other states | Normal status label |

The `GET .../status` response carries `waiting_on` alongside `status`. The portal list view shows **"Queued"** (not "Processing") when `waiting_on != null`, so in-flight unstarted batches are never misreported as already running. One resolver drives the list view, the detail view, and the `/status` poll so they cannot disagree.

<Note>
The 30-second per-lender rate limit on `enqueue` was also removed in LOA-2639. The endpoint is still throttled at **10 requests per minute per request IP** (the class-level `ThrottlerGuard` on `BankStatementController`) — a content-agnostic rate limit that does not constrain distinct borrowers or loans submitting from different IPs.
</Note>

## Business-type-aware income analysis (LOA-3908, #3908)

When a reviewer names the borrower's business type at upload, a 31-profile registry adjusts how that file's deposits are read. The feature applies to the graph (ingestion) path and the service (recompute) path identically.

### Business type at upload

The bank-statement upload modal exposes a **Business type** type-ahead search over the 31 profiles' aliases and display names. It triggers at one character, uses a 200 ms debounce, and ranks matches: exact alias > prefix > substring. The matched alias is shown in parentheses. A free-text field for the description appears only when the reviewer selects **"Other"**.

The chosen values persist on `borrower_files`:

| Column | Type | Notes |
|---|---|---|
| `business_type_key` | `text`, nullable | The profile key (e.g. `"restaurant"`, `"consulting"`), or `"other"`. |
| `business_type_freetext` | `text`, nullable | Reviewer-supplied description when key is `"other"`. Bounded to 255 characters (migration `0044`). |
| `business_type_profile_version` | `integer`, nullable | Registry version at upload time, for drift detection. Seeded by migrations `0041`–`0043`. |

### Profile registry

The registry holds 30 named profiles plus the **"Other"** sentinel. Each profile declares:

- `aliases` — display names and search terms the type-ahead matches against.
- `expenseRatioBand` — the typical `{ min, max }` expense-to-revenue ratio for the business type. Used for cash-share deviation detection.
- `p2pTreatment` — how P2P credit transactions from this account are handled:
  - `"excluded"` (16 of 30 profiles): marks P2P credits `income_excluded_reason = "p2p_profile_excluded"`, which the income veto honours, so qualifying income drops.
  - `"needs_support"` (14 of 30 profiles): emits an advisory finding listing the P2P totals for manual review without excluding the income.

**"Other" is a sentinel, not a profile.** It resolves to no active profile; every overlay call site is a documented no-op. Output is byte-identical to the pre-feature baseline.

### Overlays the profile applies

**P2P treatment.** Applied by `detectAnomalies` during ingestion and by the recompute service path. When `p2pTreatment === "excluded"`, P2P credits are vetoed from income. When `p2pTreatment === "needs_support"`, they are flagged for review without exclusion.

**Profile-band large deposits.** A deposit that exceeds the profile's typical maximum (its `expenseRatioBand.max`-derived per-account P95 ceiling) is flagged as unusually large, scoped per masked account by that account's own income P95.

**Cash-share deviation.** A file whose observed cash share (cash deposits as a fraction of total income) sits outside the band the profile expects raises an advisory anomaly.

**Business-type narrative.** `buildProfileNarrative` supplies the detail view's `business_type_narrative` field and the advisory expense band shown in the portal's bank-statement income detail.

## Credit categorization v2 (LOA-2543, LOA-2659, LOA-2696)

A deterministic credit-categorization pipeline (`lib/bank-statement/credit-categorization/pipeline.ts`) runs as a **second categorization pass** after the primary Plaid PFC enrichment. It is wired behind the `ENABLE_CREDIT_CATEGORIZATION_V2` environment variable (strict `=== "true"`; CDK sets this to `"true"` in all environments, including prod, as of LOA-2705).

`CreditCategorizationV2Service.categorizeAndPersist(borrowerFileId)` is called from `bank-statement.processor.ts::writeResults` **after** the write transaction commits. It runs outside the transaction deliberately — the service makes sequential vendor calls (the OpenAI resolver) and holding a DB connection across them would pin it for minutes. DI failure of `CreditCategorizationV2Service` is now loud at boot (the `@Optional()` decorator was removed in LOA-2696).

**What it writes:** per-transaction `transactions.credit_category` columns plus `transactions.credit_category_source` (CHECK `structural | resolver | fallback | NULL`, migration `0045`) which records how the v2 answer was derived.

**`Interest` category income eligibility fix (LOA-2767, 2026-09-16).** The `ENABLE_CREDIT_CATEGORIZATION_V2` flag went fleet-wide on 2026-09-08. The v2 vocabulary maps Plaid PFC codes `INCOME_DIVIDENDS` and `INCOME_INTEREST_EARNED` to the category `Interest`. In v1 those same codes mapped to `"Investment Income"` — ineligible for both borrower profiles. In v2, `Interest` had been marked `{ personal: true, business: true }`, silently moving interest and dividend credits into qualifying income when the flag flipped. As of LOA-2767, `Interest` is now ineligible for both profiles, restoring parity with v1. A reversal-shaped `Interest` row is no longer demoted to `Credit` (the `REVERSAL_DEMOTABLE_CATEGORIES` set was updated accordingly).

<Note>
Divergences between v1 and v2 eligibility verdicts for 13 `(PFC code, profile)` pairs are intentionally preserved as of LOA-2767 and tracked in LOA-2835. Ten inflate income (retirement pension, child support, unemployment, long-term disability, and cash advances route to `Deposit` or `P2P Payment` in v2). Two are accepted improvements (`TRANSFER_IN_ACCOUNT_TRANSFER` and `INCOME_MILITARY`). These are underwriting policy calls, not bugs.
</Note>

**How v2 is served (LOA-2696):** `creditCategoryVocabulary()` (`lib/bank-statement/credit-category-vocabulary.ts`) is the **single flag reader** — all read paths delegate to it rather than reading the env var directly. When the flag is on, `servedCategory()` returns from `v2CreditCategoryVocabulary`; when off, from `v1CreditCategoryVocabulary`. The v2 vocabulary serves answers in three tiers:

1. **Override** — a human-authored reviewer correction wins unconditionally.
2. **Structural / resolver** — when `credit_category_source` is `structural` or `resolver`, the v2 `credit_category` is returned directly.
3. **Fallback tier** — when `credit_category_source` is `fallback`, a v1→v2 translation (`v1-to-v2-translation.ts`) maps the legacy v1 category to the nearest v2 equivalent; the original v1 answer is the backstop if no translation exists.

Rows with no v2 answer (`credit_category_source IS NULL`) fall back to the v1 Plaid PFC answer, so flag-on does not break rows that pre-date the v2 pass.

**Income surfaces under flag-on:** `effective_category`, income eligibility (`baselineIncome`), filter values, and qualifying-deposit grouping all use the vocabulary, so v2 categories affect what counts as income without a reprocess. The `filter-income-transactions.ts` baseline reads `isV2Category()` to select the correct eligibility matrix.

**Institution coverage (LOA-2659):** `mapInstitution` previously admitted only three named banks and returned `null` for all others, silently skipping their statements. It now returns a `generic` layout for every unrecognized institution. To prevent cross-bank hash collisions, `RawStatementLine.namespace` is now the hash namespace, falling back to `institution` for the three already-recognized banks. Two rail rungs were also added: `Ext Deposit` (`ACH_SHAPE_PATTERNS`) and a bare `deposit` token (R4.10 — last rung, converts only a `null`).

**Portal surface:** the separate `credit-category-select-filter` dropdown (which was v2-only and gated to super-admins) was removed in LOA-2696. Category filtering now uses the single shared vocabulary and `category-select.tsx`.

**`credit_category_label_safety` column (LOA-2763, migration `0067`).** `transactions` carries a
new `credit_category_label_safety` column (CHECK: `'safe' | 'unsafe' | NULL`). `NULL` means no
safety verdict was written for this row — its absence routes a pre-existing row to the
`legacyVerdict` path in `credit-category-label-safety.ts` rather than treating it as `safe`.
No default is set deliberately: a code-side omission stays `NULL` and visible, rather than
being silently stamped `safe`. The companion migration `0067` also guards column integrity with a
CHECK constraint that enumerates the two allowed non-null values.

**Reviewer sentinels in the v2 category picker (#4199).** Three reviewer sentinel options —
previously removed during the v2 migration — have been restored to
`CREDIT_CATEGORIES_V2_PICKER_OPTIONS`. Three defects fixed alongside the restoration: sentinel
fallback behavior, exclusion re-display after a sentinel is cleared, and the per-row patch
lifecycle when a sentinel is applied and then reverted.

## Dispatch and entitlement

`bankStatementIncome` declares `requiresExplicitGrant`, so the router's zero-rows fallback that
entitles un-seeded lenders to other active agents deliberately does **not** apply here. The Octy
grant is the switch on every path. The agent reaches the plan through **two entry points**:

1. **Router planning (partner lane):** A partner audit request must name
   `"bankStatementIncome"` in `agents[]`, and the lender must hold an explicit
   `lender_agent_entitlements` row with `enabled = true`. There is no `defaultOnLanes`
   declaration; an omitted or empty `agents[]` never plans it.

2. **EPC pre-enrollment (LOA-1951):** EPC audit requests carry no `agents[]` DTO.
   `resolveBsiPreEnrollment` in `integration-orchestration.service.ts` pre-enrolls the agent
   for entitled lenders on qualifying programs. An entitlement read failure plans the agent
   speculatively to hold the audit open; the `afterPhase(0)` trigger re-checks and seals
   an unentitled lender as skipped. Pre-enrollment is not a grant — only execution confirms
   entitlement.

Grants are managed in Octy. A grant takes effect immediately.

<Note>
`bankStatementIncome` is now a member of `UiAuditAgentType` (LOA-1951 — EPC sidebar gating). This means it **does** appear in `UI_AUDIT_AGENT_TYPES`. It is absent from `GraphRegistryService` and `EXECUTOR_AGENT_KEYS` (queue_worker constraint). The agent's findings appear in the portal's `/results` income section and in the partner API `results.agents.bankStatementIncome` block, but there is no audit-result card in the standard portal audit view. The `UiAuditAgentType` membership enables the **Bank Statements** sidebar tab in the Encompass EPC plugin.
</Note>

## EPC lane (LOA-1951)

Entitled lenders on the EPC lane receive automatic enrollment for qualifying programs. The
experience differs from the partner lane in several ways:

- **Iframe review.** Encompass underwriters review the existing portal income UI inside an
  iframe embedded in the EPC plugin. The staff income section continues to use its own
  section payload.
- **Write access.** EPC iframe viewers can write (category overrides, reviewer selections)
  subject to the existing CSRF checks. Popup/read-only EPC viewers remain restricted. EPC
  writes are attributed to the partner organization with no individual user ID. Iframe cookies
  use Partitioned (CHIPS) to support cross-site embedding.
- **eFolder delivery.** EPC exports always submit PDF and hide format controls. Each export
  gets a unique object key; the integrations companion delivers the PDF to the Encompass
  eFolder via its consumer. The server communicates delivery behavior through `deliveryStatus`.
- **`epc_audit` source.** EPC batches are minted with `borrower_files.source = 'epc_audit'`
  (migration `0068` adds the column value; migration `0069` validates it). EPC writes suppress
  asset-run triggers and carry persisted EPC buckets through extraction.

## Audit lifecycle and source isolation

The agent runs as a `queue_worker` triggered via `triggerBankStatementIncome`. The execution lifecycle is managed by `AgentRunReconciler` with hand-rolled `agent_runs` ledger semantics:

- **Reopen**: a redelivered message whose ledger row is already complete (stale redelivery) is recovered by re-reading domain truth and completing idempotently.
- **Complete with output**: the income summary (qualified income, monthly breakdown, statement count, findings count) is frozen atomically onto `agent_runs.output.summary` at the terminal flip.
- **Fail**: terminal only on exhausted attempts; per-attempt retries leave the row open.

`borrower_files.source` now has three allowed values: `'portal'`, `'partner_audit'`, and
`'epc_audit'`. `portalBorrowerFileSourcePredicate()` returns `source = 'portal'` (was
`IS DISTINCT FROM 'partner_audit'`), so both partner and EPC batches are excluded from every
portal / lender-wide / status-driven `borrower_files` read or mutation. A portal credential
cannot read, mutate, delete, or reprocess a partner or EPC batch even with a leaked id.

EPC pending rows are included in deadline recovery alongside partner rows, preserving the portal
pending-backlog exemption.

### Income summary snapshot

The income summary is frozen onto `agent_runs.output` at completion (LOA-1701). The partner `results.agents.bankStatementIncome` block serves this snapshot verbatim — a later recalculation, settings change, or re-claim rewrites the batch but never alters what a past audit reported. Rows completed before the snapshot landed fall back to live derivation via `BankStatementService.getDetail`.
