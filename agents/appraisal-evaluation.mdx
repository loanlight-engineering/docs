The Appraisal-Evaluation agent (`appraisalEvaluation`) is a fully implemented, 12-node compiled
LangGraph that extracts and enriches appraisal data. Unlike
[Credit-Evaluation](/agents/credit-evaluation), rule evaluation does **not** run inside the
graph — it runs in the processor, after the graph returns.

<Note>
The graph performs extraction and enrichment only. Its output type
(`AppraisalEvaluationGraphOutput`) carries no `complianceResults`. The processor
(`appraisal.processor.ts`) re-runs `evaluateWithCustomRules` with its dependency-injected DB and
persists results. `LangGraphService.createAppraisalEvaluationGraph` does **not** persist
`appraisal_runs` — the processor does. This is a deliberate divergence from the credit agent,
whose `aggregate` node persists.
</Note>

## How it runs

Runs are created via `POST /api/v1/portal/appraisals/run` (`PortalAppraisalController`, base
path `api/v1/portal/appraisals`). The DTO `CreateRunDto` carries `s3Key` (required), optional
`xmlS3Key`, `loanProgramId`, `loanNumber`, and `agencySources?` (in `fannie_mae | freddie_mac`,
max 2). The processor (`@Processor("appraisal-extraction")`) claims the run with a heartbeat and
`claimToken` (the same recovery pattern as credit), calls
`LangGraphService.createAppraisalEvaluationGraph`, persists the graph-returned `enrichmentData`,
then runs the rules and findings (see below).

### EPC audit path (LOA-1675)

The agent also runs on the EPC audit path, triggered post-completion by
`triggerAppraisalEvaluation` in `integration-orchestration.service.ts`. After `WORKFLOW.COMPLETE`
fires, the orchestrator enumerates classified appraisal documents (`appraisal_standard`,
`desk_review`) from the S3 manifest, copies the appraisal PDF into the portal bucket, mints an
`appraisal_runs` row stamped with `loan_id`, `lender_id`, and `audit_run_id`, and dispatches
the job by identity. The EPC audit completes synchronously; the appraisal job runs as a
detached best-effort task (up to ~95 min) and does not gate `WORKFLOW.COMPLETE`.

Read the EPC-linked run via `GET /api/v1/audit_runs/:id/appraisal` — returns `PortalAppraisalPayload`
or `{ data: null }` (never 404). The `AppraisalAuditProjectionService` applies the manual-override
overlay (LOA-1685) to the projection. See [Integration orchestration pipeline](/integrations/orchestration-pipeline)
and [Reading audit results](/pipeline/results).

### Partner API path (LOA-1704)

The agent runs on the partner audit path when **all three** conditions hold: the request names
`appraisalEvaluation` in `agents[]`, the lender is entitled, and a classified appraisal report
(`appraisal_standard` or `desk_review`) is present. Explicit opt-in is required — the agent
never runs by default on the partner lane.

Naming `appraisalEvaluation` holds the audit open until the appraisal is terminal (~50 min
typical, ~120 min worst case) before the other agents' results become available via `/results`.
This is the same completion-deferral `bankStatementIncome` already applies.

Partner-specific endpoints:
- `GET /api/v1/partner/audits/:auditId/appraisal` — returns the `PortalAppraisalPayload` for the
  run, or `{ data: null }` when no run exists. Ownership via `getAuditRunByLender`; a missing or
  cross-tenant audit returns `404`.
- `GET /api/v1/partner/audits/:auditId/results` — includes an `agents.appraisalEvaluation` block
  (the same `AuditAppraisalProjection`). Partner-boundary fields `interpretedLogic`, `ruleSource`,
  `failedElements`, and `reasonCode` are stripped before the response. Summary counts
  (`totalIssues`, `criticalIssues`, `warnings`) fold in appraisal compliance outcomes — FAIL →
  `criticalIssues`; WARNING/NEEDS_INFO/PENDING → `warnings`; PASS/SKIPPED excluded.

<Note>
`appraisalEvaluation` does not declare `requiresExplicitGrant`, so the router's zero-rows
fallback (all active agents for an un-seeded lender) applies — unlike `bankStatementIncome`. The
operational consequence is that Priority Financial's integration must send `agents:
["appraisalEvaluation"]` on any audit that should include one.
</Note>

`PortalAppraisalPayload` now includes `marketComps: AppraisalMarketComps | null` (LOA-2324, `shared-types@1.21.0`) alongside the existing `rentalData` field. The EPC embedded portal renders market comps — Zillow for-sale listings and ATTOM recently-sold sales from the `marketCompsFetch` graph node — in the appraisal comparables table via `AppraisalComparablesTable` (`shared-ui@0.15.0`). A `CompSourcePill` distinguishes "Appraisal" (extracted from the PDF), "SSR" (submission support), and "LoanLight Data" (market-enrichment) rows. The `marketComps` field is `null` when `ENABLE_ZILLOW_COMPS` is off or the subject is ineligible.

`PortalAppraisalPayload` includes `rentalData: AppraisalRentalData | null` (LOA-1954). The EPC/partner
surface gets the **display subset only**: `AppraisalAuditProjectionService` pipes rental data through
`toAppraisalRentalData()` before returning, stripping the `_`-prefixed internal diagnostic fields
(`_endpointStatus`, `_synthetic`, `_skipped`, `_errors`, `propertyProfile`, `requestCoords`) that the
staff portal's own `getRunDetail` path retains. `null` when the run was not rental-gated or the lookup
was skipped.

`LangGraphService.createAppraisalEvaluationGraph` takes an options object, returns the
extraction result plus the graph-owned `enrichmentData`, and races the graph against
`APPRAISAL_GRAPH_DEADLINE_MS`. The builder `buildAppraisalEvaluationGraph` closes over
`pdfBytes`, optional `xmlCandidates`, `onPartial`, `onIteration`, and `inputFilename` — these
stay closure-delivered and are never placed in graph state or serialized progress.

## The graph

```text
__start__ → prepare → parse → classify → reductoExtract
  → resolveFields → normalizeAdapter → computeCoverage
  → (attomGate) → attomFetch? → (routeAttomReplay) → validateProject
  → mashvisorFetch → marketCompsFetch → aggregate → __end__
```

The canonical node order is pinned in `APPRAISAL_EVALUATION_NODE_IDS`. `parse` runs first —
before `classify` — so classification reads Reducto-parsed document text instead of the local PDF
text layer. This is what lets an image-only UAD 3.6 appraisal identify its own form type on
content rather than misrouting on the absence of a font table (LOA-2190, #3307).

There is no `spatialGenerate` node (the legacy pdfjs spatial-candidate path was removed when
extraction was consolidated onto Reducto, PR #2463), and there is no `detectScanned` or `ocr`
node — the scan-detection routing that previously gated extraction strategy was removed when
`parse` took over the single upload. `reductoExtract` reuses the `jobid://` handle the `parse`
node produced; Reducto OCRs scanned PDFs natively regardless.

Routing:

- `attomGate(computeCoverage)`: route to `attomFetch` only when **not** in `enrichmentPass`,
  `ENABLE_ATTOM_ENRICHMENT === "true"`, the second pass fits the lock budget
  (`attomSecondPassExceedsLockBudget`), and `hasAttomAddressInputs`; otherwise go straight to
  `validateProject`.
- `routeAttomReplay(attomFetch)`: when `hasReplayableEnrichmentData` (any of `avmDetail`,
  `attomAvmDetail`, `avmHistory`, `comparableSales`, `salesTrend`), back-edge to `reductoExtract`
  for a second extraction pass; otherwise go to `validateProject`.
- After `validateProject` the graph always runs `mashvisorFetch`, then `aggregate`.

Every node is wrapped by `instrumentNode`, which emits `node:<name>` started / complete / failed
milestones.

The single upload + parse call for the run (LOA-2190). Uploads the PDF bytes to Reducto and

<Accordion title="mashvisorFetch">
STR/LTR rental-data enrichment via Mashvisor (LOA-1449, PR #2285). Runs between `validateProject`
and `marketCompsFetch`.

The gate fires when `unitCount === 1` **and** `isDscrLoan`, fail-closed on any indeterminate input
(LOA-2109). Unit count is `max(improvements.units, units[].length)`; when `improvements.units` is
absent and `units[]` holds exactly one entry, the gate fails closed (the adapter repairs a null
scalar on every recognized single-unit form but not on a 1025, so a missing scalar beside a
one-entry array is more likely an under-extracted 2–4 unit). DSCR is detected via
`match_doc_type` (deterministic override) or `matchesDscrProgramName()` — a lender-agnostic
pattern match against `loans.loan_program_name` and `loan_programs.name`, with a negation guard
that rejects names containing `non`+DSCR or `ineligible` before the positive match fires.

<Note>
The Form 1025 disjunct (`formType === "1025"`) was removed in LOA-2109. Previously the gate fired
on any Form 1025 (2–4 unit) and on DSCR programs; the DSCR branch was effectively dead in
production (`loan_programs.match_doc_type` is NULL on every non-luxury program row), so nearly
all enriched runs were 2–4 unit properties where Mashvisor's single-address lookup produces a
correct per-unit figure but a misleading building total. Single-unit DSCR is the population where
the math is valid.
</Note>

A non-null `rentalData` on the run always carries a `_gate` marker (`{ unitCount, isDscrLoan }`)
stamped by the node. At read time (six surfaces: staff/EPC redactors, `getRunDetail`, audit
projection, export builder, `listRuns` findings count) the marker is re-checked against the
current extraction — a staleness mismatch suppresses the card and its RF-* findings without a DB
write, preserving the payload on disk for if the gate is later loosened.

With the gate open the node guards on a complete subject street/city/state, then calls
`MashvisorService.getRentalData(addr, signal)` with an abort signal capped at
`MASHVISOR_ENRICHMENT_CEILING_MS` (1 minute). The service fans out **three parallel endpoints**
(PR #2752):

- **Lookup** — STR aggregate performance: `median_rental_income`, `median_annual_revenue`,
  `median_occupancy_rate`, `sample_size`.
- **List Comps** — STR comparable listings: short-term rental comps filtered, ranked, and capped
  at **5** (see below).
- **Long-Term Comps** — LTR comparable listings: an array of long-term rental comps
  (`LtrComp`: `monthlyRent`, `bedrooms`, `bathrooms`, `sqft`, `address`, `listingDate`,
  `distanceMiles`, `url`).

`NormalizedAddress` now carries `latitude`/`longitude` (resolved from ATTOM enrichment data in
the node) so each comp's `distanceMiles` can be computed via haversine; the field is `null`
when ATTOM coordinates are unavailable — comps render with `distanceMiles: null` rather than
blocking the fetch.

#### STR comps filtering and ranking (LOA-1940, PR #2980)

The raw List Comps response is filtered and ranked before it reaches the portal:

- **Bedroom filter** — comps must exactly match the subject's bedroom count(s). Mashvisor's `beds=N` param is fuzzy (returns ≥N-ish), so a client-side exact match (`num_of_beds ∈ targets`) is applied after fetching. Multi-unit Form 1025 appraisals use the distinct bedroom counts across `units[].bedrooms`; single-unit forms use the scalar `improvements.bedrooms` (or `unit_description.bedrooms` for condos). Per-target fetches run in parallel with adaptive paging — page 2 is requested only when a target's page-1 exact-match count is below the display cap.
- **Entire-home only** — comps where `room_type !== "Entire home/apt"` (private-room, shared-room) are dropped.
- **Best 5** — the table is capped at 5 comps. Quota is allocated deterministically across bedroom targets (`floor(5/n)` + nearest-remainder + thin-pool redistribution) so each unit type retains representation, then sorted by proximity (closest first).
- **Location column** — shows a real `"City, State"` locality string (e.g. `"Brooklyn, NY"`) instead of a placeholder repeated on every row.

Two discriminators flow from backend → DTO → portal:
|- `strCompsFilteredEmpty` — list-comps returned results but bedroom/entire-home filters left none. The finding is relabelled **"Rental Comps Filtered"** (never asserts "no rental market").
|- `bedTargetsResolved` — whether subject bedroom count was derivable. Gates "matched" vs. "nearby comparable listings" copy so legacy/underivable rows do not falsely claim a bedroom match.

The `RentalDataResult` shape is:
- `strPerformance` — STR aggregate (from Lookup), or `null` on miss.
- `strComps` — STR comp array (from List Comps), after bedroom/entire-home filtering, quota ranking, and 5-comp cap.
- `ltrComps` — LTR comp array (from Long-Term Comps), **bounded to the nearest 10** (proximity-ranked
  by haversine distance, nearest-first; comps without coordinates keep API order at the tail).
  Added in LOA-1869 (#2849) — a median over the full unbounded page-1 slice (up to 30
  unranked comps) was noisy. The bound is cardinality, not sort-only: the sort picks which 10.
  Each `LtrComp` carries `city`, `state`, and `zipcode` (LOA-2108, nullable — coverage verified
  on one market fixture; absent on redacted captures). The shared-ui address composer uses these
  fields to render a `"City, ST 00000"` locality string in the portal Rent Comparables table.
- `sampleSize` — number of STR comps behind the Lookup aggregate (`null` on miss). Replaces
  the retired `confidence` field — no real confidence score exists in the Mashvisor API.

<Note>
**Occupancy format (LOA-1869):** the Mashvisor API returns `median_occupancy_rate` and the
per-comp `occupancy` field as a **percent** (0–100, e.g. `42`), not a fraction. The adapter
converts to a ratio (0–1) before writing to `strPerformance.occupancy` and
`RentalComp.occupancy`. Values outside `[0,1]` after conversion are nulled by a downstream
sanity guard. The live API also wraps every response in a `{ status, content: … }` envelope;
the adapter unwraps `content` before schema-parsing and treats a missing or non-object
`content` as an unrecognized shape (distinct from a genuine-empty `{}` response).
</Note>

The node never throws (per-endpoint failures surface in `_errors`; a timeout on the whole
request yields the null-sentinel for all fields). The result rides graph state as `rentalData`;
the processor merges rental findings (`mergeRentalFindings`) and persists
`appraisal_runs.rental_data`.
</Accordion>
<Accordion title="marketCompsFetch">
Market-comps enrichment via Zillow for-sale listings and ATTOM recently-sold sales (LOA-2068,
migration `0293`). Runs between `mashvisorFetch` and `aggregate`, ceiling 6 minutes
(`MARKET_COMPS_CEILING_MS`). The gate is fail-closed: enrichment runs only when `ENABLE_ZILLOW_COMPS
=== "true"` (default `false`) **and** the subject resolves an address with city/state/zip.

The two parallel pipelines:
- **Zillow for-sale** (via HasData) — active listings; price is an asking price, not a closed sale.
- **ATTOM recently-sold** — closed sales within a rolling window anchored to the appraisal

Each pipeline is reserved up to 5 of the 10-comp cap before the remainder is filled by haversine

candidates. The full `MarketCompsResult` shape (types in

- `outcome` — `ok | disabled | ineligible_subject | underspecified_subject |

- `comps[]` — up to 10 `CompListing` rows, discriminated on `saleType: "forSale" |

- `distinctProperties` — count of distinct dwellings (unit-stripped) across all rows.
- `diagnostics.forSale` / `diagnostics.recentlySold` — per-pipeline drop counts and
  `requestCount` (logical passes to the vendor).
- `fetchedAt`, `requestCount`, `estimatedCreditsUsed`.

### R10 appraisal-gated completion race (LOA-1751)

When an EPC audit is appraisal-gated, the orchestration service (`integration-orchestration.service.ts`) used to rely solely on the appraisal processor's own `tryCompleteAuditRun` call to close the audit. That single attempt no-oped if appraisal finished before its barrier-awaited siblings, leaving the audit permanently stuck in `processing`. Since LOA-1751 (#2709), after `orchestrator.run` resolves the gated branch unconditionally retries `tryCompleteAuditRun` (1 initial + 2 retries at 100ms and 300ms), closing the gap without risking double-emission of `workflow:complete`. The follow-up durable backstop was delivered in LOA-1752 (#2719) as `AuditCompletionReaperService` — see [Orphan reapers](/agents/runs-ledger#orphan-reapers).

## IRIS — image risk interpretation system (LOA-1901)

IRIS gives appraisal review "eyes" via per-photo Claude vision analysis. It is a separate entitlement-gated subsystem that runs alongside the main extraction graph, not a new node inside it. IRIS co-requires `appraisalEvaluation` and is seeded as non-billable.

### Entitlement and triggering

The entitlement key is `appraisalIris` (`agent_entitlements.agent_type`). The row requires `explicit: true`, meaning the lender must be explicitly seeded — the router's zero-rows fallback does not grant it. IRIS runs automatically on every appraisal extraction that the entitled lender submits (auto-trigger via the `appraisal-iris-worker`), and also on demand via `POST /api/v1/portal/appraisals/:id/iris/analyze`.

The `iris-figure-broker` service shares the Reducto figure-detection result between the main graph and the IRIS analysis so both reuse one parse call without a second upload.

### The IRIS analysis pipeline

For each extracted photo the agent runs:

1. **Reducto figure detection** — detects figure bounding boxes in the source PDF.
2. **Crop** — cuts the photo from the source PDF using the bbox; the normalized bbox (`[0,1]` coordinates) is stored in `appraisal_photos.bbox`.
3. **Claude vision conversation** — a prompt-cached conversation per photo using `inspect_closer`-named grid regions (never model-emitted coordinates). The model classifies the photo against the active taxonomy vocabulary.
4. **Expectation-matrix anomaly scan** — pure-code post-processing that checks each detected element/condition against `applicable_scenes` in the taxonomy and stamps `out_of_scene` findings.
5. **Aggregation** — results written to `appraisal_runs.iris_facts`.

The LLM step is declared as `appraisalEvaluation.irisVisionCatalog` in the llm-config and frozen onto `agent_runs.llm_config`.

<Note>
**Rules evaluation is deferred to Phase 3.** IRIS_001–014 (`injectIrisEvalInputs`) exist in the architecture but are deliberately not evaluated yet per `docs/loa-1901-vision-rules-architecture.md §13`. No compliance findings are produced by IRIS in the current phase.
</Note>

### Taxonomy as data (`appraisal_iris_taxonomy`)

The IRIS vocabulary is stored in `appraisal_iris_taxonomy` (migration `0296`). The agent loads `active = true` rows at run time and builds its prompt and Zod validators from them, so severity tuning and vocabulary changes take effect without a deploy. Rows are global (no `lender_id`). Retired entries use `active = false`, never `DELETE` — photo observation payloads reference codes.

Key columns:

- `kind` — `'scene' | 'element' | 'condition'` (CHECK constraint)
- `code` — unique within a kind (ON CONFLICT target for idempotent seed INSERTs)
- `description` — model-facing text rendered verbatim into the IRIS system prompt
- `flaggable` / `default_severity` — whether the taxonomy entry surfaces as a finding and at what severity (`info | low | medium | high | critical`)
- `applicable_scenes` — used post-detection for the out-of-scene anomaly scan, **not** a detection filter
- `out_of_scene_severity` — severity for an out-of-scene finding when applicable

**Fact-group columns** (migration `0308`, LOA-1901): fact groups are now taxonomy config, not hardcoded logic. Every distinct `fact_tags` tag across active element/condition rows defines a fact group at read time.

- `fact_tags` — array of fact-group membership tags for this element/condition (e.g. `["outbuildings", "agricultural_use"]`). An entry may carry multiple tags.
- `fact_min_strength` — `'weak' | 'moderate' | null`. Below-floor detections cannot assert `yes` for the group (they can still prevent a `no` assertion).
- `fact_scenes` — scene-scope filter for the sweep only; deliberately separate from `applicable_scenes`, which drives out-of-scene stamping.
- `instance_flag_over` — scenes only. Emit a count fact group and flag when per-dwelling confirmed instances exceed this threshold (e.g. kitchen count > 1 is the accessory-unit signal).
- `instance_flag_severity` — severity for the instance-count flag.

**Report-band column** (migration `0309`, LOA-1901):

- `photo_group` — scenes only. The level-1 band photos of this scene are grouped under in the findings report and the gallery (`subject_interior | subject_exterior | adu_outbuildings | comparables | collages | maps_sketches | other`). `NULL` resolves to `"Other"`. This replaces the hardcoded scene sets `photo-display.ts` used to carry; a new scene picks up its band purely from config.

Drift between the schema and the seed SQL is enforced by `__tests__/appraisal-iris-taxonomy.spec.ts`.

### Fact Groups v2 — read-time sweep

Fact groups (which properties the subject has: manufactured home, ADU, pool, etc.) are now computed at read time by `fact-sweep.ts`, not hardcoded. The engine (`sweepFactGroups`) derives groups from stored per-photo observations plus the **current** taxonomy config. Tuning a tag, strength floor, or scene threshold re-grades all historical runs instantly without a re-run — exactly like flag severities already do via the read-time taxonomy join. Nothing is persisted from the sweep; `appraisal_runs.iris_facts` keeps only the run lifecycle.

Two mechanism types, no per-group special cases:

- **Tag groups** — every distinct `fact_tags` tag is a group. Members are the detected element/condition rows carrying that tag. Tone derives from detected members' existing flag config.
- **Count groups** — a scene with `instance_flag_over` emits a per-dwelling instance count using the same scene-level semantics as the v1 kitchen-count logic, now generalised to every applicable scene.

Presence is tri-state: `no` is only claimable on a complete run; comparable-property photos and hidden (non-photo) scenes never feed a group.

Both the portal (in-process) and Octy (via `POST /internal/iris/fact-sweep`) read the same engine output. The batch endpoint accepts up to **25 appraisal run IDs**, up to **500 photos per run**, and resolves taxonomy from the shared Drizzle DB client.

### Photo table (`appraisal_photos`)

`appraisal_photos` (migration `0297`, bbox in `0298`) is the single photo store. One row per extracted photo; the IRIS observation columns (`scene`, `attribution`, `quality`, `elements`, `conditions`) are `NULL` until the agent catalogs the photo (`analyzed_at` is the marker). Rows use a deterministic UUIDv5 id (source signature + page + figure index) so a re-analysis of the same source upserts in place — no id churn, no orphan crops.

<Note>
**The legacy `photo_manifest` column and 8-value category contract are retired.** `PhotoClassifierService` and `ImageExtractionService` were deleted as part of LOA-1901. All photo data is now served from `appraisal_photos`. The `photo_manifest` column drop deliberately trails the `appraisal_photos` table creation by one deploy.
</Note>

### Portal and Octy surfaces

The portal **Photos** tab is gated to `super_admin` only via `canSeeIrisPhotos` — not yet visible to lenders. It has four views, selected via a tab strip: **Findings** (default), **Facts** (taxonomy-driven fact groups from the sweep), **Property features** (non-flagged element inventory), and **Gallery** (honeycomb). The processing view shows the scanning comb on top; completed photos settle into their scenes below it. Octy's audit-run modal is the primary viewing surface for IRIS data: the shared `IrisAnalysisPanel` provides the same four-view layout. See [Loan lookup and audit-run modal](/octy/loan-lookup).

Octy also provides a dedicated `/appraisals-iris` admin page with three tabs:
- **Appraisal Runs** — a paginated table of all IRIS-analyzed appraisal runs across lenders.
- **IRIS Taxonomy** — browse and inspect the seeded taxonomy rows, including the new fact-group and photo-band columns.
- **Dry Run** — internal multi-model compare harness; send a source PDF through multiple vision models side by side (`POST /api/appraisals-iris/dry-run`, SSE endpoint).

### agenticRefine, detectScanned, and ocr have been deleted

The `agenticRefine` node (factory and spec) was removed entirely in LOA-1043 — it OOM-killed a
production worker on scanned multi-page documents. Do not reintroduce an agentic refine pass
without addressing that memory profile. The `spatialGenerate` node was likewise removed when the
legacy pdfjs extraction path was retired. The `detectScanned` and `ocr` nodes were removed in
LOA-2190 (#3307): with `parse` running first, all extraction paths reuse the same Reducto parse
handle and no per-strategy upload or routing is needed.

### ATTOM budgeting and deadlines

`APPRAISAL_GRAPH_DEADLINE_MS` defaults to 95 minutes (`envMinutesMs`) and sits strictly between
the legitimate enrichment floor and the worker lock
(`APPRAISAL_EXTRACTION_LOCK_DURATION_MS`, 100 minutes). The floor
(`APPRAISAL_GRAPH_DEADLINE_LEGIT_FLOOR_MS`) is 26 min (`REDUCTO_PARSE_NODE_CEILING_MS`) +
59 min (`SUBSCHEMA_OVERALL_CEILING_MS`) + 2 min ATTOM + 1 min Mashvisor
(`MASHVISOR_ENRICHMENT_CEILING_MS`, LOA-1449) + 6 min market comps (`MARKET_COMPS_CEILING_MS`,
LOA-2068) = **94 minutes**. The market-comps node added genuinely new wall-clock spend;
LOA-2190 had previously hoisted the parse cost out of `SUBSCHEMA_OVERALL_CEILING_MS` (85 → 59
min) without changing the floor total. The floor increase forced the deadline 89 → 95 and the
worker lock 90 → 100 min (95 min + 30 s cleanup grace requires a 100-min lock to stay safely
below expiry). The pinned ordering invariant is
`single-call(60) < parse+split+ATTOM+mashvisor+comps(94) < graph(95) < lock(100)`.
`ATTOM_SECOND_PASS_CEILING_MS = SINGLE_CALL_DXT_CEILING_MS + SINGLE_CALL_DXF_TIMEOUT_MS`.
`attomSecondPassExceedsLockBudget` budgets against elapsed time since `graphStartedAt` (a missing
value means refuse). Relevant env: `ENABLE_ATTOM_ENRICHMENT`, `ENABLE_ZILLOW_COMPS`,
`APPRAISAL_GRAPH_DEADLINE_MS`.

<Warning>
LangGraph appraisal runs own ATTOM replay state. The processor must **not** perform legacy ATTOM
reruns — that is a trap door called out in the agent's `CLAUDE.md`.
</Warning>

## Processor-side rule evaluation

After the graph returns, `appraisal.processor.ts`:

<Steps>
<Step title="Persist enrichment">
Writes the graph-returned `enrichmentData`.
</Step>
<Step title="Evaluate rules">
Runs `evaluateWithCustomRules` (`lib/appraisal-pipeline/rules/evaluator.ts`) with the
processor's DI'd DB.
</Step>
<Step title="Generate findings">
`AppraisalFindingsService.generateFindings`.
</Step>
<Step title="Cross-document validation (step 7d)">
Once per extraction completion (gated on `auditRunId` + `loanId`; portal-only uploads skip
silently): retrieves three source documents — the URLA/1003 (`urla_1003` or `ed_urla`
classification type), the 1008 Transmittal (`transmittal_1008`), and the Flood Certificate
(`flood_certificate`) — via per-document deterministic LlamaCloud retrieval, then runs one
structured-output extraction call per source doc (3 LLM calls/run, no LLM query planner).
Compares 10 appraisal-extracted fields against the source values using deterministic
normalize-then-exact TypeScript (never fuzzy). Disagreements surface as `XDOC-*` **warning**
findings in the existing appraisal findings stream. Results are persisted in the new
`appraisal_runs.cross_doc_validation` jsonb column (migration `0264`), which stores only source
values — verdicts are always re-derived so corrections remain correct. The LLM step uses the
`appraisalEvaluation.crossDocExtraction` config (gpt-4.1, structuredOutput). On for all lenders;
not lender-configurable.
</Step>
<Step title="Write the run">
Writes `appraisal_runs` with `extractedData`, `complianceResults`, `findings`, coverage fields,
the field maps, and `cross_doc_validation`.
</Step>
</Steps>

### Appraisal rules

The rule definitions live in `lib/appraisal-pipeline/rules/definitions` (registry
`rule-registry.ts`) and span **67 rules** across these prefixes: `SUBJ_` (14), `SITE_` (8),
`EXH_` (6), `NEIGH_` (6), `COMP_` (6), `CONT_` (6), `IMP_` (6), `APPR_` (3), `CONDO_` (3),
`REC_` (3), `INCOME_` (2), `RENT_` (2), `GEN_` (1), `UNIT_` (1). The rules are agency-aware
(`AgencySource`: `fannie_mae`, `freddie_mac`), support compound conditions (`compound-walker`,
`condition-schema`), and use `feature-gates`.

<Note>
**SITE_005 gas-unreported behavior (LOA-2188, migrations `0304`/`0305`):** Gas reported as `"None"` now returns `NEEDS_INFO` rather than `FAIL`. The rule previously could not distinguish an all-electric property from an unreadable checkbox, so a `FAIL` on `"None"` was misleading. All other utilities with `"None"` remain a hard `FAIL`, with a per-utility message. The `CONDO_003` owner-occupancy threshold was corrected from `< 51%` to `<= 50%` to match Fannie Mae's established-project standard (strictly greater than 50% owner-occupied is required to pass). Both changes were also published to adopted lender rules via the guarded migrations, so already-adopted lenders received the corrected descriptions and thresholds automatically.
</Note>

<Note>
**SUBJ_015 removed globally (LOA-2201, migration `0290`).** SUBJ_015 (Filename vs Address
Mismatch) compared the street key extracted from the appraisal PDF's filename against
`subject.property_address` and warned on mismatches. It was grading lender naming conventions
rather than appraisal content quality, producing noise with no underwriting signal. Migration
`0290` deletes all adopted rows (writing a pre-delete snapshot to `portal_audit_log`) and
removing the master template. Historical compliance results retain the rule code. Any future
attempt to re-add SUBJ_015 to the registry or barrel export is rejected by a test guard.
</Note>

**"Unknown" escape hatch on 2.6 schemas (LOA-2088 / LOA-1156)** — Five leaves on the URAR 2.6 optimized schemas now accept `"Unknown"` as a sentinel value for an unreadable cell: `subject.occupant`, `improvements.quality`, `improvements.condition`, `neighborhood.demand_supply`, and `neighborhood.marketing_time`. The sentinel signals "the appraiser documented this field, but we could not read it" — it routes to `NEEDS_INFO` rather than a closed-enum `FAIL` from the model guessing a value. Each leaf also carries a when-to-use clause and an overuse guard.

<Warning>
**SUBJ_007 live defect (fixed in LOA-2088, PR #3177):** SUBJ_007 checks that `subject.occupant` is present and a recognized value. The rule has `requiredFields: ["subject.occupant"]`, so an **absent** value reaches `NEEDS_INFO` via the `evaluator.ts` preflight. But `"Unknown"` is `isPresent`, so it bypassed the preflight, missed the `VALID_OCCUPANT_VALUES` set, and hard-**FAIL**ed — worse than an absent value. The escape hatch introduced in LOA-1156 made unreadable occupancy rows report as appraiser defects rather than missing data. The fix routes `"Unknown"` in SUBJ_007 to `NEEDS_INFO`. The `"Unknown"` member is allowlisted in `adapter.ts`'s canonical set so nothing else non-canonical can reach the rule through the same path. This affected all URAR 3.6 runs where occupancy was unreadable; URAR 2.6 was not yet affected because the hatch was not yet open there.
</Warning>

**`CONT_006` — Appraised value below purchase price (LOA-1753)** is the newest global built-in. It flags when the appraiser's `reconciliation.final_opinion_of_value` (alias-aware via `resolveAppraisedValue`) comes in below `contract.contract_price`. Purchase transactions only; refinances return `SKIPPED`. Default severity `WARNING` (configurable per lender). A `tolerancePercent` threshold (default `0` = flag any shortfall) suppresses rounding noise. Missing operands return `NEEDS_INFO` rather than double-flagging — presence is owned by `REC_002` and `CONT_002`. Lender-neutral (no lender-code gate, no loan-context dependency) so it also evaluates on standalone portal appraisal runs. Migration `0246` seeds the template and backfills it into all active rule sets.

**LOS appraisal value reconciliation (LOA-1753)** — `reconcileAppraisedValue()` in `lib/loan-context/loan-context-adapter.ts` reconciles the appraiser's extracted `final_opinion_of_value` against the LOS (Encompass) loan-file copy. The document value remains the appraisal-axis winner and the grading source; when the two values differ beyond `toleranceDollars` (default `0` = any mismatch), a `LoanFactConflict` is emitted on axis `appraisedValue` carrying both source values and the absolute delta. The LOS copy is comparison evidence only — without a document value, the appraisal axis stays unknown rather than falling back to the LOS copy. `parseLosAppraisedValue()` normalises the raw text column (strips `$`, commas) before comparison.

**`IMP_006` — Unique / atypical property (LOA-1713)** is the previous newest global built-in.

The `COMP_` family is `COMP_001`–`COMP_005` plus `COMP_007` (there is no `COMP_006`). `COMP_007`
(**Stated vs Actual Proximity**, LOA-1200 / PR #2315) verifies each comp's stated proximity
against the geocoded actual distance; it exists in the in-code registry but production evaluates
the DB-backed rules, so migration `0192_seed_comp_007_rule_template` seeds it into
`appraisal_rule_templates` and backfills it into existing rule sets. Migration
`0193_seed_missing_appraisal_rule_templates` likewise reconciles other in-code rules that were
never seeded. Migration `0213_comp_007_tolerance_10pct` (LOA-1200) tightened the proximity
tolerance from 25% to 10%.

The `appraisal_rules.operator` CHECK (`appraisal_rules_operator_check`) is the **16-value** union
(adding `abs_less_than` and `abs_less_than_or_equal` to the base 14). Credit reached the same
16-operator parity in migration `0190_credit_operator_abs_parity`, so the two unions now match.
The appraisal union is drift-pinned by `operator-check-drift.spec.ts`; the Drizzle schema must
mirror the latest migration SQL.

### Lender-specific rule bundles

Lender-specific overlays are authored as staged bundles in the `portal-appraisal-rules` module
(`staged-bundles/`). Applied via `/admin/staged-rules` → dry-run preview → promote.

#### Deephaven Phase 1.5 bundle

The **Deephaven Phase 1.5** bundle
LOA-1367..1378) adds the single Deephaven lender's compound rules `DH_012`–`DH_052` (property
condition, site/hazard + ADU, property-type classification, condo project, sales comparison, and
occupancy/solar/income/deferred-maintenance groups) on top of new Phase 1.5 extraction signals in
the adapter and `appraisal-data` schema. These DH rules are compound rules evaluated by the shared
`compound-walker`; they are written only into the Deephaven lender's active rule set and are not
part of the 67-rule core registry.

The accessory-dwelling-unit (ADU) rules in Group B are `DH_025` (**No accessory dwelling unit** —
a flat predicate that warns when `improvements.has_accessory_unit` is `true`) and `DH_026`
(**ADU minimum area** — a conditional that, when an ADU is present, fails if `cost_approach.adu_sqft`
is under 500 sq ft). Both read fields that originally existed only as Zod defs and so returned
`NEEDS_INFO` on every appraisal; LOA-1497 (PR #2506) wired `improvements.has_accessory_unit` and
`cost_approach.adu_sqft` through the Reducto/LLM extraction path plus adapter coercion (no
rule-definition or Zod change) so the two rules actually evaluate. The XML bridge maps
`…improvements[0].units[0].detail.is_adu → improvements.has_accessory_unit`, so DH_025 evaluates
from MISMO too, but DH_026 stays `NEEDS_INFO` on XML-only ADU appraisals — MISMO carries an ADU
count, not the cost-grid area, so only the PDF path fills `adu_sqft`.

Property-type characteristic flags were renamed from their original "required-state" naming
(e.g. “Not a row home”, “No unusual floor plan”) to characteristic-first naming that describes
the property trait rather than a prohibition (LOA-1680). `DH_029` (`CUST_DEE00029`, the row-home
rule) was also downgraded from `FAIL` to `WARNING` — row homes and townhouses are eligible
property types; the rule flags for underwriter review, not disqualification. `DH_019`
(`CUST_DEE00019`) and related rules (`CUST_DEE00025`, `00030`, `00031`, `00049`) were renamed
similarly. Genuine disqualifiers (condotel, lava zone, multiple dwellings, condition defects,
recent conversion) retain `FAIL` severity and are unchanged.

<Note>
The fields were renamed between spec and as-built: LOA-1368/1374 spec'd `improvements.has_adu` and
`adu_size_sqft`, but the rule-read paths are `improvements.has_accessory_unit` and
`cost_approach.adu_sqft`. Grepping `has_adu` finds nothing.
</Note>

#### First Colony (Sharp Advantage) bundle updates (LOA-1713 / LOA-2188)

<Note>
**`FCAPP_018` scoped to condo/co-op forms (LOA-2188 follow-up, migration `0307`):** `FCAPP_018` now declares `formTypes: ["1073", "1075", "coop"]`, restricting evaluation to condo and co-op appraisals. Previously the rule evaluated on all form types, which was incorrect since its `then` arm checks `condo_project_info.presale_percent` — a field only applicable to condo projects. `FCAPP_021` remains unscoped pending the fleet-wide form-type normalization fix in LOA-2285.
</Note>

Two additions to the First Colony (`sharp_advantage`) bundle:

- **`FCAPP_010` — Atypical design style (WARNING, lender-wide):** flags any appraisal whose Design (Style) field isn't one of First Colony's accepted types — Traditional, Colonial, Contemporary, Ranch, Duplex, or Split Entry. Keyed on `improvements.design_style` using a generated case-insensitive regex (`FC_DESIGN_STYLE_PATTERN`) to handle casing, all-caps, and compound values (e.g. "2 Story/Colonial"). Variants normalized: Split Level / Split Foyer / Bi-Level → Split Entry; Raised Ranch → Ranch.
- **`IMP_006` backfill:** the new global rule is automatically included in First Colony's active rule set via migration `0216` (same as all active sets).

#### Luxury WSE Credit bundle update (LOA-1652)

The `luxury-wse-credit` bundle now **disables `CRED_011`** (hard-inquiry count check) lender-wide, including DSCR programs. ## Review summary export

`POST /:id/export` (`PortalAppraisalController.export`) renders the appraisal **Review summary**
as a branded PDF — property facts, an **Issues Found** section (the failed and warning rules,
surfaced near the top), the full findings list, and program-rule outcomes. The payload comes from
the same `getRunDetail` projection the review page renders (`appraisal-export-data.service.ts` →
`renderAppraisalReviewHtml` / `appraisal-pdf-template.ts`), so the PDF matches the on-screen
review. It reuses the `bank-statement-export` Puppeteer writer and signed-URL service.

- **Roles**: `client_admin`, `client_user`, and `super_admin` (PR #2477). Throttled to 5
  requests/minute per user; the run must be `completed` or `reviewed` or the export is refused.
- **Findings gate** (PR #2496): the Findings section's empty state is keyed on whether enrichment
  actually ran for **this** run — `findingsEvaluated = run.enrichmentData != null` — not the live
  `ENABLE_ATTOM_ENRICHMENT` env flag. A run done while ATTOM was off (or where `attomGate` skipped
  enrichment) shows no "No findings" block, so a later flag flip cannot mislabel historical runs.

## Reliability and recovery

The appraisal processor uses the same heartbeat / `claimToken` / bounded-recovery pattern as
credit, with an in-process graph deadline below the BullMQ lock. The
`sweepOrphanedRuns` reaper recovers stale `pending`/`running` runs, re-enqueues them up to
`APPRAISAL_MAX_RECOVERY_ATTEMPTS`, then terminally fails them — the same shape as the credit
orphan sweep.
