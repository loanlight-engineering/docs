This is the spine of the EPC integration service. The trigger is an Encompass user pressing **"Run LoanLight AUS"** (transaction type `"Run LoanLight AUS"`). From there, the service ingests the loan, hands it to the AUS, watches progress, and delivers the rendered report back into Encompass.

The thread that ties every stage together is the **`correlationId`** — it equals `transaction_state.id` and is the AUS `auditRunId`. It appears in S3 keys, EventBridge payloads, SQS messages, and the database. When tracing a run, start from the `correlationId`.

## End to end

<Steps>
<Step title="Signed webhook arrives">
Encompass POSTs a signed webhook to `POST /integrations/webhooks/transactions` (created/updated) or `POST /integrations/webhooks/events`. The HMAC `VerifyElliSignatureMiddleware` validates the `elli-signature` header before the controller runs. See [Webhook security](/integrations/epc-webhook-security).
</Step>
<Step title="Fetch and dedup the event">
`WebhooksService.handleWebhook` fetches the full EPC event via `EpcService.getEvent(eventId, resourceId, isUat)` (UAT is `environment === "concept"`), persists the raw event to `epc_event`, and dedups: if `event.updateCount > 1` it is a duplicate and is skipped.
</Step>
<Step title="Enqueue for processing">
The webhook handler enqueues to the `transaction-event-handling` SQS queue (`created` → `TRANSACTION_CREATED_EVENT_HANDLING`, `updated` → `TRANSACTION_UPDATED_EVENT_HANDLING`) and returns `{ message: "Transaction received" }` immediately. `QueueConsumerService.handleTransactionEvent` drains the queue and calls `processTransaction(eventData, eventType)`.
</Step>
<Step title="Persist loans and transactions">
`processTransaction` runs staged work (the `currentStage` string drives error reporting):

- **fetch-transaction** — `getTransactionByResourceRef`. For `created`, if a different EPC transaction already exists for this loan, the new one is canceled (`cancelTransaction`).
- **resolve-client** — `ensureClientExists(clientId, token)`. New clients are only auto-created if in the hard-coded `CLIENT_ALLOW_LIST` (LoanLight/ICE/Red Palm test accounts; `LOA-212` tracks removing this). Otherwise the client resolves to null and the run fails.
- **initialize-record** — upserts `loan` + `transaction_record`; back-links `epc_event.transaction_record_id`.
- **initialize-audit** — inserts `transaction_state` and upserts `audit_details` to `Processing`. `transactionStateId = transaction_state.id` becomes the `correlationId`.
</Step>
<Step title="Upload documents to S3">
**fetch-and-upload-documents** — `filterDocuments` splits the EPC resource list into the MISMO XML (required), supported docs (PDF/JPEG/PNG/TIFF/TXT/DOCX/DOC), and unsupported. Each is downloaded (`downloadResource`, base64, 400 MB cap, 2-min timeout) and uploaded to S3 with content-hash dedup. The MISMO XML is mandatory — a missing XML throws.

Recognized MISMO formats (finite `getMismoFormatPriority`) compete for the one MISMO slot; any `application/xml` with an `Infinity` priority or no recognized format is routed to a **`passthroughXml`** bucket (LOA-1673). When the `appraisal_passthrough` lender feature (`APPRAISAL_PASSTHROUGH_FEATURE_KEY`) is enabled, that passthrough XML is downloaded and stored as a non-MISMO opaque document (`is_mismo=false`) and rides into `AuditDocumentInfo[]` automatically. Gate errors are non-fatal: the XML is omitted but the critical MISMO/PDF audit always proceeds. Default off — enable per-lender via a `lender_feature` DML insert.

**finalize** writes the `{correlationId}/metadata.json` manifest plus a non-blocking transaction-history snapshot. See [S3 layout](/storage/s3-layout).
</Step>
<Step title="Publish Audit Requested">
**publishAuditRequestedEvent** publishes the "Audit Requested" EventBridge event (Source `loanlight.encompass`) carrying `correlationId`, `requestorId` (the client `providerClientId`), `environment`, `s3Bucket`, `s3Prefix`, decoded `loanMetadata`, `requestingParty`, and `documents[]`. This is the handoff to loanlight-api / AUS. See [Messaging](/integrations/messaging).

The service then PATCHes Encompass back to `Processing` / partnerStatus `Processing`, sets `referenceNumber = correlationId`, and sets the loan extension `loanLightAusHasBeenRun = "STARTED"`. An optional shadow fan-out runs here if enabled (see [Shadow audits](/integrations/shadow-audits)).
</Step>
<Step title="Consume AUS progress and results">
The AUS publishes EventBridge events (Source `loanlight.aus`). The `AusUpdateRule` routes an allow-list of detail-types to the `handle-aus-updates` SQS queue, drained by `QueueConsumerService.handleAusUpdate`:

- `workflow:complete` → terminal handler with `auditState: Complete`.
- `workflow:error` → `auditState: Error` (recoverable). `DUPLICATE_AUDIT` is ignored. Skipped if already in a final state.
- `workflow:start` → resets `audit_details` to `Processing`; shadow runs are skipped.
- progress / `document_processing:*` / `agent:*` → `updateAuditProgress(...)`, which drives the frontend progress bar.
</Step>
<Step title="Render the AUS Report PDF">
`AusUpdateService.handleAusUpdate` is the terminal handler. It loads `transaction_state` + client + `transaction_record`, applies the shadow guard, updates `audit_details`, and generates the PDF via `AuditReportPdfService.generate(...)`. That fetches results from loanlight-api (`AuditResultsFetcherService.fetchV2Inputs`) and renders with the [audit-pdf library](/integrations/audit-pdf). On a non-`Complete` state, or missing identifiers/token/fetch error, it renders a NULL_SECTIONS status PDF.

`fetchV2Inputs` uses **per-endpoint timeout semantics** (LOA-2294): `results` and `property_data` are fatal (a timeout throws and requeues the SQS message), while `urla_completeness` and `credit` degrade to a null section. This is the right tradeoff because `results` alone populates the summary, `dataConsistency`, and `documentHealth` sections — losing it leaves the report empty in every meaningful respect — and `property_data` drives the split path's per-property PDF output. A degraded section is logged at error level as `audit_data.fetch.section_degraded` and never silently swallowed.
</Step>
<Step title="PATCH the report into Encompass">
The PDF is uploaded to Encompass as a resource (`EpcService.createDocumentResources` → generate streaming URLs → PUT bytes → resource refs), then the EPC transaction is PATCHed:

- **Complete** — status `completed` / partnerStatus `Complete`, attaches the PDF, sets `loanLightAusHasBeenRun = "COMPLETED"`, emits a `ReportComplete` service event. Local `transaction_state` is updated to `completed` (3× retry).
- **Error (recoverable)** — uploads the report but keeps Encompass status `Processing` so the user can retry; no `errors[]`.
- **Failed (terminal)** — status `failed`, `loanLightAusHasBeenRun = "FAILED"`, includes `errors[]`. Only when Encompass explicitly fails.
</Step>
</Steps>

## Delivery modes

`AusUpdateService` decides delivery shape from the lender's **`document_push` feature flag** (`DOCUMENT_PUSH_FEATURE_KEY` on the `lender_feature` table). `resolveDocumentPushGate` resolves the lender for the transaction and reads the flag. A DB error throws (fail-loud — an opted-in lender is never silently downgraded to the combined path); an unmapped client is simply not enabled.

<Tabs>
<Tab title="Combined (default — flag OFF)">
One AUS Report PDF is generated via `deliverComplete`. No property PDFs, no document-push routing. This is the default for every lender until the `document_push` flag is enabled.

In the common case the report is attached in a **single** Complete PATCH. When `aus_results` and `appraisal_review_summary` both resolve to the same Encompass eFolder (a lender-overridable `nameTemplate` applies to each), `deliverComplete` batches into multiple PATCHes to prevent Encompass silently orphaning the earlier document into the loan’s default folder (LOA-2230, third in the LOA-2207 collision stack). Batches are separated by resource type via `deliveryBatchIndexByType` / `partitionIntoBatches` — the same utilities used on the split path.

Batch throw semantics differ from the split path deliberately:

| Case | Behaviour |
|---|---|
| Single batch, PATCH unconfirmed | Throws — SQS/DLQ retries. Safe because nothing was attached, so a retry attaches once. |
| Multiple batches, any PATCH unconfirmed | Does **not** throw. Logs a `split_delivery_degraded` event and returns. The local `transaction_state` is left un-completed if the terminal batch is unconfirmed; `findStuckCompletedDeliveries` will pick it up. If the terminal batch confirmed, local state is written to `completed`. |

When zero resources are present (LOA-1003: a missing document must not fail the audit), the batching produces no non-empty batches; an explicit fallback sends a bare terminal Complete so the audit is not left un-completed.
</Tab>
<Tab title="Routed (flag ON — LOA-948)">
When `document_push` is enabled and the audit state is `Complete`, `deliverSplit` generates one main AUS PDF plus one PDF **per property**. Both the AUS report and each property PDF are routed through the table-driven `document_push_routing_config` via `buildRoute` — the same routing table used for classified document delivery. Each property lands in its own eFolder container named from its address (identical addresses collapse per the EPC-1379 duplicate rule). All files are stored in S3 under `audit-deliveries/{transactionStateId}/`.

Since LOA-989 (#497), document upload is **fail-soft per document**: network errors and HTTP 429 → up to 4 attempts (exponential backoff with 50%–100% jitter via `retryWithBackoff`); all other error classes fail fast. A dropped upload no longer requeues the whole batch. The audit status and completion message **never** change based on document streaming — the terminal PATCH always uses the normal `Complete` / `ReportComplete` status, attaching whichever core documents uploaded. If zero core documents upload, the completion PATCH is skipped entirely (recovery via LOA-1730 manual re-attempt).

One `audit_delivery_log` row per planned core document (`aus_report` / `property`) is upserted **before** the terminal PATCH, keyed on `(transaction_state_id, file_name)`, recording `status = 'delivered'` or `'failed'` and the retry count. A non-full delivery emits a `split_delivery_degraded` structured Datadog log (event key, failed/total counts, error classes, and missing document kinds — never file names, which embed borrower addresses). The path still fails loud on a missing or inapplicable routing config.

The `audit_delivery_mode='split'` column and its trigger (LOA-970) are retired in favor of this flag-based routing. The dead durable-pipeline scaffolding (`epc-delivery` package, `epc_delivery_records` table, migrations 010/011) was **removed** in migration 022 (LOA-1678, integrations PR #499). The `audit_delivery_mode` column is retained as a legacy artifact.

#### Delivery decisions (LOA-1980)

Every document going through the routed path receives a `delivery_decision` — one of four values — before any EPC upload happens. The decision is recorded on `document_push_record.delivery_decision` so each push record is a permanent audit trail of why a document was or was not filed:

| Decision | Meaning |
|---|---|
| `new` | Not yet filed in Encompass → delivered to its routed folder |
| `refile` | Filed, but in the wrong folder → a correctly-named copy delivered to the right folder (Encompass cannot move files, so the lender's original remains where it is) |
| `skip_already_filed` | Already sitting in its routed folder → nothing delivered |
| `skip_duplicate_delivery` | A previous audit run already put this exact content in that folder → nothing delivered |

The decision comes from two independent checks run in order:

1. **Live check** — compares `transaction_document.assigned_container_name` (the folder the document was in at ingestion) against the routed container name. A name match → `skip_already_filed`. Because the container name is re-read from Encompass on every ingestion, this check self-heals across re-audits when a lender re-files a document between runs.
2. **Content ledger** — searches `document_push_record` for a prior row on the same transaction that delivered this exact content hash (`content_hash`) to the same folder. A match → `skip_duplicate_delivery`. This backstops the one case the live check cannot handle: a document that was originally filed in the wrong folder and then re-filed by LoanLight. Encompass cannot move the original, so the live check would keep saying "wrong folder" on every subsequent re-audit; the ledger recognizes that the content already exists in the correct folder and skips.

Whole documents — segments that are the entire source PDF — carry an Encompass container name and a content hash and therefore go through both checks normally. A segment is a whole document when its page range is null (degraded rows from `buildDegradedSegment`) **or** when its range spans every page (`pageStart === 1 && pageEnd === totalPages`). The latter is the common case: `majority_collapse` and `two_pass_resolved` emit concrete `1..totalPages` ranges for full-document segments, not null ranges. Prior to LOA-2208 (#529), only null ranges were recognized, so full-range whole-document segments from `majority_bucket` lenders were treated as carved splits, bypassing the skip / re-file / dedup checks on every re-audit. The fix corrects this.

Carved splits arrive with no container name and no content hash, so they fall through both checks to `new` — correct, since a split has no original Encompass counterpart to duplicate.

The `document_push_record.content_hash` column (migration 026) is the ledger key; `transaction_document.assigned_container_name` (migration 025) supplies the live check. Both columns are NULL on rows predating the feature.

#### Atomic delivery claims (LOA-2031)

Both de-dup checks are “read — decide — write” with S3 fetch and EPC push in between. On a standard (non-FIFO) SQS queue with multiple concurrent workers, two workers can both observe “not yet delivered” and both push. The `document_delivery_claim` table (migration `027`) closes this window.

Before the first external call the push service takes a claim for each `(transaction_record_id, claim_key, container_norm)` via INSERT … ON CONFLICT. If a claim is already `in_flight` or `delivered`, the new worker skips the document rather than double-filing it. Three claim states:

| State | Behavior |
|---|---|
| `in_flight` | Held by a live worker; blocks other claimants until `lease_expires_at` |
| `delivered` | Push reached `attached`; blocks permanently |
| `failed` | Push failed; immediately reclaimable by the SQS retry |

The lease is **shorter** than the SQS visibility timeout (600 s vs. 900 s, with a δ larger than the worst-case receive-to-acquire delay). When a worker is SIGKILL’d mid-push its claims expire before the redelivered message is picked up, so the retrying worker always finds expired claims and can re-acquire them.

The split materializer gains the same semantics via migration `028`: `state`, `claimant_id`, `lease_expires_at`, and `attempts` are added to `materialized_split_record`. Existing rows are backfilled to `state = 'delivered'`.
</Tab>
</Tabs>

## Failure handling

- On any failure after `transactionStateId` is set, `processTransaction` publishes a `workflow:error` EventBridge event (Source `loanlight.aus`, errorCode `TRANSACTION_PROCESSING_FAILED`, errorStep `transaction_processing`) so `audit_details` and the UI reflect the failure. These errors are treated as **recoverable** — the user can retry.
- A stuck-audit cron (`@Cron(EVERY_5_MINUTES)` plus on-startup) resets audits stuck in `Processing` for over 30 minutes to `Error` (recoverable, errorCode `INTERRUPTED`, errorStep `system_recovery`). Shadow rows are excluded.
- `POST /integrations/admin/trigger-recovery` runs recovery manually when `ENABLE_ADMIN_ENDPOINTS=true`.

For the events and queues referenced here, see [Messaging](/integrations/messaging). For the persisted state, see [Integrations database schema](/integrations/database-schema).
