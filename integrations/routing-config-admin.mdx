The integration service exposes a secured admin API for managing the EPC document-routing config — the global default rule set and per-lender overrides that decide which Encompass eFolder a classified document lands in. It is served by `RoutingConfigAdminController` and backed by the [`document_push_routing_config` table](/integrations/database-schema). Authoring or editing a lender's rules is pure DML against that table, never a schema migration (LOA-1188).

The controller base path is `integrations/routing-config`. There is **no global route prefix** — every path below is literal.

## Auth

Every route is guarded by `InternalApiKeyGuard`. This API is internal, server-to-server only; it is not reachable through the public API Gateway.

- The caller sends the shared secret in the `x-internal-api-key` header. The guard reads `INTERNAL_API_KEY` (trimmed) and compares with `crypto.timingSafeEqual`.
- **Fail-closed**: an unset or blank `INTERNAL_API_KEY` returns `401` even with a matching header. A missing, blank, or array-valued header returns `401 "Missing internal API key"`; a length or value mismatch returns `401 "Invalid internal API key"`.
- The optional `x-acting-user-id` / `x-acting-user-email` headers are **logged only** (they appear in the `routing_config_authored` / `_activated` / `_deactivated` audit log lines); they are not part of authorization.

## Endpoints

`:orgId` is a **WorkOS org id**, mapped to a `lender.id` via `lender.workos_org_id`. `:version` is parsed with `ParseIntPipe`.

| Method & path | Action |
|---|---|
| `GET /integrations/routing-config/global` | The global rule set: active version, `defaultContainer`, rules, and version history. |
| `POST /integrations/routing-config/global/versions` | Author a new global version. Body is `AuthorVersionDto`. Returns `{ version, ... }`. |
| `POST /integrations/routing-config/global/versions/:version/activate` | Activate a global version. Returns `{ activated: version }`. |
| `POST /integrations/routing-config/global/deactivate` | Deactivate the active global version. Returns `{ deactivated: true }`. |
| `GET /integrations/routing-config/lenders` | List lenders with their active routing version. |
| `GET /integrations/routing-config/lenders/:orgId` | A lender's overrides and history. Query `includeGlobal` and `resolve` (both `"true"`) add the global rule set and the resolved effective rules. |
| `POST /integrations/routing-config/lenders/:orgId/versions` | Author a new per-lender version. Body is `AuthorVersionDto`. |
| `POST /integrations/routing-config/lenders/:orgId/versions/:version/activate` | Activate a per-lender version. Returns `{ activated: version }`. |
| `POST /integrations/routing-config/lenders/:orgId/deactivate` | Deactivate the lender's active override. Returns `{ deactivated: true }`. |

### Request body

The author endpoints take `AuthorVersionDto`:

```ts
interface AuthorVersionDto {
  rules: unknown;          // the routing rule set (dynamic jsonb)
  activateOnCreate?: boolean; // default false
}
```

`rules` is dynamic jsonb, so the global `ValidationPipe` is intentionally a no-op for these bodies — the service validates the payload shape itself.

### Rule shape

Each rule in a global rule set maps a `classificationType` to a `RoutingRule`:

```ts
interface RoutingRule {
  classificationType: string;
  nameTemplate: string;          // Encompass eFolder name
  typeTemplate: string;          // EPC container-matching key (system-controlled, not lender-overridable)
  descriptionTemplate?: string | null;
  fileNameTemplate?: string | null; // EPC file (resource) name — LOA-1958 (see below)
  requiredFields: string[];
  onMissingFields: "fallback_to_default_container" | "degraded";
}
```

Per-lender overrides (`LenderRoutingOverride`) can customise `nameTemplate`, `descriptionTemplate`, and `fileNameTemplate`. All three are three-state: absent → inherit global; `null` → explicitly clear (fall back to default); string → override.

**`fileNameTemplate` (LOA-1958):** controls the EPC *file* (resource) name pushed to the Encompass eFolder, independent of the folder `nameTemplate`/`descriptionTemplate`. Supports the same field placeholders as `nameTemplate` plus optional `[...]` segments (a bracketed segment is omitted entirely when its placeholder values are empty, rather than leaving a blank slot). When absent or null on both the global rule and the lender override, the service falls back to a type-based default name. The resolved file name (before extension) is available in `RoutingDecision.fileName` for observability logging.

**Generated document types (LOA-1975):** three classification types produced by LoanLight itself — `aus_results`, `property_report`, and `appraisal_review_summary` — never receive a `fileName` from the resolver, regardless of any configured `fileNameTemplate`. Their file names come from the generation step itself. The resolver returns `DocTypeView.renamable = false` for these types; the portal routing config editor uses this flag to hide the file-name field for them. A `fileNameTemplate` typed into the raw JSON editor is silently inert for these three types.

### Bucket routing tier (LOA-2463)

Phase 2 of the classify-failed routing strategy. When Phase 2 classification produces no usable `classificationType` (`"unknown"`), the resolver can fall back to the coarse Phase 1 split bucket (`BUSINESS`, `INCOME`, `PROPERTY`, etc.) to pick a destination folder rather than always collapsing into manual review.

**How it works.** `resolveRouting` runs this tier **before** the classification lookup — not as a fallback after it. The reason: `"unknown"` is itself a seeded rule in the global config, so a `config.global["unknown"]` lookup returns `mapped` and the `!globalRule` branch is never taken for classify-failed documents. A post-lookup fallback would be unreachable in production.

Four conditions must all be true for the tier to fire:

1. The lender's `bucket_routing` feature flag is enabled (default off; LOA-2554).
2. `classificationType === "unknown"` — a successfully classified document keeps its own rule even when its bucket is known; a `paystub` is never routed as "Income".
3. The Phase 1 split bucket is non-null, non-blank, and not `UNKNOWN` — genuinely un-typeable documents collapse into manual review, deliberately.
4. A rule is configured for that bucket in `bucketRules` — the shipped state has none.

If any condition fails, the tier returns null and the resolver falls through to the normal classification tier.

A new `BucketRoutingRule` shape lives alongside the global rules on `RoutingConfig`:

```ts
interface BucketRoutingRule {
  // The map key IS the bucket — no separate `bucket` field (LOA-2465).
  nameTemplate: string;         // must be a non-blank literal — no {{field}} placeholders
  typeTemplate: string;         // must be a non-blank literal — no {{field}} placeholders
  descriptionTemplate?: string | null;
  fileNameTemplate?: string | null;
}

interface RoutingConfig {
  // ... global, lenderOverrides ...
  bucketRules?: Record<string, BucketRoutingRule>; // bucket key → rule
}
```

<Note>
The `bucket` field was removed from `BucketRoutingRule` in LOA-2465 — the map key is the canonical bucket value (`"PROPERTY"`, `"INCOME"`, etc.) and no rule body can disagree with it. A payload that still carries a `bucket` field is rejected with `400 invalid_routing_config`.
</Note>

`bucketRules` is a **sibling field** on `RoutingConfig`, not extra keys in `global` — the two vocabularies are different and merging them would let an incoming `classificationType` collide with a bucket key. The validator **rejects** `requiredFields`/`onMissingFields` on bucket rules rather than ignoring them — those policies have no meaning when per-document metadata cannot be relied on.

**`nameTemplate` and `typeTemplate` must be non-blank string literals** (no `{{ }}` placeholders). These two fields are the container's identity, and this tier only fires when document metadata is unreliable, so requiring literals makes both a blank render and a placeholder collapse structurally impossible. `descriptionTemplate` and `fileNameTemplate` may still use placeholders.

The resolver emits a new routing outcome `bucket_fallback` (a success outcome) when this tier routes a document. It logs a distinct line so monitoring can distinguish it from the existing failure paths.

**Per-lender opt-in (LOA-2554).** The bucket tier is **gated by the `bucket_routing` per-lender feature flag** (default off). Documents for a lender whose flag is off fall through to today's behaviour regardless of whether bucket rules are seeded globally. Enable via the [feature-flags admin API](/integrations/feature-flags-admin). Leave off until the lender's bucket destinations are confirmed; once on, the tier preempts any lender-scoped `unknown` override for documents it covers (see preemption advisory below).

**Preemption advisory.** When a lender has a per-lender override on the `"unknown"` classification type _and_ at least one bucket rule is seeded globally, `GET /integrations/routing-config/lenders/:orgId?resolve=true` includes an advisory warning naming the configured buckets. This does not change how documents route; it signals that the bucket tier takes precedence over the `unknown` override for any classify-failed document whose split bucket is covered. The warning is silent when `bucketRules` is empty (current shipped state), when no `unknown` override is configured, or when `unknown` has no active global rule (and the dead-key warning already fires).

**Shipped inert.** No `bucketRules` are seeded. Every document falls through to today's behaviour until LOA-2464 seeds the first bucket rules.

## Error responses

| Status | Body | When |
|---|---|---|
| `409` | `{ code: "LENDER_NOT_PROVISIONED", message }` | The `:orgId` does not resolve to a provisioned lender. |
| `409` | `{ code: "ACTIVATION_CONFLICT", message }` | The activation conflicts with the one-active-per-scope invariant. |
| `400` | `{ error: "invalid_routing_config", message }` | The submitted `rules` payload fails validation. |
| `404` | `{ error: "version_not_found" }` | The requested version does not exist. |

<Note>
Only the `409` responses carry the structured `{ code, message }` shape. `400` and `404` use the `{ error, ... }` shape. Octy and loanlight-api map these codes to their own UI/telemetry.
</Note>

## Transport

Octy and loanlight-api reach this API server-to-server over the integrations **internal NLB**, not the public gateway. The NLB has a `:443` TLS listener and is addressed at `https://integrations-internal.{zone}`; both callers' ECS security groups are admitted on TCP 443. The `INTERNAL_API_KEY` is delivered to the integrations ECS task as a secret from Secrets Manager (`LLIntegrations/INTERNAL_API_KEY`). See [Integrations infrastructure](/integrations/infrastructure).
