`audit-pdf` (workspace package `audit-pdf`, in `packages/audit-pdf/`) is a pure TypeScript library that renders the **AUS Pre-Underwriting Analysis PDF** and per-property detail PDFs from audit results. It has no NestJS dependency and is imported by the encompass service's `AuditReportPdfService`.

It uses `pdfmake` for document layout and `pdf-lib` for merging. The report font is **Roboto** (TTFs embedded from `pdfmake`'s bundled assets; `bold` maps to Roboto Medium, not a dedicated bold weight).

<Note>
This is a different PDF path from the one in loanlight-api. The loanlight-api [audit report PDF](/storage/pdf-reports) renders per-agent reports with Handlebars + Puppeteer and pushes them to the LOS. The `audit-pdf` library here renders the consolidated AUS Report that the EPC integration delivers into the Encompass transaction. They are separate engines.
</Note>

## Public API

The package exports from `src/index.ts`:

| Function | Purpose |
|---|---|
| `generateAuditPdfV2(input: GenerateAuditPdfV2Input)` | Render the main AUS report. |
| `generatePropertyPdf(input: GeneratePropertyPdfInput)` | Render one property's detail pages (subject + related + comparables) from `GetPropertyDataResponse`, with optional listing screenshots. |
| `combinePdfs(...)` | Merge audit + property PDFs (used in the combined-delivery path). |

Exported types: `AuditState`, `AuditErrorDetails`, `AuditSectionsInput`, `GenerateAuditPdfV2Input`, `GeneratePropertyPdfInput`.

### generateAuditPdfV2

The main entry point. Input shape:

```ts
interface GenerateAuditPdfV2Input {
  auditState: AuditState;            // Processing | Complete | Failed | Error
  sections: AuditSectionsInput;      // see below
  errorDetails?: AuditErrorDetails;
  hasAccompanyingAppraisalReport?: boolean; // LOA-2094
}
```

`hasAccompanyingAppraisalReport` is set when both delivery paths (split and combined) successfully fetch the Appraisal Review Summary PDF bytes before generating this report. When `true`, the body all-clear banner and the `auditSubtitle` scope their claims to the checks this report covers and direct the reader at the companion document — the AUS report has no appraisal input, so an unqualified "all validations passed" would contradict an accompanying appraisal PDF that carries findings. When `false` or absent the wording is byte-identical to before LOA-2094. The flag keys on fetched bytes, not file presence — a post-fetch streaming drop in Encompass can leave the banner referencing an unfiled document, alarmed via `appraisal_banner_orphaned`.

`AuditSectionsInput` carries the six core report sections:

```ts
interface AuditSectionsInput {
  summary;
  dataConsistency;
  documentHealth;
  check1003;
  propertiesCheck;
  credit;
}
```

Business Verification data is fetched separately (see below) and is not part of this interface.

The render order (exceptions-first) is:

1. Loan Details
2. Audit Summary
3. Important Expiration Dates (strip of expiration-only findings, before the full Document Health section)
4. 1003 Check
5. Document Health
6. Data Consistency
7. Credit Review
8. Property Review
9. Business Verification (when the agent ran and results are present — see [Business Verification section](#business-verification-section-loa-3276))

When the audit state is not `Complete`, or sections are missing, the encompass service passes the data through so the library renders a status / NULL_SECTIONS PDF rather than a full report.

### Header subtitle

`auditSubtitle(sections, hasAccompanyingAppraisalReport?)` emits the subtitle line below "Pre-Underwriting Analysis". It returns:
- `undefined` when `sections.summary` is null (status-only PDFs).
- `"All checks covered by this report passed. See the accompanying Appraisal Review Summary for appraisal findings."` when `issueCount === 0`, no exception sections have findings, **and** `hasAccompanyingAppraisalReport` is `true` (LOA-2094).
- `"All checks passed across analyzed documents."` when `issueCount === 0` and no exception sections have findings (no accompanying appraisal).
- `"Issues found across analyzed documents. Items in good standing are summarized, not listed."` otherwise.

The body all-clear banner (`buildAuditContent`) uses the same `hasAccompanyingAppraisalReport` flag: when `true` it prints `"No issues found in the checks covered by this report. See the accompanying Appraisal Review Summary for appraisal findings."` instead of `"No issues found. All validations passed."`

<Note>
Prior to the grouped-Document-Health redesign (#516), the subtitle keyed only on `summary.issueCount`. A loan with zero document issues but a FAILing credit or 1003 rule would falsely claim "All checks passed". The fix adds `exceptionSectionsHaveFindings(sections)` as a second gate so the subtitle is consistent with the report body.
</Note>

### Document Health section

Findings are **grouped by document type** (`documentType` field, falling back to the friendly display name). Each group occupies one or more rows in a table with a **Document (25%) / Status (15%) / Issue (60%)** column layout; the Document cell uses `rowSpan` to span all category rows within the group.

Category rows within a group appear in canonical order: missing → expiration → incomplete → unsigned. The issue cell content varies by category:

| Category | Status pill colour | Issue cell content |
|---|---|---|
| `missing` (1 instance) | Red — **Missing** | "Required by the loan program but not found in the loan file." |
| `missing` (multiple instances) | Red — **Missing** | Count header + bulleted list of instance names; dated bank-statement instances sorted newest → oldest. |
| `expiration` (expired) | Red — **Expired** | Document + dated clause + expired/on clause; requests a current document. |
| `expiration` (expiring soon) | Amber — **Expiring** | Document + dated clause + will expire/on clause; requests a renewal. |
| `incomplete` (bank statement) | Amber — **Incomplete** | Names the account and statement month; directs re-upload of all pages. |
| `incomplete` (other doc) | Amber — **Incomplete** | Generic re-upload directive. |
| `unsigned` | Amber — **Unsigned** | Wording by `signatureStatus`: `unsigned` / `partially_signed` / `verification_failed`. |

Group ordering: top band (missing or expired findings) first, then alphabetical by label.

The `document-health-model.ts` module owns group construction (`groupFindings`, `deriveCategories`, `parseMissingInstanceLabel`). `document-health-phrasing.ts` owns issue-cell and pill rendering (`buildIssueContent`, `categoryPill`, `expirationPhrase`, `incompletePhrase`, `unsignedPhrase`).

<Note>
The `required-documents.ts` module that existed before the grouped redesign has been removed. Its responsibilities (listing per-document status rows) are replaced by `document-health-model.ts` + `document-health-phrasing.ts`.
</Note>

### Credit section

The `credit` section (`{ data: CreditReportInput[] }`) renders one block per credit report
(loans usually have exactly one). Each `CreditReportInput` is
`{ status?, inputFilename?, extractedData?, complianceResults?, people? }`. A report with
neither extracted data nor compliance results (for example a pending run) is skipped.
Each block has:

- **Borrower Information table (LOA-3398).** When the report carries `people` (borrowers with
  identifying info), the section opens with a person-per-column table headed by each person's
  display name ("Borrower" or "Co-Borrower" as fallback; disambiguated with role or index when
  names repeat). Rows: Role/Occupancy, Name on report, Current address.
- A **bureau-score card** with columns **TransUnion**, **Experian**, **Equifax**,
  **Payments/mo.**, **Failed Rules**, **Warnings**. Scores are resolved per borrower by
  `borrower_id` tag (preferring tagged entries; positional fallback for legacy untagged data).
  A primary-borrower row is always shown; a co-borrower row is added when a second borrower
  carries identifying info.
- A **flagged-rules table** with columns **Rule**, **Result**, **Issue**. Rows render based on
  their `label` field (see [Check labels on sections](#check-labels-on-sections-loa-3298) below).
  The full `CreditRuleOutcome` set is `PASS`, `FAIL`, `WARNING`, `NEEDS_INFO`, `PENDING`, `SKIPPED`.
- A green note, `"{X} of {Y} credit rules passed."`, when the report has any compliance results.

### Loan Details card

The Loan Details card (`summary.loanDetails`, a `LoanDetails`) renders on a 6-column grid:

- **Row 1** (50/50 split): Borrower(s), Property — each spans 3 columns.
- **Rows 2–5** (even thirds): 12 remaining fields, 3 per row.

All values are pre-formatted display strings resolved by loanlight-api; an absent field renders as `—`.

| Label | Key |
|---|---|
| Borrower(s) | `borrowers` |
| Property | `propertyAddress` |
| Loan # | `loanNumber` |
| Loan Program | `loanProgramName` |
| Income Type | `incomeType` |
| Est. Closing Date | `estimatedClosingDate` |
| Purpose | `loanPurpose` |
| Occupancy | `occupancyType` |
| Loan Amount | `loanAmount` |
| Purchase Price | `purchasePrice` |
| Appraised Value | `appraisedValue` |
| Note Rate | `noteRate` |
| Rate Lock Status | `rateLockStatus` |
| Current Milestone | `currentMilestone` |

<Note>
`LTV / CLTV` was removed from the Loan Details card in the grouped-Document-Health redesign (#516). The fields (`ltv`, `combinedLtv`) still exist in `LoanDetails` and the API type, but the card no longer renders them.
</Note>

## Business Verification section (LOA-3276)

When the Business-Verification agent ran for a loan, `AuditReportPdfService` fetches results from
`GET /api/v1/audit_runs/:id/business_verification` and passes them to `buildAuditContent` as a
separate argument. The section is omitted when the agent did not run or its run was absent or skipped.

For each business in the result, the section lists:

- Business name and state of registration.
- Whether the lookup is for a borrower or for a vesting entity.
- Match confidence (the portal result labels and confidence level).
- When no match is found: the search details used (SOS query parameters).
- When a match is found: per-check results (verified, unverified, or could not verify) with
  short explanations.

State-record screenshots are included **only when the checks identify a matched record**. Rejected
or unmatched records do not include screenshots. Screenshots are rendered with a caption identifying
the source and capture timestamp.

When the run is `failed` or `pending`, the section states that nothing could be verified for that
business. A run that is absent or skipped is simply not rendered.

<Note>
The Coverage Appendix (a full per-check grid for every run) is not yet included in the PDF. It
depends on LOA-3145 and will be added in a later slice.
</Note>

The section is built by `audit/sections/business-verification.ts` in `packages/audit-pdf` and is
consumed by `AuditReportPdfService` in `packages/encompass`. Optional data fetching is gracefully
degraded: a fetch failure logs a warning and the section is omitted rather than failing the PDF
render.

**State filings in the PDF (LOA-3354).** When a business's lookup matched a record and the state returned filing documents, the PDF renders a filings block beneath that business's checks table (`filingsBlock`). The block lists:

- The oldest filing (labeled "Formation") — the last dated filing, or the last filing overall when none is dated.
- Up to five of the most recent filings (labeled "Most recent"), newest first.
- When more filings exist, a note: `and N more filing(s), listed in the portal.`
- A footer: `Filing links open the state's website.` followed by the lookup capture date.

Each filing name is rendered as a hyperlink (`link: f.url`) to the state's own page. Undated filings carry no positional label ("Formation" or "Most recent"), because without a date their order relative to others is unknown. The block is omitted for unmatched records, pending or failed lookups, and businesses with no filings returned.

## Property value sources (LOA-3272)

The property PDF's stats row (`buildStatsRow` in `property/property-content.ts`) labels every price by its data supplier. The API fields driving this — `estimateSource`, `listingSources`, `lastSold`, and `pricePerSqftDetail` — are read through a local `PropertyDataResponseWithSource` type that extends `PropertyDataResponse` from `@loanlight-engineering/shared-types`. This extension exists because the shared-types package version pinned by integrations consumers does not yet publish these fields.

| Stat column | Label shown | Source attribution shown |
|---|---|---|
| Listing estimate | `Zestimate` (when `estimateSource` is `zillow`) or `Redfin Estimate` (when `redfin`) | None — the column label names the site |
| Automated valuation | `Automated valuation (AVM)` | `N% confident` below the value when `avmConfidence` is present |
| List price | `List price` | `Zillow listing` or `Redfin listing` below the price when listed |
| Sale Price | `Sale Price:` | Source name below the price (`Zillow`, `Redfin`, or `Public records`) |

Key rules:

- The listing estimate column (`Zestimate` / `Redfin Estimate`) is hidden when `estimateSource` is ATTOM, null, absent, or unrecognized. When it is hidden the only valuation column is the AVM.
- The AVM column appears whenever `avmValue` is non-null, regardless of source. ATTOM is never named; its estimate surfaces here only.
- `listingSources.currentListing` determines the list price attribution. A missing `listingSources` defaults to Zillow because rows stored before Redfin support came from Zillow alone.
- Recording Date and Transfer Type in the last-sold block show only when `lastSold.source` is `attom` or the API sends no `lastSold` object (the pre-Redfin fallback to `transactions.lastSale`). They read N/A beside a Zillow or Redfin sale.
- Rent appears as `Stated rent (1003)`. ATTOM is never labeled anywhere in the rendered PDF.

## Subject listing screenshots (LOA-2989)

`GeneratePropertyPdfInput` accepts an optional `listingScreenshots: ListingScreenshot[]` field. When present, `buildPropertyContent` appends one captioned page per screenshot **after the subject property's findings** and nowhere else (not for related properties or comparables).

Each screenshot page carries a caption in the form:
```
<Zillow|Redfin> screenshot — Captured <MM/DD/YYYY HH:mm UTC> — <url>
```
where `<url>` is rendered as a live link. There is no standalone block heading; the caption names the artifact.

`AuditResultsFetcherService.fetchListingScreenshots(auditRunId, requestorId, token)` fetches screenshots from the API:

- Calls `GET /api/v1/audit_runs/:id/listing_screenshots` with a 15 s timeout covering the body read.
- Any non-2xx response (for example a 404 on an API build that does not have the route), timeout, network failure, or unusable body resolves to `[]` and logs `audit_pdf.listing_screenshots.degraded`. It never rejects.

In `AuditReportPdfService`, screenshots are fetched only when a `subject` row exists in the property data. On the combined-delivery path they are passed alongside property data; on the split-delivery path they are passed only to the subject property's PDF. If rendering with screenshots throws, the service logs `audit_pdf.listing_screenshots.render_failed`, drops the failing screenshot(s), and re-renders with the remainder. With no screenshots the call is byte-identical to the pre-LOA-2989 baseline.

`ListingScreenshot` is defined in `@loanlight-engineering/shared-types`:

```ts
interface ListingScreenshot {
  source: "zillow" | "redfin";
  capturedAt: string;  // ISO-8601; time of original capture, not of this read
  sourceUrl: string;   // the listing page screenshotted
  contentType: "image/png" | "image/jpeg";
  width: number;
  height: number;
  data: string;        // base64, no data: prefix; producer caps decoded size
}
```

## Check labels on sections (LOA-3298)

When a lender has the `pdf_check_labels` flag enabled, every section table renders rows using the
API's `label` field rather than legacy `hasIssue` / outcome heuristics. Two new modules in
`audit/` implement this:

**`label-selection.ts`** — `selectByLabel(row)` returns one of three values:
- `"skip"` — `label` is `null` (the API says there is nothing to show) or is `"passed"` or
  `"not_applicable"`.
- `"fallback"` — `label` is absent or blank (older payload predating labels); the caller applies
  its own pre-label filter.
- `"render"` — any other label, including unknown future labels, renders; hiding an unknown
  label could read cleaner than the audit, so it always shows.

`rendersRow(row, preLabelFilter)` combines both paths: returns the pre-label filter result when
`selectByLabel` is `"fallback"`, otherwise follows `selectByLabel`.

**`label-display.ts`** — defines display text and pill colours for the six known labels:

| Label | Pill colour | Text |
|---|---|---|
| `passed` | green | Passed |
| `failed` | red | Failed |
| `missing` | amber | Missing |
| `incomplete` | amber | Incomplete |
| `warning` | gray | Warning |
| `not_applicable` | gray | Not applicable |

Severity order (most severe first): `failed` → `missing`/`incomplete` (tied) → `warning` →
unknown labels → `not_applicable` → `passed`. An unknown label renders as a gray pill with its
own text. `groupLabel(labels)` picks the most severe known label in a group, or the first label
when all are unknown.

The "all-clear" banner and accompanying-appraisal-report handling that previously appeared in
`audit-content.ts` were moved to the API side; the `pdf_check_labels` mode no longer renders
them from the PDF library.

## EPC findings delivered alongside the PDF

The encompass service evaluates a set of **EPC findings** from the audit results
and pushes them to the Encompass transaction alongside the PDF. Findings are
defined in `packages/encompass/src/findings/definitions/`, each keyed by a
finding code.

### LL-Data-01 — data consistency (LOA-2829)

`LL-Data-01` fires when the loan file and supporting documents disagree on one
or more fields. It delivers **one finding per audit run** (never one per field)
listing every discrepancy.

- **Title:** `[LoanLight] N data discrepancies between the loan file and documents`
- **Body:** one line per discrepancy in the form
  `FAIL — Loan Amount (Co-Borrower): 1003 shows 412000; Note.pdf (p. 3) shows 410500.`
  `high` severity rows appear as FAIL; `medium` and `low` as WARNING. The list
  is capped at 25 lines with “…and N more”.
- **Masking:** taxpayer identifiers (SSN, ITIN, EIN, TIN) show only their last
  four digits. Dates of birth show no value.
- **PII suppression:** when the PII validation agent failed or never ran, the
  finding is suppressed — a failed PII run cannot be distinguished from a clean
  run that produced no mismatches.
- **Registration:** `LL-Data-01` is mapped on the Int EPC product only. On prod
  it is `not requested` and will be silently accepted and dropped by EPC if
  delivered. Enabled per lender by the `findings_data_consistency` flag
  (`auto` value).

The finding reads `dataConsistency` from `AuditSectionsInput` — the same
section the PDF renders in its Data Consistency section.

## How encompass consumes it

The encompass `AuditReportPdfService.generate(...)` orchestrates the render:

<Steps>
<Step title="Fetch the sections">
`AuditResultsFetcherService.fetchV2Inputs(auditRunId, requestorId, token)` pulls the sections from loanlight-api via four parallel calls (`Promise.allSettled`), each with retry/backoff: `GET /api/v1/audit_runs/{id}/results?includeNonIssues=true&includeEncompassLoanDetails=true`, `…/urla_completeness`, `…/property_data`, and `…/credit`. `includeEncompassLoanDetails=true` opts the `/results` response into the Encompass-only Loan Details fields (`incomeType`, `noteRate`); see [Results access](/integrations/results-access).
</Step>
<Step title="Render">
The assembled `AuditSectionsInput` plus `auditState` are passed to `generateAuditPdfV2`. For split delivery, `generatePropertyPdf` is called once per property and the outputs are stored individually (or merged via `combinePdfs` for the combined path).
</Step>
<Step title="Deliver">
The encompass service uploads the rendered bytes to Encompass and PATCHes the transaction. See [Audit lifecycle](/integrations/audit-lifecycle).
</Step>
</Steps>

For where the rendered PDFs land in S3 (split-delivery and shadow paths), see [S3 layout](/storage/s3-layout) and [Shadow audits](/integrations/shadow-audits).
