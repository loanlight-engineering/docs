LOA-1078 introduced a **unified external-service resilience layer** (`src/common/resilience/`) that protects every Reducto caller from vendor outages. When the circuit opens, work is parked rather than hard-failed; it drains automatically when Reducto recovers.

## What it protects

Six named **consumer lanes** call Reducto for document extraction: `appraisal_extract`, `appraisal_parse`, `appraisal_figures`, `bank_statement`, `credit`, and `ssr`. Each lane has its own circuit so a broken lane can stop itself without gating the healthy ones. A shared **vendor circuit** is the overall kill-switch: it opens only when cross-lane evidence confirms a fleet-wide Reducto outage rather than a single-lane problem.

- **Appraisal extraction** (`portal-appraisal` module) — uses lanes `appraisal_extract`, `appraisal_parse`, and `appraisal_figures`.
- **Bank-statement structuring** (`bank-statement-pipeline` module) — uses lane `bank_statement`.
- **Credit** and **SSR** — use lanes `credit` and `ssr` respectively.

## Lane isolation model (LOA-2777)

Every terminal failure is tagged with the caller's `ReductoConsumer` class. Two circuits are maintained in parallel:

| Circuit | Redis key | Opens when |
|---|---|---|
| **Vendor circuit** | `resilience:reducto:state` | 3 distinct PDFs fail **and** failures span ≥ 2 distinct consumer classes within 5 min. One lane cannot open this circuit alone. |
| **Lane circuits** (one per consumer) | `resilience:reducto:<lane>:state` | 3 distinct PDFs fail from **that lane alone** within 5 min. |

A lane-only failure parks only that lane's work. A vendor-circuit open parks all lanes simultaneously. Recovery probes against each circuit independently; the trial-release fence (`resilience:reducto:<scope>:trial-release`) prevents concurrent probes on the same circuit.

Thresholds (`reducto-terminal-policy.ts`):

| Constant | Value | Applies to |
|---|---|---|
| `REDUCTO_TERMINAL_FAILURE_THRESHOLD` | 3 | Both vendor and lane circuits |
| `REDUCTO_TERMINAL_FAILURE_WINDOW_MS` | 300 000 ms (5 min) | Both |
| `REDUCTO_TERMINAL_FAILURE_CLASS_SPREAD` | 2 | Vendor circuit — minimum distinct classes required |
| `REDUCTO_LANE_TERMINAL_FAILURE_CLASS_SPREAD` | 1 | Lane circuits — only the lane's own class counts |

## Circuit breaker

Each circuit uses the **cockatiel** library with a `consecutive` policy:

| Config | Value |
|---|---|
| `failureThreshold` | 2 consecutive vendor failures to open |
| `halfOpenAfterMs` | 60 000 ms (1 minute) before probing |
| `retryable` | based on `classifyReductoError` — transient vendor errors open the breaker; local errors (parse failures) do not |

Circuit state is persisted in Redis. The vendor circuit key is `resilience:reducto:state`; each lane's key is `resilience:reducto:<lane>:state` (e.g. `resilience:reducto:bank_statement:state`). A single `QueueAndRecoverOrchestrator` owns the recovery-driver timer (one per process; `.unref()`'d).

### Terminal-failure outage policy

The circuit breaker has a second opening mechanism independent of the consecutive policy: a **terminal-failure threshold**. `ReductoCircuitStore.recordTerminalFailure(documentHash, callClass?)` is called by the shared executor each time a distinct original PDF receives a `Failed` response from Reducto.

For the **vendor circuit**: when 3 distinct documents fail within the 5-minute window **and** the failures span at least 2 distinct `ReductoConsumer` classes, the vendor circuit opens immediately. A single lane failing 3 PDFs alone does not open the vendor circuit.

For a **lane circuit**: when 3 distinct documents tagged with that lane's class fail within the window, that lane's circuit opens. Evidence from other lanes does not count.

The `reducto-terminal-policy.ts` module owns the sliding-window accounting. `lifecycle.ts` exports `getReductoJobLifecycle` and `withReductoJobLifecycle` hooks used by test harnesses and the break-glass probe to override lifecycle behavior. The shared executor exposes `assertReductoCallAllowed()`, which callers invoke before submission to check either the lifecycle hooks or the relevant circuit store.

### Redis read outcomes and indeterminate state (LOA-2361)

`CircuitStore.readWithinBudget` (bounded by `CIRCUIT_REDIS_CONNECT_BUDGET_MS` = 1.5 s and `CIRCUIT_REDIS_COMMAND_TIMEOUT_MS` = 1.5 s) distinguishes four outcomes:

| Outcome | Meaning | Effect |
|---|---|---|
| Redis answered, key absent | Determinate — nothing persisted yet; legitimately closed | Circuit is closed |
| Redis answered, valid snapshot | Determinate — circuit state known | Apply the stored state |
| Redis answered, garbage (bad JSON / unexpected shape) | Determinate error — distinct from an unreachable store | Logged; circuit treated as closed (conservative) |
| Redis did **not** answer (timeout, connection refused, partition) | **Indeterminate** | Raises `CircuitStateUnavailableError` (subclass of `BrokenCircuitError`) |

Before LOA-2361, a Redis read failure (network partition, timeout) was treated as a clean "nothing persisted yet" — equivalent to a closed circuit. Work passed through even when the stored open/force_open state was inaccessible. Now, an unreadable store raises `CircuitStateUnavailableError`, which callers treat the same as an open circuit: work is parked rather than let through. The open-circuit path itself (`force_open`, deliberate stops) is unchanged.

`getReductoCircuitStore()` awaits the first Redis connection with a bounded budget and memoizes the readiness promise to avoid bootstrap races.

## Queue and recover

When the circuit is open (or `force_open` overridden), both adapters **park** incoming work rather than hard-failing it.

### Appraisal adapter

Parks `appraisal_runs` at `status = 'queued'` (migration `0239`). A partial-unique dedupe index `idx_appraisal_runs_queued_dedupe` prevents double-queueing the same run. On recovery, queued runs are drained oldest-first, bounded by `REDUCTO_DRAIN_CONCURRENCY`.

### Bank-statement adapter

Parks `borrower_files` at `status = 'queued'` (migration `0240`). Two columns added:

- `recovery_attempts integer NOT NULL DEFAULT 0` — incremented on each drain attempt.
- Partial-unique dedupe index `idx_borrower_files_queued_dedupe` (migration `0241`).

Drain uses a **fresh** `jobId` each time (not the stable `process-${id}`) to prevent BullMQ from silently deduping against a retained completed job. A **dual-gate reaper** fails terminal on either `recovery_attempts >= MAX` or `processing_started_at < now() - GRACE`, whichever fires first — preventing a borrower from being stranded forever.

The portal renders `status = 'queued'` as "Waiting on Reducto — will resume automatically" (amber, no stage bar) on both statement-analyzer pages.

## Break-glass control

```
POST /api/v1/portal/resilience/break-glass
```

Super-admin endpoint. Backed by `QueueAndRecoverOrchestrator.applyBreakGlass`. Body: `{ action: "force_open" | "force_closed" | "clear" }`.

| Action | Effect |
|---|---|
| `force_open` | Both adapters park all new work (no probe) |
| `force_closed` | Bypass the circuit and call Reducto **raw** — ⚠ do not use during an outage |
| `clear` | Remove the override and resume normal breaker behavior |

<Warning>
The old `POST .../appraisals/break-glass` endpoint is gone. Update any runbook or operator script that references the old path.
</Warning>

## Adding a third service

See `packages/api/docs/resilience-add-third-service.md` in `loanlight-api` for the step-by-step checklist. The guard test `only-reducto-has-live-breaker.spec.ts` is a merge-blocking census — it fails the moment a live breaker is wired somewhere unexpected. Update the `BREAKER_ALLOWLIST` in that spec when a new caller is deliberately added.
